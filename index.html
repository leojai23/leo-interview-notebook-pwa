Data Types, Storage Classes & Type Qualifiers

The vocabulary question set: what a type guarantees, where a variable lives, and how long it lives.

Notes

Fundamental types and their sizes

C guarantees only minimum ranges, not exact sizes. The standard promises 1 == sizeof(char) ≤ sizeof(short) ≤ sizeof(int) ≤ sizeof(long) ≤ sizeof(long long), with char at least 8 bits, short and int at least 16, long at least 32, long long at least 64. On the common LP64 model (Linux/macOS 64-bit): int 4 bytes, long 8, pointer 8. On Windows LLP64: long is 4. Use <stdint.h> (int32_t, uint64_t, intptr_t) when the width matters.

char may be signed or unsigned — it is implementation-defined. That is a classic bug source when using char to index a table with bytes ≥ 0x80.

Type qualifiers

  • const — the program will not modify this object through this name. Enables optimisation and lets the compiler catch mistakes. const objects with static duration can go in read-only memory.
  • volatile — the value may change outside the program's control (memory-mapped hardware register, variable touched by a signal handler or another thread). The compiler must not cache it in a register or elide reads/writes.
  • restrict (C99, pointers only) — a promise that this pointer is the only way the pointed-to object is accessed in its scope, so the compiler may keep values in registers across writes through other pointers.

Read declarations right-to-left: const char *p is “p is a pointer to char that is const” (data read-only, pointer rebindable); char * const p is “p is a const pointer to char” (pointer fixed, data writable).

Integer promotion and usual arithmetic conversions

Anything narrower than int is promoted to int before arithmetic. In a mixed signed/unsigned expression of the same rank, the signed operand converts to unsigned — so -1 > 0u is true. This bites in loops like for (size_t i = n-1; i >= 0; i--), which never ends.

Cheat Sheet
  • Sizes are minimums; use <stdint.h> for fixed width. sizeof(char) == 1 always.
  • char signedness is implementation-defined → use unsigned char for raw bytes.
  • Storage duration: static (whole program), automatic (block), allocated (malloc/free), thread (_Thread_local).
  • Linkage: external (default global), internal (static at file scope), none (locals).
  • static local = persistent + private; static global = file-private.
  • const = I won't write it. volatile = someone else might. They can combine: const volatile (read-only hardware status register).
  • Declaration reading: right-to-left / “spiral”. const char * vs char * const.
  • Mixed signed/unsigned compare → signed becomes unsigned. Beware backward size_t loops.
  • Uninitialised static/global → zero. Uninitialised automatic → indeterminate (garbage).
Q&A
Is sizeof(int) guaranteed to be 4?
No. Only ≥ 2 bytes and ≥ sizeof(short). It is 4 on most 32/64-bit desktop targets but 2 on some embedded ones.
What is the difference between static on a global and on a local?
On a file-scope variable/function it changes linkage to internal (invisible to other translation units). On a local it changes duration to static (value persists between calls); linkage is already none.
Where do const globals and string literals live?
Typically a read-only data segment (.rodata); writing to them is undefined behaviour and usually faults.
When do you actually need volatile?
Memory-mapped I/O registers, a variable shared with a signal handler (volatile sig_atomic_t), or a spin flag on bare metal. It is not a substitute for atomics/locks in multithreaded code.
What is the default value of an uninitialised local int?
Indeterminate. Reading it is undefined behaviour. Only static-duration objects are zero-initialised.
Why can register variables not have their address taken?
The whole point is to allow the compiler to keep them in a CPU register, which has no memory address.
Interview Questions

Basic warm-up

Name the storage classes in C and what each does.
auto (automatic duration, the default for locals), register (automatic, hint to keep in a register, address cannot be taken), static (static duration; internal linkage at file scope, persistent value for locals), and extern (static duration, external linkage — refers to a definition elsewhere).
What is the difference between const and #define for a constant?
#define is textual substitution by the preprocessor: no type, no scope, not visible to the debugger. const int has a type, obeys scope, is type-checked, and can be given internal linkage. Prefer const / enum for constants; use #define only when you need a compile-time constant expression in contexts like array sizes in C89 or conditional compilation.
What does sizeof return, and is it evaluated at run time?
It yields a size_t — the number of bytes of its operand's type. It is a compile-time constant for all normal types; the operand is not evaluated (e.g. sizeof(a++) does not increment a). The one exception is a C99 variable-length array, where sizeof is computed at run time.
Is char signed or unsigned?
Implementation-defined. It is a distinct type from both signed char and unsigned char. For portable byte manipulation use unsigned char.

Intermediate core

Explain the output: unsigned int a = 1; int b = -1; if (b > a) puts("yes");
It prints yes. In the comparison, the usual arithmetic conversions turn the signed b into unsigned int. -1 becomes UINT_MAX, which is greater than 1. This is why mixing signed and unsigned in comparisons is dangerous.
What is integer promotion and where does it apply?
Any operand of an integer type with rank lower than int (char, short, bit-fields, enum) is converted to int (or unsigned int if int can't hold all its values) before arithmetic, in function arguments to variadic/unprototyped functions, and for the operands of unary + - ~ and the shift operators. So char a=200, b=100; a+b is computed in int and is well-defined even though it overflows a char.
Give a real use of const volatile together.
A hardware status register that firmware can only read but whose bits change on their own, e.g. const volatile uint32_t *STATUS = (uint32_t *)0x40001000;. const stops the code writing it; volatile forces an actual bus read on every access so the compiler doesn't reuse a stale cached value.
What linkage and duration does a static function have, and why use one?
Internal linkage, static duration. It is invisible outside its translation unit, so it doesn't pollute the global namespace, can't collide with a same-named symbol in another file, and gives the compiler freedom to inline or drop it. It's the C equivalent of “private helper”.

Advanced deep

Does volatile make a variable safe to share between threads?
No. volatile only prevents the compiler from optimising away or reordering accesses to that variable. It provides no atomicity (a read-modify-write can still tear), no ordering guarantees for other memory, and no CPU memory barriers. Correct sharing needs _Atomic / <stdatomic.h> or a mutex. volatile's legitimate uses are memory-mapped I/O, sig_atomic_t flags, and setjmp/longjmp locals.
What is the restrict qualifier and what does the programmer promise?
Applied to a pointer, restrict promises that, for the lifetime of the pointer, the object it points to is accessed only through that pointer (or pointers derived from it). This lets the compiler assume no aliasing between, say, src and dst in a copy loop and keep values in registers across stores. Breaking the promise (passing overlapping buffers to a restrict API like memcpy) is undefined behaviour.
An int global is defined in a.c and used in b.c via extern. What happens if b.c instead writes int g; at file scope with no extern?
Both files now have a file-scope definition of g. Under the older “common symbol” model (default in many C compilers historically) the linker merges them into one object — it links but is fragile. Under the stricter C standard rule and modern compilers using -fno-common (now the GCC/Clang default), it is a multiple-definition link error. The correct pattern is one definition (int g = 0;) in exactly one .c and a declaration (extern int g;) in a shared header.

Pointers & Pointer Arithmetic

The topic that separates people who have used C from people who have read about it.

Notes

What a pointer is

A pointer is a variable whose value is an address. Its type tells the compiler the type of the object at that address, which drives dereferencing and arithmetic. int *p; declares p as “pointer to int”. &x takes the address of x; *p is the object p points to (an lvalue — you can read or assign it).

Pointer arithmetic is in units of the pointed-to type

int a[5] = {10,20,30,40,50};
int *p = a;        // &a[0]
p + 3              // address of a[3]  == (char*)p + 3*sizeof(int)
*(p + 3)           // 40   -- identical to p[3] and to a[3]
p[3] is defined as *(p + 3), so 3[a] is legal C and equals a[3]
&a[5]             // one-past-the-end: legal to form, UB to dereference

Subtracting two pointers into the same array yields a ptrdiff_t count of elements. Adding/subtracting or comparing pointers into different objects is undefined behaviour (except forming — not dereferencing — the one-past-the-end pointer).

Levels of indirection

int **pp is a pointer to a pointer to int. You need it to let a function modify the caller's pointer (e.g. allocate and hand back a buffer), or for a dynamically allocated “2-D” array built as an array of row pointers.

void make(int **out) {          // caller passes &ptr
    *out = malloc(10 * sizeof **out);
}
int *buf;
make(&buf);                       // buf now points to 10 ints

void * and function pointers

void * is a generic object pointer: any object pointer converts to it and back without loss, but you cannot dereference it or do arithmetic on it (GCC allows void* arithmetic as an extension, treating it as char*). malloc returns void *. Function pointers are a separate family — a void * is not guaranteed to hold one portably.

Null, wild, and dangling

  • Null pointer — compares equal to 0/NULL; dereferencing is UB (usually a segfault). Always check the result of malloc.
  • Wild pointer — uninitialised; contains garbage. Initialise to NULL.
  • Dangling pointer — still holds an address whose object has ended its lifetime (freed, or a local that went out of scope). Set to NULL after free.
Cheat Sheet
  • *&x == x; &*p == p (when p is valid).
  • p[i] ≡ *(p + i) ≡ *(i + p) ≡ i[p].
  • p + n moves n * sizeof(*p) bytes.
  • q - p = element count (ptrdiff_t), only valid within one array.
  • Array name decays to &array[0] in expressions — but not for sizeof, &, or a string-literal initialiser.
  • int *p, q; → q is an int, not a pointer. The * binds to the declarator.
  • Prefer sizeof *p over sizeof(int) in malloc — stays correct if the type changes.
  • After free(p): p = NULL;. Never free a pointer not from malloc/calloc/realloc, and never twice.
  • const position: const T * (pointee const) vs T * const (pointer const).
Q&A
What is the size of a pointer?
Implementation-defined; on a given platform all object pointers are usually the same size (4 bytes on 32-bit, 8 on 64-bit). void* and char* are guaranteed to have the same representation; function pointers may differ.
Difference between NULL, 0, and nullptr?
In C, NULL is a macro for a null pointer constant, typically ((void*)0) or 0. A 0 in pointer context is a null pointer constant too. nullptr is C++11 (and C23); it has a distinct type and avoids ambiguity in overloads/variadic calls.
Why does sizeof(arr)/sizeof(arr[0]) break inside a function?
The array parameter has decayed to a pointer, so sizeof(arr) is the pointer size, not the array size. You must pass the length separately.
Can you do arithmetic on a void *?
Not in standard C — the element size is unknown. GCC/Clang allow it as an extension, treating it like char *. Cast to char * for portable byte offsets.
What does int (*p)[10] mean?
“p is a pointer to an array of 10 ints.” p + 1 advances 40 bytes. Contrast int *p[10] = “array of 10 pointers to int”.
Interview Questions

Basic warm-up

What do & and * do?
&x yields the address of x (a pointer). *p dereferences p — it names the object at that address and can be used on either side of an assignment.
What is wrong with char *p; strcpy(p, "hi");?
p is uninitialised (a wild pointer); it points nowhere valid, so the copy writes to a random address — undefined behaviour. You need real storage: char buf[8]; strcpy(buf, "hi"); or char *p = malloc(8);.
Is arr the same as &arr?
They hold the same address but have different types. arr decays to int *; &arr is int (*)[N]. So arr + 1 moves one int; &arr + 1 moves the whole array.
How do you return an error and a value from a C function using pointers?
Return the status code and write the result through an out-parameter: int parse(const char *s, long *out);. The caller passes &value; the function fills *out on success.

Intermediate core

Why prefer p = malloc(n * sizeof *p) over malloc(n * sizeof(int))?
sizeof *p is always the size of whatever p points to, so if the type of p changes later the allocation stays correct and you can't get a mismatch. It also removes the need to name the type twice.
Explain the difference between const char *p, char * const p, and const char * const p.
const char *p: the characters are read-only through p, but p can be repointed. char * const p: p is fixed for its lifetime, but the characters are writable. const char * const p: both the pointer and the data are read-only.
What is pointer decay and where does it not happen?
In most expressions an array is implicitly converted to a pointer to its first element. It does not decay as the operand of sizeof, as the operand of unary &, or when used to initialise a char[] from a string literal. Function parameters written as arrays are silently adjusted to pointers.
How is a dynamically allocated 2-D array typically built, and how do you free it?
Either (a) a single block: int *m = malloc(rows*cols*sizeof *m); indexed as m[r*cols + c] — one free; or (b) an array of row pointers: int **m = malloc(rows*sizeof *m); then m[r] = malloc(cols*sizeof *m[r]); in a loop — free every row then free(m). Option (a) has better locality and one allocation.

Advanced deep

Is comparing two pointers with < always defined?
Only when both point into (or one past) the same array object or the same struct. Relational comparison of pointers to unrelated objects is undefined behaviour, even though it “works” on flat address spaces. Equality comparison (==, !=) is always defined. qsort-style code that needs a total order across arbitrary pointers should compare via uintptr_t.
What does the standard say about converting a pointer to an integer and back?
Any pointer can be converted to intptr_t/uintptr_t (if provided) and back, yielding a pointer that compares equal to the original. Conversions to smaller integer types are implementation-defined and may not round-trip. The bit pattern and whether the result is meaningful arithmetic is not guaranteed by the standard — only the round-trip.
Given int a[3][4];, what are the types of a, a[0], *a, &a[0][0], and a[1] - a[0]?
a → int (*)[4] (after decay). a[0] → int[4] decaying to int *. *a is a[0], same thing. &a[0][0] → int * to the very first element. a[1] - a[0] is a ptrdiff_t equal to 4 (elements), because both are int * into contiguous storage.

Arrays, Strings & Multidimensional Arrays

C strings are a convention, not a type — know exactly what that convention costs.

Notes

Arrays

An array is a contiguous block of N objects of one type. Its name is not a pointer, but decays to &arr[0] in most expressions. You cannot assign or pass an array by value; passing one to a function passes a pointer, losing the size. C99 adds variable-length arrays (VLAs) — array objects whose size is a run-time expression; they live on the stack and can blow it, so many code bases ban them.

C strings

A “string” is a char array containing a '\0' terminator. The length is found by scanning for that byte (strlen is O(n)). Every buffer must have room for the terminator: storing "cat" needs 4 bytes. The classic overflow is forgetting the +1.

char a[] = "cat";     // 4 bytes: 'c' 'a' 't' '\0'  -- modifiable
char *b   = "cat";     // pointer to a string literal -- read-only, writing is UB
sizeof a               // 4
strlen(a)              // 3

Prefer bounded functions: snprintf over sprintf; be careful that strncpy does not guarantee termination if the source is longer than n. strlcpy/strlcat (BSD, and now C23's strcpy_s family) are safer where available.

Multidimensional arrays

int m[3][4] is “array of 3 arrays of 4 ints”, stored row-major and fully contiguous (48 bytes). Indexing m[i][j] is *(*(m + i) + j). When passed to a function, all dimensions except the first must be known: void f(int m[][4], int rows). Contrast an “array of pointers” char *argv[], where each element is a separately located string and rows can have different lengths — this is what main's argv is.

Common bugs

  • Off-by-one: looping i <= n instead of i < n.
  • sizeof(arr) inside a function (pointer size, not array size).
  • Returning a pointer to a local array (dangles once the function returns).
  • Comparing strings with == (compares addresses); use strcmp.
  • Assuming char buf[64] from fgets has no trailing '\n'.
Cheat Sheet
  • Buffer size for a string of visible length L is L + 1.
  • sizeof arr = total bytes; sizeof arr / sizeof arr[0] = element count (only where arr is a real array).
  • strlen is O(n); cache it, don't call it in a loop condition.
  • strcmp returns <0 / 0 / >0, not a boolean.
  • strncpy(d, s, n): pads with \0 if s is short, but does not terminate if s has ≥ n chars.
  • Use snprintf(buf, sizeof buf, ...) and check the return (it's the length that would have been written).
  • 2-D array param: int m[][COLS]. Array-of-pointers: char *rows[].
  • String literal → const in spirit; assign to const char *. Never modify.
  • VLAs: legal C99, stack-allocated, no size check — avoid for untrusted sizes.
Q&A
Difference between char s[] = "hi" and char *s = "hi"?
The first copies the 3 bytes into a local, modifiable array. The second makes s point at a (usually read-only) string literal; modifying it is UB and s can be repointed.
How do you find the length of an array passed to a function?
You can't from the pointer alone — pass the length as a separate argument, or use a sentinel value, or wrap pointer+length in a struct.
Why is if (str == "yes") wrong?
It compares two pointers for address equality, which is almost never what you want. Use strcmp(str, "yes") == 0.
Is a[i] ever different from *(a + i)?
No — they are defined to be identical, including the commutative i[a] form.
What does strncpy not do that people assume it does?
It doesn't guarantee a null terminator when the source length is ≥ n. You must set dst[n-1] = '\0' yourself or use a safer API.
Interview Questions

Basic warm-up

How is a string represented in C?
As a contiguous array of char ending in a null byte '\0'. There is no length field; functions find the end by scanning for the terminator.
What will sizeof("hello") give?
6 — five letters plus the null terminator. (strlen("hello") is 5.)
Can you assign one array to another with =?
No. Arrays are not assignable. You copy element by element or with memcpy. (A struct containing an array can be assigned, which copies the array.)
What's the risk in gets(buf)?
It has no way to know the size of buf, so any input longer than the buffer overflows it. gets was removed from the C standard in C11. Use fgets(buf, sizeof buf, stdin).

Intermediate core

Why must all but the first dimension be specified when passing a 2-D array?
Indexing m[i][j] compiles to *( (int*)m + i*COLS + j ). The compiler needs COLS (and any further dimensions) to compute the row stride. The first dimension is just a count and isn't needed for addressing.
Contrast int m[3][4] with int *m[3] in memory.
int m[3][4] is one contiguous 48-byte block, row-major, no pointers stored. int *m[3] is three pointers (24 bytes on 64-bit) that you must each point at separately allocated rows; rows can be non-contiguous and of different lengths. The first has better cache behaviour; the second is more flexible (jagged arrays).
Write a safe copy of a C string into a fixed buffer.
int n = snprintf(dst, sizeof dst, "%s", src);
if (n < 0 || (size_t)n >= sizeof dst) {
    /* truncated -- handle as error */
}
snprintf always null-terminates (given size > 0) and its return tells you whether truncation happened.
What's undefined about char *f(void){ char b[4]="abc"; return b; }?
It returns the address of a local array whose lifetime ends when f returns. Any use of the returned pointer is a dangling-pointer access (UB). Fix: make b static, allocate with malloc, or have the caller pass in a buffer.

Advanced deep

Is int m[3][4]; int *p = &m[0][0]; p[10]; well-defined?
Contentious. The whole object is contiguous, so the address arithmetic lands inside m. But strictly, p points into the sub-array m[0] which has only 4 elements, so p + 10 steps outside that array object, which the standard treats as UB even though it stays inside m. Portable code indexes via m[i][j] or uses a genuine 1-D view allocated as one block. Compilers in practice make it work, but sanitizers may flag it.
How does a flexible array member help with variable-length string records?
struct msg { int len; char data[]; };
struct msg *m = malloc(sizeof *m + n + 1);
m->len = n; memcpy(m->data, src, n); m->data[n] = '\0';
One allocation holds header and payload contiguously — better locality, one free, and no separate pointer to keep in sync. The FAM must be the last member and the struct can't be array-of or nested non-last.
What does the restrict keyword let a compiler assume about memcpy(dst, src, n)?
Both parameters are declared restrict, so the compiler assumes src and dst ranges do not overlap. It can then vectorise / load-ahead freely. If they do overlap you must use memmove, which is defined for overlapping regions.

Dynamic Memory Management

Every interviewer's favourite failure modes: leak, dangling, double free, and the null you didn't check.

Notes

The four functions

int *tmp = realloc(p, n * sizeof *p);

else { p = tmp; }

The bug catalogue

  • Leak — losing the last pointer to a block without freeing it. Long-running processes die slowly.
  • Dangling / use-after-free — reading or writing through a pointer after free. Often “works” until the allocator reuses the block, then corrupts unrelated data.
  • Double free — corrupts allocator metadata; a classic exploit primitive. Null the pointer after freeing.
  • Buffer overrun — writing past the end smashes the next block's header (heap) or the return address (stack).
  • Mismatched size — allocating n bytes but treating it as n elements.
  • Unchecked NULL — dereferencing a failed malloc.

Ownership discipline

C has no destructors, so decide for every allocation who frees it and when. Common patterns: the creator frees; the last user frees; a cleanup label with goto for functions with multiple exit points; reference counting for shared objects. Tools: Valgrind, AddressSanitizer (-fsanitize=address), LeakSanitizer, static analysers.

Stack vs heap allocation

Stack: automatic, extremely fast (bump a pointer), freed on scope exit, limited size (often 1–8 MB), size usually fixed. Heap: explicit, slower, large, size decided at run time, must be freed. Use the heap when the object must outlive the function, is large, or has a run-time-determined size.

Cheat Sheet
  • Always check the return of malloc/calloc/realloc.
  • realloc idiom: assign to a temp, test, then reassign.
  • free(NULL) is fine. After any other free(p): p = NULL;.
  • One malloc ↔ one free. Match them like brackets.
  • calloc(n, sz) for zeroed memory and safe size multiplication.
  • Never free stack memory, string literals, or a pointer you did arithmetic on (free the original base).
  • sizeof *p not sizeof(type).
  • Don't cast malloc in C (hides a missing <stdlib.h>); do cast in C++.
  • Free everything before process exit only for tooling cleanliness — the OS reclaims it anyway; but do free inside loops/long-lived services.
  • Debug with valgrind --leak-check=full or -fsanitize=address,undefined.
Q&A
malloc vs calloc?
calloc zero-initialises and checks n*size for overflow; malloc does neither and is marginally faster. Use calloc when you need zeroed memory or are multiplying a count by a size.
What happens if realloc fails?
It returns NULL and leaves the original block untouched and still allocated. If you wrote p = realloc(p, ...) you've just leaked it.
Is free(NULL) safe?
Yes, it is defined to do nothing. That's why you can null-then-free without guarding.
Do you have to free memory before the program exits?
Not for correctness — the OS reclaims the whole address space. But you must free inside long-running loops/services, and freeing at exit keeps leak detectors quiet.
What is a memory leak in a language with no GC?
Allocated heap memory that the program can no longer reach (all pointers to it lost or overwritten) and therefore can never free.
Interview Questions

Basic warm-up

What does malloc return on failure, and what should you do?
NULL. Check for it immediately and handle the error (return, retry with less, or abort). Never dereference the result unconditionally.
What is a dangling pointer?
A pointer that still holds an address whose object has been freed or has gone out of scope. Dereferencing it is undefined behaviour. Mitigation: set pointers to NULL right after free.
How many free calls for a block from malloc?
Exactly one. Zero leaks it; two or more corrupt the heap.
Is the memory from malloc zeroed?
No. It holds indeterminate bytes. Use calloc or memset if you need it zeroed.

Intermediate core

Show the correct way to grow a dynamic array.
size_t cap = ...;
int *tmp = realloc(arr, cap * 2 * sizeof *arr);
if (!tmp) { free(arr); return -1; }   // or keep arr and report
arr = tmp;
cap *= 2;
Doubling gives amortised O(1) appends. Never assign realloc's result straight back to the only pointer you have.
Why is a double free a security problem, not just a bug?
free writes bookkeeping data into the freed chunk and links it into free lists. Freeing it again, especially interleaved with attacker-controlled allocations, lets an attacker corrupt those lists and eventually get malloc to return a pointer into memory they choose — a write-what-where primitive.
How would you find a leak in a large C program?
Run under Valgrind (--leak-check=full --show-leak-kinds=all) or build with -fsanitize=address (bundles LeakSanitizer). Both report the allocation stack of unreachable blocks at exit. For production, hook malloc/free or use jemalloc/tcmalloc heap profiling.
What is the cleanup pattern for a function with several failure points?
Single-exit with goto: allocate progressively, and on any error goto a cleanup label that frees whatever has been allocated so far (freeing NULL is safe, so initialise all pointers to NULL first). This avoids duplicating the free sequence at every return.

Advanced deep

What is heap fragmentation and when does it bite?
Over time, interleaved allocations and frees of varying sizes leave the heap as many small non-contiguous free gaps. A later large request can fail even though the total free bytes suffice (external fragmentation), and each block also wastes some bytes to headers/alignment (internal fragmentation). It hurts long-running processes with mixed allocation sizes. Mitigations: size-class allocators (jemalloc/tcmalloc), pool/arena allocators for same-size objects, allocating up front, or compacting designs that use offsets not pointers.
What alignment guarantee does malloc give, and when isn't it enough?
malloc returns memory aligned for any standard type (alignof(max_align_t), typically 8 or 16 bytes). It is not enough for over-aligned types — SIMD vectors needing 32/64-byte alignment, or cache-line-aligned structures. Use C11 aligned_alloc(alignment, size) or POSIX posix_memalign; free both with free.
Your program calls free(p) then later free(p) again but the code “seems fine” in testing. Why is that dangerous reasoning?
Undefined behaviour isn't required to fail visibly. Whether the second free corrupts anything depends on intervening allocations, allocator implementation, and build flags. It can pass every test and then corrupt the heap in production under different timing. The correct stance: treat any UB as a defect regardless of observed behaviour. Null the pointer after the first free so a second free becomes a harmless no-op.

Program Memory Layout & Stack vs Heap

Where each kind of variable lives, how long it lives, and why the stack is fast but small.

Notes

Segments of a running C program

SegmentHoldsLifetime
.text (code)Machine instructions; often read-only + executable.Whole program.
.rodataString literals, const globals.Whole program; read-only.
.dataInitialised globals / statics with non-zero value.Whole program.
.bssGlobals / statics that are zero or uninitialised. Takes no file space.Whole program; zeroed at start.

StackFunction frames: locals, saved registers, return address, args. Grows downward.Until the function returns.

The stack

Each call pushes a stack frame: space for the function's automatic variables, the return address, and saved registers. Returning pops it — which is why returning a pointer to a local is a bug, and why deep or infinite recursion causes stack overflow. Allocation is a single register adjustment, so it's essentially free; there's no fragmentation. Typical size is 1–8 MB (tunable with ulimit -s or thread attributes).

The heap

A pool the C library manages via brk/sbrk or mmap under the hood. Allocation walks free lists / size classes, so it's slower and can fragment, but blocks live until freed and can be huge. Good for objects whose size or count is known only at run time, or that must outlive their creating function.

Where variables go

int g;                 // .bss  (zero-init global)
int gi = 7;             // .data
const char *msg = "hi";  // msg in .data/.bss; "hi" in .rodata
void f(void) {
    int x;             // stack
    static int s;      // .bss  (persists, but file-local)
    int *h = malloc(40); // h on stack, the 40 bytes on the heap
}

Related concepts

  • ASLR randomises segment base addresses each run for security — don't rely on absolute addresses.
  • Guard page below the stack triggers a fault on overflow instead of silent corruption.
  • Data vs BSS: BSS costs nothing on disk because the loader just zero-fills it.
Cheat Sheet
  • Segments: text / rodata / data / bss / heap ↑ / stack ↓.
  • Zero/uninit globals → .bss (no disk cost). Non-zero init globals → .data.
  • String literals → .rodata (read-only).
  • Locals & call bookkeeping → stack. static locals → .bss/.data.
  • malloc block → heap; the pointer variable itself lives wherever it's declared.
  • Stack alloc = adjust SP, O(1), auto-freed, small (~1–8 MB), no fragmentation.
  • Heap alloc = free-list search, slower, big, manual free, can fragment.
  • Stack overflow → deep/infinite recursion or huge VLAs/local arrays.
  • Never return the address of a local; its frame is gone after return.
Q&A
Why is stack allocation faster than heap allocation?
It's a single adjustment of the stack pointer, with no bookkeeping, no search, and no locking. Heap allocation must find a suitable free block, update metadata, and be thread-safe.
What goes in BSS vs DATA?
BSS: globals/statics that are zero or uninitialised — stored as just a size, zero-filled by the loader. DATA: globals/statics with an explicit non-zero initial value — the bytes are in the executable.
Does the heap grow up or down?
Conventionally the heap grows toward higher addresses and the stack toward lower ones, so they grow “toward each other” in the classic diagram. Real layouts with mmap and ASLR are more scattered.
Where does a static local variable live?
In .data or .bss (static storage), not on the stack — that's why it keeps its value between calls.
What causes a stack overflow?
Exceeding the stack limit: unbounded recursion, very large local arrays or VLAs, or too many nested calls.
Interview Questions

Basic warm-up

Name the memory segments of a C program.
Text (code), read-only data (literals, const), initialised data (.data), uninitialised/zero data (.bss), heap, and stack.
Which segment is a string literal in, and what does that imply?
.rodata (read-only). Writing through a char * that points at a literal is undefined behaviour and typically faults.
What is a stack frame?
The per-call region on the stack holding that invocation's local variables, saved registers, the return address, and (depending on ABI) some arguments. It's created on call and destroyed on return.
Heap memory lifetime — when does it end?
When you explicitly free it (or the process exits). It is not tied to scope.

Intermediate core

Why does a large char buf[8*1024*1024] local often crash but the same via malloc doesn't?
The local is carved out of the thread's stack, which is typically only 1–8 MB, so the frame overflows the stack (often hitting a guard page). malloc draws from the heap, which can be gigabytes and grows via mmap/sbrk.
Two globals: int a[1000000]; and int b[1000000] = {1};. How do they differ in the binary?
a is all-zero, so it goes in .bss and adds essentially nothing to the file — just a recorded size. b has a non-zero initialiser, so all 4 MB of its initial contents are stored in .data inside the executable.
How can two calls to the same recursive function have variables at different addresses?
Each call gets its own frame at a lower stack address than the previous, so the “same” local occupies a different address per depth. That's what makes recursion work — each level has independent storage.
What is ASLR and how does it affect your code?
Address Space Layout Randomisation places the stack, heap, libraries, and (with PIE) the executable at randomised base addresses each run, to make memory-corruption exploits harder. Practical impact: never hard-code or persist absolute addresses; pointer values differ between runs; debugging needs symbolised traces.

Advanced deep

Explain how malloc gets memory from the OS and why free often doesn't shrink RSS.
Small requests are carved from an arena the allocator grows with sbrk (moving the program break) or anonymous mmap; large requests get their own mmap region. free returns the block to the allocator's free lists, not necessarily to the OS — the top-of-heap can only shrink if the freed block is at the break, and mmapped blocks are unmapped only when fully free. So resident memory (RSS) frequently stays high after freeing; that's caching, not a leak. malloc_trim or a different allocator can be more aggressive.
You must allocate millions of same-sized nodes with minimal overhead and fast free. What design?
A pool / slab allocator: malloc one big slab, hand out fixed-size slots by bumping an index, keep a free list of returned slots (an intrusive singly linked list stored in the free slots themselves). O(1) alloc/free, near-zero per-object header overhead, excellent locality, and you can free the whole pool at once. Trade-off: only one object size, and memory isn't returned to the general heap until the pool is destroyed.
Why can taking &local and comparing it across frames give surprising results under optimisation?
The compiler may keep a local entirely in a register (no address at all until forced), reorder or coalesce frame slots, elide frames via inlining or tail-call optimisation, or reuse the same stack slot for non-overlapping locals. So “stack grows down” reasoning about specific offsets is unreliable; only lifetime and scope rules are guaranteed.

Structures, Unions, Bit-fields, Padding & Alignment

Why sizeof(struct) isn't the sum of its members, and how to control it.

Notes

Alignment & padding

Each scalar type has an alignment requirement (usually its own size): an int must sit at an address divisible by 4, a double by 8. The compiler inserts padding bytes between members so each is aligned, and tail padding at the end so that in an array every element stays aligned. The whole struct's alignment is that of its strictest member.

struct bad { char a; int b; char c; };  // 1 +3pad +4 +1 +3pad = 12
struct good { int b; char a; char c; };  // 4 +1 +1 +2pad = 8

Order members large→small to minimise padding. offsetof(type, member) from <stddef.h> gives the real offset. C11 _Alignas / alignof let you query or force alignment.

Unions

All members share the same storage; sizeof is the largest member (plus alignment). Writing one member and reading another is type punning — in C this is defined for inspecting bytes and for a common initial sequence of struct members, but reading a different type generally has implementation-defined/UB corners (the popular float↔int trick works on GCC/Clang; memcpy is the fully portable route). A tagged union (an enum tag + a union) is the safe idiom.

struct value {
    enum { V_INT, V_STR } tag;
    union { long i; char *s; } as;
};

Bit-fields

Members declared with a bit width pack flags/small counters tightly: unsigned mode : 3;. Useful for protocol headers and hardware registers, but allocation order, straddling of storage units, and signedness of plain int bit-fields are implementation-defined — not portable across compilers/endianness. You cannot take a bit-field's address.

Flexible array member (C99)

A trailing T arr[]; with no size lets one allocation hold a header plus a run-time-sized payload contiguously. Must be the last member; the struct must have at least one other member.

Copying & comparing

Struct assignment and passing by value copy all members (including padding, whose contents are unspecified). That's why you cannot compare structs with memcmp reliably — padding bytes may differ. Compare field by field, or memset the whole struct to 0 before filling it if you must byte-compare.

Cheat Sheet
  • sizeof(struct) ≥ sum of members, rounded so arrays stay aligned.
  • Struct alignment = max alignment of any member.
  • Reorder members big→small to cut padding.
  • offsetof(T, m) for real offsets; alignof(T) / _Alignas (C11).
  • union size = largest member; only one member valid at a time — track with a tag.
  • Portable type-pun = memcpy, not union reads.
  • Bit-field layout is implementation-defined — don't rely on it for wire formats across toolchains.
  • Can't & a bit-field.
  • Don't memcmp structs — padding bytes are unspecified. Compare fields.
  • #pragma pack(1) / __attribute__((packed)) removes padding — at the cost of unaligned access (slow / faulting on some CPUs).
Q&A
Why is struct {char a; int b;} 8 bytes, not 5?
3 padding bytes after a so b lands on a 4-byte boundary. Total is also rounded up to the struct's alignment (4) — here already satisfied.
Difference between a struct and a union?
Struct members have distinct storage laid out sequentially; union members overlap in the same storage. A struct's size is the sum (plus padding); a union's is the max.
How do you portably reinterpret a float's bits as uint32_t?
uint32_t u; memcpy(&u, &f, sizeof u);. The union trick is common but not strictly portable in C++ and has ISO-C caveats.
Can you compare two structs with ==?
No, there's no == for structs in C. And memcmp is unreliable because of padding. Compare member by member.
What is a flexible array member good for?
Allocating a variable-length record (header + payload) in a single malloc, improving locality and simplifying free.
Interview Questions

Basic warm-up

What is structure padding and why does the compiler add it?
Unused bytes inserted between (and after) members so each member meets its alignment requirement and so array elements stay aligned. It trades a little space for correct, fast aligned access.
What is sizeof a union with an int and a double member?
At least sizeof(double) (8), possibly rounded to the union's alignment — the members share storage, so it's sized for the largest.
Can you store a value in one union member and read it from another?
Mechanically yes, but semantically it's type punning: only reading as bytes / unsigned char, or via a common initial sequence, is clearly defined. For a real reinterpret, use memcpy. Track which member is active with a tag.
How do you get the byte offset of a struct member?
offsetof(struct T, member) from <stddef.h>.

Intermediate core

Reorder struct { char a; double b; char c; int d; } to minimise size. Show both sizes.
Original: char a(1)+7 pad+double b(8)+char c(1)+3 pad+int d(4)+4 tail pad = 24. Reordered { double b; int d; char a; char c; }: 8+4+1+1+2 tail pad = 16.
What does __attribute__((packed)) / #pragma pack(1) do and what's the danger?
It removes all padding so the layout matches a wire/hardware format exactly. Danger: members may now be misaligned, so accessing them can be slow (extra loads on x86) or fault (SIGBUS on ARM/SPARC and in some strict modes). Access packed fields through helpers/memcpy, not by taking pointers to them.
Why is memcmp(&s1, &s2, sizeof s1) a fragile equality test?
The padding bytes between members hold unspecified values — two structs with equal members can have different padding (e.g. from stack garbage before assignment), so memcmp reports them unequal. It only works if every such struct was memset to a known value first and only assigned whole.
Design a type that can hold either an integer or a string, safely.
A tagged union: struct { enum {INT, STR} tag; union { long i; char *s; } u; };. Every read switches on tag; every write sets tag and the matching member. This makes the “which member is live” question explicit and checkable.

Advanced deep

What is the “common initial sequence” rule for unions?
If a union contains several structs that share a common initial run of members with compatible types, and the union object's completed type is visible, you may inspect that shared prefix through any of those struct members regardless of which was last written. It's what lets you read a discriminant/tag placed as the first field of every variant. Beyond that shared prefix, behaviour is not guaranteed.
Bit-fields in a network packet struct broke when compiled on a different platform. Why, and what's the fix?
The C standard leaves it implementation-defined whether bit-fields are allocated low-to-high or high-to-low within a unit, whether they can straddle storage units, the addressable unit size, and whether plain int bit-fields are signed. Change compiler or endianness and the bits land elsewhere. Fix: don't use bit-fields for wire formats — read/write whole bytes and do explicit shift-and-mask, or use fixed serialization code.
How does the strict aliasing rule interact with reading memory as two different struct types?
The compiler assumes pointers to unrelated types don't refer to the same storage, so it may cache/reorder loads and stores across them. Casting a struct A * to a struct B * and dereferencing (when the object's real type is A) is UB and can be miscompiled. The sanctioned escapes: access through char */unsigned char *, use a union containing both types, or memcpy into a fresh object of the target type. -fno-strict-aliasing disables the optimisation as a blunt fix.

Function Pointers & Callbacks

How C does polymorphism, plugins, and qsort.

Notes

Declaration & use

int (*fp)(int, int);        // fp: pointer to fn taking (int,int) returning int
int add(int a, int b){ return a+b; }
fp = add;    // or &add -- function name decays to a pointer
fp(2,3);      // or (*fp)(2,3) -- both call it

The parentheses around *fp matter: int *f(int,int) is a function returning int*, whereas int (*f)(int,int) is a pointer to function. Use a typedef to stay sane: typedef int (*BinOp)(int,int);.

Callbacks

Pass behaviour into a generic routine. qsort is the canonical example:

int cmp(const void *a, const void *b) {
    int x = *(const int *)a, y = *(const int *)b;
    return (x > y) - (x < y);   // avoids overflow of x - y
}
qsort(arr, n, sizeof arr[0], cmp);

A well-designed callback API also takes a void *user context pointer so the callback can reach caller state without globals (qsort_r/qsort_s add this; plain qsort lacks it).

Dispatch tables

An array (or struct) of function pointers replaces a big switch and enables run-time extensibility: opcode interpreters, state machines, driver struct file_operations-style vtables, plugin registration.

typedef void (*Handler)(Event *);
static Handler table[EVENT_MAX] = { [EV_OPEN]=on_open, [EV_TICK]=on_tick };
if (e->type < EVENT_MAX && table[e->type]) table[e->type](e);

Rules & pitfalls

  • Calling through a pointer whose type doesn't match the actual function is UB.
  • A void * is not guaranteed to hold a function pointer — use a function-pointer type (POSIX dlsym works in practice via a documented cast).
  • Comparisons: two function pointers are equal iff they name the same function.
  • No arithmetic on function pointers.
Cheat Sheet
  • ret (*name)(params) — parens around *name are mandatory.
  • typedef ret (*Name)(params); then use Name everywhere.
  • Function name decays to &function; call as fp(...) or (*fp)(...).
  • Comparator returns sign, not difference: (x>y)-(x<y).
  • Good callback API = function pointer plus void *ctx.
  • Dispatch table = Handler t[N]; guard index and null before calling.
  • No pointer arithmetic; equality = same function.
  • Signature mismatch on call = UB (even if it “works”).
Q&A
Why int (*f)(void) and not int *f(void)?
Without the parentheses, * binds to the return type: int *f(void) is a function returning int*. The parentheses make f a pointer to a function.
Do you need & to take a function's address?
No — a function name decays to its address automatically. fp = f; and fp = &f; are equivalent, as are fp() and (*fp)().
How does qsort stay type-generic?
It works in terms of byte counts (size, nmemb) and delegates ordering to a caller-supplied comparator taking const void * arguments.
Why pass a void *user to a callback?
So the callback can access caller-specific state (config, accumulators, an object this) without resorting to global variables, keeping it reentrant.
Can you put function pointers in a struct?
Yes — that's how C builds vtable-like interfaces (e.g. the Linux kernel's file_operations).
Interview Questions

Basic warm-up

Declare a pointer to a function taking two doubles and returning double.
double (*fp)(double, double); — or with a typedef: typedef double (*DFn)(double,double); DFn fp;.
What is a callback?
A function passed (as a pointer) into another function so the callee can invoke caller-supplied behaviour at the right moment — e.g. a comparator for sorting, an event handler, an iteration visitor.
Two ways to call through fp?
fp(args) and (*fp)(args) — identical in effect.
What must a qsort comparator return?
A negative value if the first element sorts before the second, zero if equal, positive if after. Not necessarily -1/0/1.

Intermediate core

Why is return a - b; a buggy comparator for int?
a - b can overflow (e.g. INT_MIN vs a large positive), which is undefined behaviour and can invert the ordering. Use (a > b) - (a < b) or explicit ifs.
Implement a tiny event dispatcher using a table of handlers.
typedef void (*Handler)(void *ev, void *ctx);
Handler table[N];
void dispatch(int type, void *ev, void *ctx) {
    if ((unsigned)type < N && table[type])
        table[type](ev, ctx);
}
Registration is just table[type] = fn;. This replaces a growing switch and lets modules self-register.
How do you emulate a virtual method / interface in C?
Put function pointers in a struct (“ops” / vtable). Each “object” carries a pointer to its ops table plus its own data: struct shape { const struct shape_ops *ops; ... }; s->ops->area(s);. Different concrete types supply different ops tables.
What breaks if you cast a void(*)(int) to void(*)(void) and call it?
Calling a function through a pointer of incompatible type is undefined behaviour. It may happen to work with a compatible calling convention on one ABI and crash or pass garbage on another. Keep the pointer type matching the function.

Advanced deep

POSIX dlsym returns void * but you need a function pointer. Is the cast legal?
ISO C says object and function pointers need not be interconvertible, so strictly it's implementation-defined. POSIX explicitly requires the conversion to work and documents the idiom; the portable-looking workaround is *(void **)&fn = dlsym(...) to dodge a compiler warning, but on any real POSIX platform a direct cast is fine and defined by POSIX itself.
How does a function-pointer dispatch table compare to a switch for a bytecode interpreter, performance-wise?
A dense switch often compiles to a jump table already, so raw dispatch cost is similar. The interpreter-specific win is computed goto / “threaded code” (a GCC label-pointer table), where each opcode handler ends by jumping directly to the next opcode's handler. That spreads the indirect branch across many sites, improving branch-predictor accuracy versus one hot switch dispatch point. A struct-of-pointers table is also more extensible at run time; a switch is faster to write and lets the optimiser see all cases.
Can you store a pointer to a function with C linkage in a variable typed for C++ linkage (or vice versa)?
Language linkage is part of a function type in C++. A pointer to an extern "C" function has a different type from a pointer to an ordinary C++ function, and mixing them is technically ill-formed (many compilers allow it). When registering C++ callbacks with a C API, declare the callback extern "C" so its type matches what the C library expects.

The Preprocessor & Macros

A text-substitution pass that runs before the compiler — powerful, and full of foot-guns.

Notes

What it does

The preprocessor handles #include (paste a file), #define (object- and function-like macros), conditional compilation (#if / #ifdef / #ifndef / #elif / #else / #endif), #pragma, #error, and line control. It works purely on tokens — it knows nothing about types, scopes, or C syntax.

Macro pitfalls

// 1. missing parentheses
#define SQ(x) x*x
SQ(a+b)        // -> a+b*b   ... wrong
#define SQ(x) ((x)*(x))   // fix: parens around params AND whole body

// 2. double evaluation of arguments with side effects
#define MAX(a,b) ((a)>(b)?(a):(b))
MAX(i++, j)    // i incremented once or twice depending on branch

// 3. dangling-else / multi-statement macros
#define DBG(x) printf("%d\n",x); log(x)   // breaks after an if without braces
#define DBG(x) do { printf("%d\n",x); log(x); } while (0)  // fix

# stringize and ## token paste

#define STR(x)  #x            // STR(foo)  -> "foo"
#define XSTR(x) STR(x)         // expands x first: XSTR(__LINE__) -> "42"
#define CAT(a,b) a##b          // CAT(var,3) -> var3

You need the extra indirection layer (XSTR) because # and ## suppress expansion of their operands.

Include guards vs #pragma once

#ifndef MYLIB_FOO_H
#define MYLIB_FOO_H
/* declarations */
#endif

Standard, portable, and works even if the same file is reachable by two paths. #pragma once is shorter and widely supported but not in the standard.

Useful predefined macros

__FILE__, __LINE__, __func__ (actually a variable, C99), __DATE__, __STDC_VERSION__, and compiler-specific ones like __GNUC__. assert is a macro that expands to nothing when NDEBUG is defined.

X-macros

A single list macro drives multiple generated tables (enum + names + handlers) so they can't drift out of sync:

#define COLORS  X(RED) X(GREEN) X(BLUE)
enum Color { #define X(c) c, COLORS #undef X };
const char *name[] = { #define X(c) #c, COLORS #undef X };
Cheat Sheet
  • Wrap every macro parameter and the whole body in parentheses.
  • Multi-statement macro → do { ... } while (0).
  • Never pass side-effecting expressions to a macro that may use the arg twice.
  • Prefer static inline functions, const, and enum over macros where possible — they have types and scope.
  • #x stringizes; a##b pastes; both need a helper layer to expand args first.
  • Header guard: #ifndef UNIQUE / #define UNIQUE / ... / #endif.
  • #if defined(X) && X > 2 for version checks; undefined names in #if count as 0.
  • assert() vanishes under -DNDEBUG — never put required side effects inside it.
  • -E (gcc/clang) dumps preprocessed output for debugging expansions.
Q&A
Why parenthesise macro bodies and parameters?
Because expansion is textual: without parentheses the surrounding operators bind differently than intended (SQ(a+b) → a+b*b).
Why do { } while(0) around a multi-statement macro?
It makes the macro a single statement that still needs a terminating semicolon and behaves correctly after an if without braces.
Difference between #include <x> and #include "x"?
" " searches the current file's directory (and user paths) first, then the system paths; < > searches only the system/include paths. Use quotes for your project headers.
What does # do in a function-like macro?
Stringizes the argument — turns the token(s) into a string literal, with special handling of embedded quotes/backslashes.
Macro vs inline function — which to prefer?
inline (or static inline): it's type-checked, scoped, debuggable, and evaluates arguments once. Reach for a macro only when you need textual tricks (stringize, paste, generic-over-type without _Generic, compile-time constants).
Interview Questions

Basic warm-up

What phase does the preprocessor run in, and does it understand C types?
It runs before compilation proper, operating on the token stream. It has no knowledge of types, scope, or expressions — it only does inclusion, macro substitution, and conditional compilation.
Write a safe MIN(a,b) macro.
#define MIN(a,b) ((a) < (b) ? (a) : (b)) — parens around each parameter and the whole expression. (Still evaluates one argument twice; document that or use a GCC statement-expression / an inline function.)
What's a header include guard?
An #ifndef NAME / #define NAME / ... / #endif wrapper that prevents the header's contents being processed more than once per translation unit.
What does #undef do?
Removes a current macro definition, so the name reverts to being an ordinary identifier (or can be redefined differently).

Intermediate core

Why does STR(__LINE__) give "__LINE__" and how do you fix it?
The # operator stringizes its argument without expanding it first. Add an indirection: #define STR(x) #x and #define XSTR(x) STR(x), then XSTR(__LINE__) expands __LINE__ to the number, which STR then stringizes.
Give a concrete bug from passing arr[i++] to MAX(a,b).
MAX(arr[i++], x) expands to ((arr[i++]) > (x) ? (arr[i++]) : (x)). If the first branch is taken, i is incremented twice and a different element is returned than the one compared — and the double modification of i without a sequence point is itself UB.
What is an X-macro and what problem does it solve?
A macro that lists items once (#define LIST X(a) X(b) X(c)); you then #define X differently and re-expand LIST to generate several parallel constructs (an enum, a name array, a jump table). It keeps those tables in sync because they're all generated from one source list.
How do you conditionally compile code only on GCC ≥ 7?
#if defined(__GNUC__) && (__GNUC__ > 7 || (__GNUC__ == 7 && __GNUC_MINOR__ >= 0)). Undefined identifiers evaluate to 0 in #if, so the defined() guard prevents a false match on other compilers.

Advanced deep

Explain the preprocessor's argument prescan and when it does not happen.
When a function-like macro is invoked, each argument is fully macro-expanded (“prescanned”) before being substituted into the body — unless that parameter is an operand of # or ## in the body, in which case it's used raw. That's the whole reason two-level STR/XSTR and CAT/XCAT wrappers exist: the outer macro expands the argument, the inner one applies #/##.
How can you build a variadic macro that forwards __VA_ARGS__ and handles the zero-argument case?
#define LOG(fmt, ...) fprintf(stderr, fmt, __VA_ARGS__) breaks when called with just a format. C99 workaround: GCC's , ##__VA_ARGS__ deletes the comma when empty; C++20 / C23 provide __VA_OPT__(,) for a portable version: #define LOG(fmt, ...) fprintf(stderr, fmt __VA_OPT__(,) __VA_ARGS__).
Why can't the preprocessor implement true recursion, and how do libraries fake counting/iteration?
A macro is “painted blue” (marked non-replaceable) while its own expansion is being rescanned, so it cannot call itself. Metaprogramming libraries (Boost.Preprocessor) simulate recursion by pre-defining a finite ladder of differently-named macros (REPEAT_1, REPEAT_2, ... up to a fixed limit) and deferring expansion with EMPTY()/DEFER tricks so an outer rescan pass performs the next step.

const, volatile, static, extern & Linkage

How names, definitions, and translation units fit together — and how headers should be written.

Notes

Translation units and the one-definition idea

Each .c file plus everything it #includes is a translation unit, compiled to an object file; the linker joins them. A symbol with external linkage may be declared many times but must be defined exactly once across the whole program.

Linkage

LinkageMeaningHow to get it
ExternalOne entity shared across all translation units.File-scope function/variable with no static.

NoneA fresh entity each time the declaration is seen.Locals, function parameters, typedef, most block-scope names.

extern and the header pattern

// config.h
extern int g_verbosity;          // declaration -- promise it exists
void set_verbosity(int);

// config.c
#include "config.h"
int g_verbosity = 0;             // the single definition

Put declarations (not definitions) in headers. A bare int g; in a header included by several .c files gives multiple definitions — a link error under modern -fno-common defaults.

const and linkage

In C, a file-scope const still has external linkage by default (unlike C++, where it's internal). So const int K = 10; in a header included twice is a redefinition; use static const or (better) put the definition in one .c and extern const in the header, or use an enum/#define for true compile-time constants.

inline in C (differs from C++)

C99 inline without static or extern provides an inline definition that does not emit an external symbol; you must supply one extern inline (or normal) definition in exactly one .c for the address/non-inlined calls. The simple, portable choice for header helpers is static inline.

Tentative definitions

int x; at file scope is a tentative definition. Multiple tentative definitions of the same variable in one translation unit collapse into one, initialised to zero. Across translation units they're still multiple definitions.

Cheat Sheet
  • Translation unit = one .c + its includes → one .o.
  • Declare in headers, define in exactly one .c.
  • static @ file scope → internal linkage (file-private).
  • extern → “defined elsewhere”; needed to share a global via a header.
  • C const at file scope has external linkage (unlike C++).
  • Header constants: enum, #define, or static const / extern const + one definition.
  • Header helpers: static inline (simplest correct choice).
  • -fno-common (modern default) turns duplicate globals into link errors — good.
  • Function default linkage is external; add static for internal helpers.
Q&A
Declaration vs definition?
A declaration introduces a name and its type; a definition also allocates storage (variables) or provides the body (functions). You can declare many times, define once.
What does static do to a global?
Gives it internal linkage — other translation units cannot see or link to it, avoiding name clashes.
How do two .c files share one global correctly?
Define it once (int g = 0;) in one .c; declare it (extern int g;) in a header both include.
Why did const int MAX = 100; in a shared header cause a link error in C but not C++?
C keeps file-scope const at external linkage, so each including .c defines the same symbol. C++ makes it internal by default, so each unit gets its own private copy.
Safest way to put a small helper in a header?
static inline — each including file gets its own inlinable copy with no duplicate-symbol risk.
Interview Questions

Basic warm-up

What is a translation unit?
A single source file after preprocessing — the .c file with all its #includes pasted in and macros expanded. It's the unit the compiler turns into one object file.
Where should function declarations live, and where their definitions?
Declarations (prototypes) go in a header shared by callers and the implementer. The definition (body) goes in exactly one .c file.
What linkage does a local variable have?
None — each entry into its scope creates a distinct object; the name isn't visible to the linker at all.
How do you make a helper function invisible to other files?
Mark it static at file scope — internal linkage.

Intermediate core

You get “multiple definition of `g`” at link time. Likely cause and fix?
A real definition (int g; or int g = ...;) sits in a header that's included by more than one .c, so every unit defines g. Fix: header gets extern int g; only; put int g = 0; in exactly one .c. (Historically the “common” model hid this; modern compilers default to -fno-common.)
What's a tentative definition?
A file-scope declaration like int x; with no initialiser and no extern. If no other definition of x with an initialiser appears in the translation unit, the compiler emits one zero-initialised definition. Several tentative definitions of the same name in one unit are fine and merge.
Explain C99 inline and why static inline is usually recommended.
A plain inline function definition in a header is an “inline definition” that emits no standalone symbol; you must place exactly one extern (or ordinary) definition in some .c to satisfy address-of and non-inlined calls — easy to forget and get a link error. static inline sidesteps that: every translation unit gets its own internal copy, inlinable, no external symbol, no coordination needed.
Does const on a global let the compiler put it in read-only memory?
Yes, a const object with static storage duration and no volatile can be placed in .rodata. Attempting to cast away const and write it is undefined behaviour and typically faults.

Advanced deep

How does -fno-common change behaviour, and why is it now the default?
With the old “common” model, an uninitialised file-scope variable became a common symbol; the linker merged same-named commons from different objects into one, silently. That hid bugs (accidental global name collisions) and interacted badly with link-time optimisation and shared libraries. -fno-common makes each such variable a normal definition, so duplicates become multiple-definition errors, forcing the correct extern-in-header pattern. GCC 10 / modern Clang made it the default.
What is the difference between visibility (__attribute__((visibility("hidden"))) and linkage?
Linkage is a C-language concept about name sharing between translation units at static link time. Symbol visibility is an ELF/shared-library concept controlling whether an external-linkage symbol is exported from a .so for dynamic linking. A function can have external linkage (visible to other .os in the same library) yet hidden visibility (not part of the library's public ABI), which shrinks the dynamic symbol table and speeds load time.
Two libraries both define a static function helper(). Any conflict?
No. static gives internal linkage, so each helper is private to its own translation unit; the linker never compares them. The symbols may not even appear in the global symbol table. This is exactly why library-internal helpers should be static.

Bit Manipulation Tricks

Masks, shifts, and the handful of idioms that come up in almost every low-level interview.

Notes

The four fundamental operations

x |  (1u << n)     // set bit n
x & ~(1u << n)     // clear bit n
x ^  (1u << n)     // toggle bit n
(x >> n) & 1u       // test bit n  (0 or 1)

Use unsigned types and 1u/1UL so the shift can't hit signed overflow or shift into the sign bit (both UB). Shifting by ≥ the type width is also UB.

In practice, prefer compiler intrinsics: __builtin_popcount, __builtin_clz (count leading zeros), __builtin_ctz (trailing), or C23 <stdbit.h>. They map to single instructions.

Masks & fields

// extract bits [hi:lo] of x
(x >> lo) & ((1u << (hi - lo + 1)) - 1)
// insert value v into field [hi:lo]
x = (x & ~(mask << lo)) | ((v & mask) << lo);

Shift gotchas

  • Right shift of a negative signed value is implementation-defined (usually arithmetic / sign-extending).
  • 1 << 31 on 32-bit int is UB (overflows INT_MAX); use 1u << 31.
  • Shift count must be 0 ≤ n < width. x << 32 for 32-bit x is UB, not 0.
  • Operands narrower than int are promoted first, so (uint8_t)0xFF << 8 is computed in int.
Cheat Sheet
  • set x|=1u<<n · clear x&=~(1u<<n) · toggle x^=1u<<n · test (x>>n)&1u
  • power of two: x && !(x & (x-1))
  • x & (x-1) drops lowest set bit; x & -x isolates it.
  • popcount / clz / ctz → use __builtin_* or C23 <stdbit.h>.
  • Always shift unsigned; suffix the literal (1u, 1ull).
  • Shift by ≥ width or into/of the sign bit → UB.
  • XOR swap is a party trick — fails when the two operands alias; just use a temp.
  • Field insert: x = (x & ~(m<<lo)) | ((v & m) << lo);
  • a ^ b ^ b == a — basis of XOR checksums, the “single number” trick, and XOR linked lists.
Q&A
How to check if an integer is a power of two?
x > 0 && (x & (x - 1)) == 0. A power of two has exactly one set bit; subtracting 1 flips that bit and sets all lower ones, so the AND is zero.
What does x & -x give?
The lowest set bit of x as a value (two's complement negation flips all bits above the lowest set bit and leaves it). Useful in Fenwick trees.
Why use 1u instead of 1 when shifting?
1 is a signed int; shifting into the sign bit or past it is undefined. 1u (or wider) makes the operation well-defined modulo the width.
Fastest way to count set bits?
A hardware POPCNT via __builtin_popcount / std::popcount / C23 stdc_count_ones. Kernighan's loop is the portable fallback; table lookup is another.
Is right-shifting a negative number safe?
It's implementation-defined (nearly always arithmetic shift, preserving sign). For portable, predictable behaviour, shift unsigned values.
Interview Questions

Basic warm-up

How do you set, clear, and toggle bit n of x?
Set: x |= 1u << n;. Clear: x &= ~(1u << n);. Toggle: x ^= 1u << n;.
How do you test whether bit n is set?
(x >> n) & 1u (yields 0 or 1), or (x & (1u << n)) != 0.
What is x << 3 equivalent to arithmetically?
Multiplying by 8 (2^3), for unsigned or non-overflowing values. x >> 3 is integer division by 8 for non-negative values.
Swap two integers without a temporary.
a ^= b; b ^= a; a ^= b; — but only if a and b are different objects. If they alias, this zeroes the value. A temp variable is clearer and just as fast.

Intermediate core

Given an array where every value appears twice except one, find the single value in O(n)/O(1).
XOR all elements together. Pairs cancel (v ^ v == 0), leaving the unique value. long r = 0; for (i) r ^= a[i]; return r;.
Round x up to the next power of two (32-bit).
x--; x|=x>>1; x|=x>>2; x|=x>>4;
x|=x>>8; x|=x>>16; x++;
This smears the highest set bit down through all lower positions, then +1 carries to the next power of two. Handle x == 0 and overflow separately.
Extract bits [12:4] of a 32-bit register value r.
Width is 12 - 4 + 1 = 9 bits: (r >> 4) & ((1u << 9) - 1), i.e. (r >> 4) & 0x1FF.
Why is uint16_t a = 0xFFFF; uint32_t b = a << 16; a trap on some code, and safe here?
a is promoted to int before the shift. If int is 32-bit, 0xFFFF << 16 sets bit 31 of a signed int — that's signed overflow / UB. It's only safe if you cast first: (uint32_t)a << 16. So the given line is actually the trap; the fix is the cast.

Advanced deep

Implement branchless abs(int x) and explain why it works.
int mask = x >> (sizeof(int)*8 - 1); return (x ^ mask) - mask;. For x ≥ 0, mask is 0: result is x. For x < 0, arithmetic right shift makes mask all-ones (-1): x ^ -1 is ~x, then - (-1) adds 1, giving ~x + 1 == -x. Caveat: relies on arithmetic right shift (implementation-defined) and still overflows for INT_MIN.
How would you reverse the bits of a 32-bit word efficiently?
Divide-and-conquer swaps: exchange adjacent 1-bit groups, then 2-bit, 4-bit, 8-bit, 16-bit, each with a mask and shifts — 5 steps, O(1): 
x = ((x&0x55555555)<<1)|((x>>1)&0x55555555);
x = ((x&0x33333333)<<2)|((x>>2)&0x33333333);
x = ((x&0x0F0F0F0F)<<4)|((x>>4)&0x0F0F0F0F);
x = (x<<24)|((x&0xFF00)<<8)|((x>>8)&0xFF00)|(x>>24);
Or use a byte lookup table, or __builtin/ARM RBIT.
What's the trick behind a Fenwick (binary indexed) tree's i & -i?
i & -i isolates the least-significant set bit, which equals the size of the range that node i is responsible for. To move to the parent in an update you add it (i += i & -i); to move to the previous responsible node in a prefix query you subtract it (i -= i & -i). This gives O(log n) update and query with O(n) space and almost no constant factor.

Undefined Behaviour & Classic Pitfalls

The interviewer isn't testing trivia — they want to know you won't ship a time bomb.

Notes

The three flavours

  • Undefined behaviour (UB) — the standard imposes no requirements. The compiler may do anything: crash, corrupt data, or (worse) optimise your code away assuming UB can't happen.
  • Unspecified behaviour — several outcomes are allowed, no choice documented (e.g. order of evaluation of function arguments).
  • Implementation-defined — allowed to vary, but the implementation must document its choice (e.g. sizeof(int), right shift of negatives, char signedness).

The greatest hits

Signed integer overflowINT_MAX + 1; also -INT_MIN, INT_MIN / -1

Use after free / danglingreading a freed block or a returned local's address

Strict aliasing violationreading an int object through a float *

Bad printf format/arg mismatchprintf("%d", 3.0), %s with an int
Calling a function through a wrong-type pointersee Function Pointers topic

Why “it works on my machine” is not a defence

Modern optimisers actively assume the absence of UB. If p is dereferenced, later code may drop a if (p == NULL) check as “dead”. Signed-overflow assumptions turn x + 1 > x into true. So UB can delete security checks or loops entirely, and the symptom can appear far from the cause and only at -O2.

Sequence points / sequencing (C11 model)

Between two sequence points (the ;, &&, ||, ?:, comma operator, end of a full expression), an object may be modified at most once, and a value read only to compute the new value. i = i++ violates this; i = i + 1 is fine.

Defences

  • Compile with -Wall -Wextra -Wpedantic, treat warnings as errors.
  • Run tests under -fsanitize=address,undefined (ASan + UBSan) and Valgrind.
  • Use -fno-strict-aliasing only as a stopgap; fix the aliasing.
  • Static analysis (clang-tidy, Coverity, cppcheck).
Cheat Sheet
  • UB = anything allowed, retroactively. Unspecified = pick from a set. Impl-defined = documented choice.
  • Signed overflow is UB; unsigned overflow wraps (well-defined mod 2^N).
  • No modifying an object twice between sequence points (i = i++;).
  • Argument evaluation order is unspecified — don't rely on it.
  • OOB, use-after-free, null deref, uninitialised read = classic UB.
  • Type-pun via memcpy or union, never a raw incompatible pointer cast.
  • UB can make the optimiser delete checks — bugs appear only at -O2, far from the cause.
  • Tooling: -Wall -Wextra, ASan, UBSan, Valgrind, static analysers.
Q&A
Signed vs unsigned overflow?
Unsigned arithmetic wraps modulo 2^N — fully defined. Signed overflow is undefined behaviour; the compiler may assume it never happens.
Is a[i] = i++; defined?
No. The read of i to index and the modification of i are unsequenced — UB. Split it into two statements.
What's wrong with printf(user_string)?
If the string contains % specifiers, printf reads non-existent arguments — a crash or an info-leak / write (%n) vulnerability. Use printf("%s", user_string).
Does UB only affect the offending statement?
No. The standard puts no bound on the effects; optimisers propagate the “can't happen” assumption backward and forward, so earlier or later code can be transformed or removed.
How do you catch UB you can't see?
Run the test suite under UBSan/ASan, use Valgrind, enable all warnings, and add static analysis in CI.
Interview Questions

Basic warm-up

Define “undefined behaviour”.
A construct for which the C standard imposes no requirements at all. A conforming compiler may produce any result, including one that looks correct, and is entitled to optimise on the assumption that it never occurs.
Give three everyday examples of UB.
Reading an uninitialised local, indexing an array out of bounds, dereferencing a pointer after free, signed integer overflow, dividing by zero, dereferencing NULL — any three.
Is unsigned integer overflow undefined?
No. Unsigned arithmetic is defined to wrap modulo 2^N. Only signed overflow is UB.
What flag turns on the runtime UB checker in GCC/Clang?
-fsanitize=undefined (UBSan), usually paired with -fsanitize=address.

Intermediate core

Why might the compiler remove if (ptr == NULL) return; that appears after *ptr = 0;?
Dereferencing ptr is UB if it's null, so the compiler is allowed to assume ptr is non-null from that point on. The later null check is therefore “provably false” and gets deleted as dead code. The fix is to check before dereferencing.
Explain the strict aliasing rule with an example that breaks.
float f = 1.0f;
unsigned bits = *(unsigned *)&f;   // UB: reading a float object as unsigned
The compiler assumes an unsigned * and a float * never alias, so it may reorder or cache across the access and produce a wrong bits. Use memcpy(&bits, &f, sizeof bits).
What is unspecified (not undefined) about f(g(), h())?
The order in which g() and h() are called is unspecified — the compiler picks, and may differ between calls/builds. It's not UB (nothing catastrophic), but code that depends on the order is non-portable and fragile.
Is INT_MIN % -1 safe?
No — like INT_MIN / -1, the mathematical result (or the division it implies) overflows int, which is UB. Guard division/modulo when the divisor could be -1 and the dividend could be the minimum value.

Advanced deep

How can signed-overflow UB cause a loop to become infinite under optimisation?
for (int i = 0; i <= n; i++) where n == INT_MAX: the compiler may assume i + 1 never overflows (signed), conclude i <= n is always true, and turn the exit test into a constant “true”. It's entitled to because reaching the overflow would be UB. Using an unsigned or size_t counter (defined wraparound) or a < bound avoids it.
What does the “as-if” rule permit, and how does UB interact with it?
The compiler may transform the program however it likes as long as the observable behaviour (I/O, volatile accesses, program termination) of a conforming program is preserved. If the program has UB it is not a conforming program for that input, so the as-if constraint is void — the compiler owes you nothing, which is why UB-based optimisations are legal even when they change what you expected.
You must reinterpret a buffer of bytes as a struct received off the wire. How do you do it without aliasing UB?
Don't cast the buffer pointer to struct T * and dereference. Instead memcpy the bytes into a real struct T object (the compiler treats memcpy as changing the effective type), and account for endianness and padding explicitly — ideally parse field by field from the byte array rather than relying on struct layout at all. Access as unsigned char * is also always allowed.

File I/O & Standard Library Essentials

FILE* vs file descriptors, buffering, and the str* / mem* functions you'll be asked to reimplement.

stdio wraps a descriptor with a user-space buffer to cut syscall count. Get the underlying fd with fileno(fp); wrap an fd with fdopen.

Buffering modes

  • Fully buffered — flushed when the buffer fills. Default for files and non-tty pipes.
  • Line buffered — flushed on '\n'. Default for stdout when it's a terminal.
  • Unbuffered — each write goes straight out. Default for stderr.

This is why interleaved printf/fprintf(stderr,...) can print out of order, and why a crash can “lose” the last printf — the buffer wasn't flushed. Force it with fflush(stdout), setvbuf, or a trailing '\n' on a tty. Streams are flushed on normal exit() / return from main, but not on _exit, abort, or a signal.

Reading lines safely

char buf[256];
while (fgets(buf, sizeof buf, fp)) {
    buf[strcspn(buf, "\n")] = '\0';   // strip newline if present
    ...
}
// POSIX getline() handles arbitrary length via realloc

Return values & errors

  • fopen returns NULL on failure and sets errno; print with perror / strerror.
  • fread/fwrite return the count of elements transferred; a short count means EOF or error — disambiguate with feof/ferror.
  • fgetc/getchar return int (so EOF, which is negative, is distinguishable from any unsigned char). Storing the result in a char is a classic bug.

  • stdout: line-buffered on a tty, fully buffered to a pipe/file. stderr: unbuffered.
  • A crash before fflush loses buffered output. exit() flushes; _exit/abort/signal don't.
  • getchar() returns int — store in int, compare to EOF.
  • fread/fwrite return element counts; check with feof/ferror.
  • Reading lines: fgets + strip \n, or POSIX getline for unbounded.
  • snprintf over sprintf; memmove when ranges overlap.
  • strtol/strtod (check endptr + errno) over atoi/atof.
  • strtok is stateful & destructive — use strtok_r.
  • Always fclose (it flushes); check its return for write errors.
Q&A
Difference between FILE * and a file descriptor?
A file descriptor is a small integer index into the kernel's open-file table; each read/write is a syscall. FILE * is a stdio structure that adds a user-space buffer and formatting on top of a descriptor, reducing syscalls.
Why did my printf output not appear before the crash?
stdout was fully or line buffered and the buffer wasn't flushed before the abnormal termination. Add \n (on a tty), call fflush(stdout), or set unbuffered with setvbuf.
Why must getchar()'s result be stored in an int?
It returns every possible unsigned char value plus a distinct negative EOF. In a char, either EOF is indistinguishable from a valid byte (0xFF) or the comparison never matches.
memcpy vs memmove?
memcpy is undefined if source and destination overlap; memmove handles overlap correctly (as if via a temporary). Use memmove for arr-shifting.
Why prefer strtol to atoi?
atoi has no way to report overflow or “not a number” — it returns 0 for garbage. strtol reports the first unparsed character via endptr and range errors via errno == ERANGE.
Interview Questions

Basic warm-up

What does fopen return on failure?
NULL, with errno set. Always check before using the stream; report with perror("open failed").
Which stream is unbuffered by default?
stderr, so error messages appear immediately even if the program crashes. stdout is line-buffered to a terminal, fully buffered otherwise.
How do you read a line of unknown length portably-ish?
fgets into a fixed buffer in a loop (detect the missing \n to know it was truncated), or POSIX getline(), which reallocs the buffer to fit.
What does fclose do besides releasing the handle?
Flushes any buffered output first. Its return value can report a deferred write error, so it's worth checking for files you wrote.

Intermediate core

A program's stdout looks fine on the terminal but is reordered when redirected to a file. Why?
On a terminal stdout is line-buffered, so lines appear promptly and roughly in order with stderr (unbuffered). Redirected to a file it becomes fully buffered — large chunks flush at once, so its output can land after stderr text that was actually produced later. Fix with setvbuf, explicit fflush, or stdbuf.
Implement strlen.
size_t my_strlen(const char *s) {
    const char *p = s;
    while (*p) p++;
    return (size_t)(p - s);
}
O(n), no bounds check (matches the standard). Real libc versions read word-at-a-time with bit tricks.
Why is char buf[64]; fread(buf, 1, 64, fp); printf("%s", buf); risky?
fread doesn't null-terminate. If it read 64 bytes with no \0, printf("%s") runs off the end of buf. Read into buf[65], capture the return count n, and set buf[n] = '\0'.
How do you distinguish EOF from a read error after fgets returns NULL?
Call feof(fp) (true → clean end of input) versus ferror(fp) (true → an I/O error occurred, check errno). fgets alone can't tell you which.

Advanced deep

You fork() a process that has buffered but unflushed stdout. What can go wrong?
The child inherits a copy of the not-yet-flushed buffer. If both parent and child later flush (e.g. at exit), the buffered text is written twice. Standard practice: fflush(NULL) before fork, and have the child use _exit (which skips stdio cleanup) after an exec failure so it doesn't double-flush.
When is raw read()/write() preferable to stdio, and what must you handle that stdio hid?
For large bulk transfers, non-blocking/async I/O, sockets with poll, or when you need exact syscall control (O_DIRECT, sendfile, precise lseek). You must then handle short reads/writes (loop until the full count is done), EINTR retries, and your own buffering — all of which stdio did for you.
Why can zeroing a struct with memset(&s, 0, sizeof s) not be assumed to make its pointer members NULL or its floats 0.0 — and why is it fine in practice?
The C standard only guarantees that all-bits-zero is a valid representation for integer types. A null pointer or 0.0 need not be all-bits-zero on exotic architectures, so strictly you should assign NULL/0.0 explicitly (or use {0} initialisation, which does the right thing). In practice every mainstream platform (x86, ARM, IEEE-754, null == 0) makes memset-to-zero produce null pointers and zero floats, so it's a portability pedantry point rather than a real bug on normal targets.

Shell Basics, the Shebang & Execution Model

What actually happens between pressing Enter and the command running.

Notes

What a shell is

A shell is both an interactive command interpreter and a programming language. Common ones: bash (the usual Linux default), dash (a small, fast POSIX sh — often /bin/sh on Debian/Ubuntu), zsh (macOS default), ksh. Scripts that must be portable target POSIX sh; scripts that use [[ ]], arrays, local, etc. require bash.

Three ways to run a script

InvocationWhat happens
./script.shNeeds the execute bit (chmod +x) and a shebang. The kernel reads #! and runs the named interpreter with the script as an argument. Runs in a new process.
bash script.shRuns explicitly under bash; execute bit and shebang are ignored. New process.
source script.sh / . script.shExecutes each line in the current shell — no subprocess. Variable assignments, cd, and function definitions persist. Used for env setup (. ~/.bashrc).

The shebang

#!/usr/bin/env bash   # find bash via PATH -- portable across distros/macOS/Homebrew
#!/bin/bash           # exact path -- predictable, no PATH games (safer for root/cron)
#!/bin/sh             # POSIX shell -- do not use bashisms

Only the first line, and only if it starts with the two bytes #!. On Linux you get at most one argument after the interpreter path, so #!/usr/bin/env bash -e is unreliable — put set -e in the script instead.

How a command name is resolved

bash looks in this order: alias → function → builtin (cd, echo, [, …) → executable found by scanning $PATH left to right (bash caches hits — hash -r clears it). Inspect with type -a name; get just the path with command -v name. Avoid which (an external program, not aware of builtins/functions, behaviour varies).

Exit status

Every command returns 0–255. 0 means success; non-zero means failure. $? holds the last command's status. A process killed by signal N reports 128 + N (so 130 = Ctrl-C / SIGINT, 137 = SIGKILL). true/: always succeed, false always fails.

Startup files (interactive shells)

  • Login shell (SSH, console login, bash -l): reads /etc/profile then the first of ~/.bash_profile, ~/.bash_login, ~/.profile.
  • Interactive non-login (a new terminal tab): reads ~/.bashrc.
  • Common practice: put everything in ~/.bashrc and have ~/.bash_profile source it.
  • Non-interactive scripts read neither — but honour $BASH_ENV if set.
Cheat Sheet
  • ./s.sh & bash s.sh → subshell (changes don't leak). . s.sh / source s.sh → current shell (changes persist).
  • chmod +x s.sh is only needed for ./s.sh.
  • Shebang must be line 1, byte 0. #!/usr/bin/env bash for portability; #!/bin/sh = no bashisms.
  • Don't rely on flags in the shebang — use set -euo pipefail inside.
  • Resolution: alias → function → builtin → $PATH. Check with type -a, command -v.
  • $? = last exit code. 0 = ok. Signal N → 128+N (130 = Ctrl-C).
  • set -x trace, set -e exit on error, set -n parse only.
  • Login shell → ~/.bash_profile; new terminal → ~/.bashrc; script → neither.
Q&A
Difference between running ./script.sh and source script.sh?
./script.sh forks a new shell process; its cd, variable, and function changes vanish when it exits. source (or .) runs the lines in your current shell, so those changes stick. That's why you source an environment file but execute a normal script.
Why #!/usr/bin/env bash instead of #!/bin/bash?
env looks up bash on $PATH, so it works when bash lives in /usr/local/bin or /opt/homebrew/bin (macOS). #!/bin/bash is more predictable and is preferred for privileged/cron scripts where you don't want $PATH to influence which interpreter runs.
What does exit code 130 mean?
The process was terminated by SIGINT (signal 2) — typically the user pressed Ctrl-C. The convention is 128 + signal_number.
Script runs with bash script.sh but "permission denied" with ./script.sh. Why?
./script.sh needs the execute permission bit; bash script.sh only needs read. Run chmod +x script.sh.
Is sh script.sh the same as bash script.sh?
Not necessarily. On many systems /bin/sh is dash or bash-in-POSIX-mode, which rejects arrays, [[ ]], local, source, C-style for, and more.

Basic warm-up

What is a shebang and where must it appear?
The #! line at the very top of a script (first line, first character). It tells the kernel which interpreter to run the file with, e.g. #!/usr/bin/env bash. Without it, ./file is executed by the caller's shell (or fails).
How do you check a script's exit status?
Read $? immediately after it runs: ./job.sh; echo "exit=$?". 0 is success, anything else is failure.
Which file should custom aliases go in for a normal terminal?
~/.bashrc, which is read by interactive non-login shells (new terminal windows/tabs).
What does chmod +x script.sh do?
Adds the execute permission bit so the file can be run directly as ./script.sh.

Intermediate core

A script does cd /var/log and you want your shell to end up there. How do you run it?
Source it: source ./goto.sh or . ./goto.sh. Executing it normally runs the cd in a child process that then exits, leaving your shell's directory unchanged.
Why is which discouraged in scripts?
which is an external binary that doesn't know about shell functions, aliases, or builtins, and its output/exit-code conventions differ between systems. command -v name is a POSIX builtin that reports whatever the shell would actually run, and type -a name shows every match in order.
Explain the difference between a login shell and an interactive shell.
"Login" means the shell was started as part of authenticating a session (console login, SSH, su -) — it reads profile files. "Interactive" means it has a prompt and reads commands from a user — it reads ~/.bashrc. A shell can be one, both, or neither: an SSH session is both; a terminal tab is interactive non-login; a cron job is neither.
What's wrong with #!/usr/bin/env bash -euo pipefail?
On Linux the kernel passes everything after the interpreter as a single argument, so env receives the literal string "bash -euo pipefail" and fails to find that command. Put set -euo pipefail on the first line of the script body instead.

Advanced deep

Walk through exactly what the kernel and shell do when you type ls -l and press Enter.
The shell reads the line, performs expansions (none here), and splits it into words ls and -l. It checks: alias? function? builtin? — no — then searches $PATH, finds /usr/bin/ls (and caches it). It fork()s; the child execve("/usr/bin/ls", ["ls","-l"], environ) which replaces the process image. The parent wait()s. ls writes to fd 1, exits with a status; the shell stores it in $? and prints the next prompt.
How can a script detect whether it was sourced or executed?
In bash: compare ${BASH_SOURCE[0]} with $0 — if they're equal the file is being executed, if they differ it was sourced. A common guard: 
if [[ "${BASH_SOURCE[0]}" == "${0}" ]]; then
    main "$@"   # only run when executed directly
fi
This lets a file act as both a runnable script and a sourceable library of functions.
Your cron job works interactively but fails under cron with "command not found". Why?
cron runs a minimal non-interactive, non-login shell with a bare PATH (often just /usr/bin:/bin) and none of your ~/.bashrc / ~/.profile environment. Tools in /usr/local/bin or a language version manager's shims aren't found. Fixes: use absolute paths, set PATH explicitly at the top of the script, or source the needed profile.

Variables, Quoting & Parameter Expansion

Ninety percent of shell bugs are a missing pair of double quotes.

Notes

Variables

No spaces around =: name=value (a space makes the shell try to run name as a command). Everything is a string. Read with $name or ${name}; use braces when the name touches other text: ${file}_bak. export name puts it in the environment of child processes; without export it's a shell-local variable.

The three quoting modes

FormBehaviour
'single'Completely literal. No expansion of anything. Cannot contain a '.
"double"Expands $var, $(cmd), `cmd`, and \ before $ ` " \ . Suppresses word-splitting and globbing. The default choice.
unquotedExpands and then word-splits on $IFS (space/tab/newline) and applies globbing (*, ?, []). Dangerous with data.
f="my file.txt"
rm $f          # runs: rm my file.txt   -> two args, wrong
rm "$f"        # runs: rm "my file.txt" -> one arg, correct
echo "$HOME"   # /home/leo
echo '$HOME'   # $HOME literally

Always quote expansions unless you have a specific reason not to. The main deliberate exception is when you want splitting, e.g. set -- $flags.

Word splitting and $IFS

After expansion, an unquoted result is split into words at any run of $IFS characters (default space, tab, newline). "$var" is not split; "$@" expands to the positional parameters each individually quoted (the one form you almost always want); "$*" joins them with the first $IFS char.

${v:?msg}Error out with msg if v is unset/empty.

Cheat Sheet
  • Assignment: x=1 — no spaces. Read: "$x" or "${x}".
  • Quote every expansion: "$var", "$(cmd)", "${arr[@]}", "$@".
  • '...' = fully literal. "..." = expand but don't split/glob. Unquoted = expand + split + glob.
  • "$@" = args as separate words (use this). "$*" = args joined into one string.
  • Defaults: ${v:-x} use x, ${v:=x} use & set x, ${v:?err} fail if empty, ${v:+x} x only if v set.
  • Trim: ${v#pfx} ${v##pfx} (front), ${v%sfx} ${v%%sfx} (back). Double = greedy.
  • Replace: ${v/a/b} first, ${v//a/b} all. Case (bash): ${v^^} upper, ${v,,} lower.
  • Length ${#v}; substring ${v:2:3}.
  • Unset vs empty: -/+ without the colon test only "unset"; with : they also treat empty as unset.
Q&A
When do single vs double quotes matter?
Single quotes are fully literal — use them for regexes, sed/awk programs, and passwords. Double quotes still expand $, ` `, $() but prevent word-splitting and globbing — use them around every variable reference.
What does "$@" give you that $@ or "$*" doesn't?
The positional parameters as separate words, each individually quoted, preserving spaces inside each argument. $@ unquoted splits each arg on whitespace; "$*" mashes them into a single string.
Difference between ${v-x} and ${v:-x}?
Without the colon, the fallback applies only when v is unset. With the colon, it also applies when v is set but empty.
How do you get the filename and directory from a path without calling basename/dirname?
"${p##*/}" for the filename, "${p%/*}" for the directory — pure parameter expansion, no subprocess.
Why did for f in $files break on a file called "budget report.xlsx"?
Unquoted $files is word-split on spaces, so the loop sees budget and report.xlsx separately. Store names in an array and iterate "${files[@]}".

Advanced deep

Explain the full order of expansions bash performs on a command line.
1. Brace expansion ({a,b}). 2. Tilde expansion (~). 3. Parameter/variable expansion, command substitution, arithmetic expansion — left to right. 4. Word splitting on $IFS (only on the results of step 3 that were unquoted). 5. Pathname expansion (globbing). 6. Quote removal. Crucially, word splitting and globbing happen after variable expansion, which is why "$var" (quoted) is safe from both, and why you can't glob using a pattern stored in a quoted variable.
You need to split a string on commas into an array. Show a robust way and its caveats.
IFS=, read -r -a parts <<< "$csv"
# parts=(a b c) for csv="a,b,c"
Caveats: this doesn't handle quoted fields or embedded commas (not a real CSV parser); a trailing , yields an empty last element; and setting IFS only for the read line (prefix form) avoids leaking it. For real CSV, use awk/python.
What is the difference between ${arr[@]} and ${arr[*]} inside vs outside double quotes?
Unquoted, both expand and then word-split, so they behave similarly (and unsafely). Quoted, "${arr[@]}" produces one word per element (spaces preserved) — the correct way to pass an array on. "${arr[*]}" produces a single word with elements joined by the first character of IFS. The same distinction as "$@" vs "$*".

Cheat Sheet
  • if branches on exit status 0. Brackets are optional if you already have a command.
  • Prefer [[ ... ]] in bash: no word-split surprises, supports && || < > == globs, =~ regex.
  • POSIX [ ... ]: quote everything, use -a/-o sparingly (prefer [ ] && [ ]).
  • Strings: -z -n = !=. Numbers: -eq -ne -lt -le -gt -ge. Never mix.
  • Files: -e -f -d -r/-w/-x -s -L (symlink) f1 -nt f2.
  • Arithmetic condition: (( n > 0 )). Arithmetic value: x=$(( a*b )).
  • (( )) returns non-zero when the result is 0 — watch out under set -e.
  • case $x in pat) ... ;; *) ... ;; esac — glob patterns, clean multi-way branch.
  • Regex: [[ $s =~ ^[0-9]+$ ]]; captured groups in ${BASH_REMATCH[@]}. Don't quote the pattern.
Q&A
Why prefer [[ ]] over [ ] in bash?
Inside [[ ]] there is no word-splitting or globbing, so [[ $x == foo ]] is safe even when x is empty or has spaces. It also supports &&, ||, unescaped </>, glob matching with ==, and regex with =~.
How do you compare numbers vs strings?
Numbers: [ "$a" -lt "$b" ] or (( a < b )). Strings: [ "$a" = "$b" ] or [[ $a == "$b" ]]. Using = on numbers compares them as text ("10" != "010").
What does if grep -q pattern file; then do without any brackets?
grep -q exits 0 if it found a match, 1 otherwise, and prints nothing. if branches on that status directly — brackets are only needed for test expressions.
How do you test that a variable is a non-negative integer?
[[ $n =~ ^[0-9]+$ ]]. The pattern after =~ must be unquoted; quoting it makes it a literal string match.
Why did [ $answer = yes ] throw "unary operator expected"?
answer was empty, so after expansion the test became [ = yes ] — malformed. Quote it: [ "$answer" = yes ], or use [[ $answer == yes ]].

Advanced deep

Why is [ "$a" = "$b" -a "$c" = "$d" ] considered unsafe, and what should you write?
With -a/-o, test receives many arguments and has to guess how to parse them; certain values (e.g. an operand that is itself =, !, or -n) make the parse ambiguous and the result is unspecified by POSIX. Chain separate tests instead: [ "$a" = "$b" ] && [ "$c" = "$d" ], or use [[ $a == "$b" && $c == "$d" ]] in bash.
What's the difference between [[ $x == $y ]] and [[ $x == "$y" ]]?
On the right side of ==/!= inside [[ ]], an unquoted value is treated as a glob pattern. So if y='*', [[ $x == $y ]] is true for any x, while [[ $x == "$y" ]] is true only when x is literally *. Quote the right side unless you specifically want pattern matching.
How would you emulate [[ ]]'s safety in a POSIX sh script that must run under dash?
Quote every operand, and defend against operands that look like operators by prefixing a constant: [ "x$a" = "x$b" ] or [ "${a}" = "${b}" ] with the leading-x trick for values that could start with -. Use case for pattern matching (case $f in *.txt) ... esac) since [ has no glob operator. For numeric work use [ "$a" -lt "$b" ] which is well-defined.

Loops: for, while, until

And the one correct way to loop over lines of a file.

Notes

for

for host in web1 web2 db1; do ssh "$host" uptime; done
for f in *.log; do gzip -- "$f"; done       # glob; handles spaces
for i in {1..10}; do echo "$i"; done          # brace range (bash)
for ((i = 0; i < n; i++)); do ...; done          # C-style (bash)
for arg in "$@"; do process "$arg"; done     # iterate script args

If a glob matches nothing it stays literal by default (*.log as text). Guard with shopt -s nullglob (bash) so the loop body simply doesn't run.

while / until

while ! ping -c1 -W1 "$host" &>/dev/null; do sleep 2; done
until [[ -f /tmp/ready ]]; do sleep 1; done

while cond loops while cond succeeds; until cond loops until it succeeds.

Reading a file line by line — the correct idiom

while IFS= read -r line; do
    printf '%s\n' "$line"
done < input.txt
  • IFS= — don't trim leading/trailing whitespace.
  • -r — don't treat backslash as an escape.
  • redirect the file into the loop with <, not cat file |.
  • To also get the last line when the file has no trailing newline: while ... || [[ -n $line ]]; do.

Never for line in $(cat file) — it word-splits on spaces and globs, so lines with spaces or * break.

The subshell-in-a-pipeline trap

count=0
cat file | while read -r _; do ((count++)); done
echo "$count"    # prints 0 !

Each pipeline stage runs in a subshell, so count is incremented in a child and lost. Fixes: redirect instead of pipe (done < file), use a process substitution (done < <(cmd)), or in bash set shopt -s lastpipe (non-interactive only).

break / continue

break N and continue N act on the N-th enclosing loop.

Cheat Sheet
  • for x in a b c; do ...; done — iterate a word list / glob / "$@".
  • Glob that might not match: shopt -s nullglob first.
  • C-style: for ((i=0;i<n;i++)). Range: {1..10}, {0..20..5}.
  • Line-by-line: while IFS= read -r line; do ...; done < file.
  • NUL-delimited (filenames from find -print0): while IFS= read -r -d '' f; do ...; done < <(find ... -print0).
  • Never for line in $(cat file); never cat file | while read if you need vars afterwards.
  • Pipeline stages run in subshells → variable changes don't survive. Redirect or use < <(...).
  • break N / continue N target the N-th enclosing loop.
Q&A
Why is for line in $(cat file) wrong?
Command substitution output is word-split on $IFS (spaces, tabs, newlines) and then globbed, so you iterate over words, not lines, and any * expands to filenames. Use while IFS= read -r line; do ...; done < file.
Why does a counter incremented inside cmd | while read read back as unchanged?
The while loop on the right of the pipe runs in a subshell. Its variable updates are in that child process and disappear when it exits. Feed the loop with redirection or process substitution instead of a pipe.
What do IFS= and -r do in read?
IFS= stops read stripping leading/trailing whitespace from the line. -r stops it interpreting backslashes. Together they give you the raw line.
How do you loop over files safely, including names with spaces or newlines?
Use a glob directly (for f in ./*.txt) which is space-safe, or for recursive/complex selection use find ... -print0 piped into while IFS= read -r -d '' f.
Difference between while and until?
while c runs the body as long as c succeeds (exit 0). until c runs the body as long as c fails, stopping once it succeeds.

Functions & Positional Parameters

Functions return an exit code, not a value — internalise that and the rest follows.

Notes

Defining and calling

greet() {                 # POSIX form (preferred)
    local name="$1"       # 'local' is bash/ksh, not POSIX
    printf 'Hello, %s\n' "$name"
}
greet World               # call: no parentheses, args space-separated

Functions must be defined before they're called. They share the shell's environment; local keeps a variable scoped to the function (and its callees — dynamic scope).

Positional parameters

TokenMeaning
$0Script name (not affected by function calls).
$1 … $9, ${10}Arguments. Braces required past 9.
$#Number of arguments.
"$@"All args as separate quoted words. Use this to forward args.
"$*"All args as one string joined by first char of IFS.
shift [n]Drop the first n (default 1) args; $2 becomes $1, etc.

Inside a function, $1… are the function's arguments; $0 is still the script.

Returning results

  • Status: return N sets the exit code (0–255). With no return, the function's status is that of its last command.
  • Value: there is no value return. Either echo/printf the result and have the caller capture it with $(...), or write it into a variable the caller names (pass the name, assign with printf -v or a nameref).
max() { (( $1 > $2 )) && echo "$1" || echo "$2"; }
biggest=$(max 3 9)        # capture stdout

# by-reference (bash 4.3+ nameref)
parse() { local -n out=$1; out="parsed:$2"; }
parse result "data"; echo "$result"   # parsed:data

Gotchas

  • Capturing with $(...) runs the function in a subshell — side effects (variable changes, cd) don't persist.
  • Mixing echo "logging" with echo "result" pollutes the captured value — send logs to >&2.
  • return only takes 0–255; returning -1 becomes 255, and large numbers wrap mod 256.
  • local x=$(cmd) masks cmd's exit status (it becomes local's status, always 0). Split into two lines if you need $?.
Cheat Sheet
  • Define: name() { ...; }. Call: name arg1 arg2 (no parens, no commas).
  • $# count, $1..$9 / ${10} args, "$@" forward-all, shift to consume.
  • Return an exit code with return N (0–255). Return a value via stdout + $(func), or a nameref (local -n).
  • Send diagnostics to stderr (echo ... >&2) so they don't contaminate $(func).
  • local every function variable to avoid clobbering the caller (bash; POSIX has no local).
  • local x=$(cmd) hides cmd's failure — declare then assign on separate lines.
  • $(func) runs in a subshell: no persistent side effects.
  • $0 stays the script name even inside functions; there's no "function name" in $0 (use ${FUNCNAME[0]} in bash).
Q&A
How does a shell function "return" data?
It doesn't return a value. It prints to stdout and the caller captures it with command substitution, or it assigns to a variable whose name the caller passed in. return only sets the numeric exit status.
"$@" vs "$*" for passing arguments through?
"$@" — it preserves each argument as a distinct word, including embedded spaces. "$*" flattens everything into one string and is almost never what you want when forwarding.
What does shift 2 do?
Discards the first two positional parameters; what was $3 becomes $1, and $# drops by 2. Used to consume parsed options before handling the rest.
Why did result=$(myfunc); echo $? always show 0 even when myfunc failed?
If the assignment is local result=$(myfunc), $? reflects the local builtin (success), not the function. Without local, result=$(myfunc) does propagate the function's status. Declare and assign separately when in doubt.
Do variable changes inside x=$(myfunc) persist?
No. Command substitution runs the function in a subshell, so any variables it sets or directories it enters are gone once it returns.

Advanced deep

Explain dynamic scoping in bash functions and a bug it causes.
A local variable is visible not just in the declaring function but in every function it calls (unlike lexical scope). So a helper that reads $i can accidentally see a caller's loop variable i. Worse, a callee that does i=... without local mutates the caller's local i. Defence: local-declare every variable in every function, and give loop counters unlikely names in reusable helpers.
Why can return not signal "value 300", and how do people encode richer results?
Exit statuses are a single byte: return 300 yields 300 & 255 = 44. Conventions: reserve small codes for categories of failure (like curl/rsync do), print the real payload to stdout, or set well-known variables / a nameref. For structured data, emit JSON on stdout and parse with jq.
What's the difference between func() ( ... ) and func() { ... }?
Braces run the body in the current shell; parentheses run it in a subshell. The subshell form auto-isolates side effects: cd, set options, IFS changes, and variable assignments inside it don't leak out. Handy for a function that must cd somewhere to do its work, at the cost of a fork.

I/O Redirection, Pipes & Here-docs

Three fixed file descriptors, and the ordering rule that trips everyone up.

Notes

The standard descriptors

0 = stdin, 1 = stdout, 2 = stderr. Redirection rewires them for one command.

SyntaxEffect
> filestdout to file, truncating it (1> is the same).
>> filestdout appended to file.
2> filestderr to file.
> file 2>&1stdout to file, then stderr to "wherever fd 1 now points" (the file).
2>&1 > fileWrong order: stderr goes to the terminal (fd 1's value at that moment), then stdout goes to file.

2>/dev/nulldiscard stderr.

Redirections are applied left to right. 2>&1 means "make fd 2 a copy of whatever fd 1 is right now", so it must come after > file.

Pipes

a | b connects a's stdout to b's stdin; stderr is not piped unless you add 2>&1 (or |& in bash). Exit status of the pipeline is the last command's, unless set -o pipefail (then it's the last non-zero). $PIPESTATUS (bash array) holds every stage's status. Each stage runs in its own subshell (see the Loops topic for why that matters).

make 2>&1 | tee build.log      # see output AND save it, incl. errors
grep -c ERROR < app.log         # prefer redirection to 'cat app.log |'

Here-documents and here-strings

cat <<EOF          # here-doc: expands $var and $(cmd)
user = $USER
host = $(hostname)
EOF

cat <<'EOF'        # quoted delimiter -> NO expansion (literal)
$USER stays literal
EOF

cat <<-EOF         # <<- strips leading TAB indentation (tabs only!)
	indented with tabs
EOF

grep foo <<< "$text"   # here-string: feed one string as stdin

Custom file descriptors & process substitution

exec 3> audit.log          # open fd 3 for the rest of the script

diff <(sort a.txt) <(sort b.txt)   # <(...) is a filename that streams cmd output

Cheat Sheet
  • fds: 0 in, 1 out, 2 err. > truncate, >> append, < read.
  • Merge err into out: cmd > f 2>&1 — order matters, 2>&1 comes last. Shorthand &> f.
  • Discard: 2>/dev/null, everything: &>/dev/null.
  • Pipes don't carry stderr; use 2>&1 | or bash |&.
  • Pipeline status = last stage. set -o pipefail + ${PIPESTATUS[@]} to catch earlier failures.
  • Prefer cmd < file over cat file | cmd (no extra process, keeps vars in-shell).
  • Here-doc <<EOF expands vars; <<'EOF' is literal; <<-EOF strips leading tabs.
  • Here-string: cmd <<< "$var".
  • Process substitution: diff <(a) <(b), ... > >(consumer). bash/zsh only.
  • Persistent fd: exec 3>file ... echo x >&3 ... exec 3>&-.
Q&A
Why does cmd 2>&1 > file still print errors to the screen?
Redirections apply left to right. At 2>&1, fd 1 is still the terminal, so fd 2 is pointed there. Then > file moves fd 1 to the file — but fd 2 already has its own copy of the terminal. Correct order: cmd > file 2>&1.
How do you save a command's output and see it live?
Pipe to tee: cmd | tee out.log. Add 2>&1 before the pipe to include errors, and tee -a to append.
Difference between <<EOF and <<'EOF'?
Unquoted delimiter: the here-doc body undergoes variable and command substitution. Quoted ('EOF' or \EOF): the body is passed through literally — useful for embedding scripts or config with $ in them.
What's a here-string?
cmd <<< "word" feeds word (plus a trailing newline) to cmd's stdin. Handy: read a b c <<< "$line", bc <<< "2^10".
What does <(command) evaluate to?
A filename (like /dev/fd/63) that, when read, yields command's stdout. It lets tools that require file arguments consume a pipeline, e.g. diff <(cmd1) <(cmd2).

The child inherited the script's stdout/stderr, which may be a pipe (e.g. script | tee). Command Substitution & Arithmetic

Capturing output, doing maths, and not losing exit codes in the process.

Notes

Command substitution

now=$(date +%s)                 # preferred
now=`date +%s`                  # legacy backticks -- avoid
files=$(ls)                     # fine to print; bad to parse (see caveats)

$(...) runs the command in a subshell, captures its stdout, and strips all trailing newlines. Prefer it over backticks: $() nests cleanly ($(a $(b))), and backslashes inside behave predictably.

  • The result is subject to word-splitting and globbing unless quoted: always write x="$(cmd)".
  • Only stdout is captured; stderr still goes to the terminal (add 2>&1 to capture it too).
  • Exit status: x=$(cmd) sets $? to cmd's status. But local x=$(cmd) / export x=$(cmd) set $? to the builtin's status (0). Declare then assign separately.
  • Trailing-newline stripping bites when you expected one: [[ "$(printf 'a\n\n')" == "a" ]] is true.

Arithmetic

FormUse

  • A leading zero means octal: $(( 08 )) is an error. Strip it: $(( 10#$var )) forces base 10 — essential for values like "09" from date.

  • Undefined variables in arithmetic are treated as 0 (even under set -u for bare names inside (( ))).
Cheat Sheet
  • Capture: out="$(cmd)" — always quote; use $() not backticks.
  • $() strips trailing newlines and captures stdout only.
  • local x=$(cmd) loses cmd's exit code — use local x; x=$(cmd).
  • Maths value: n=$(( a + b )). Maths condition/side-effect: (( n > 0 )), (( n++ )).
  • Inside (( )) / $(( )), use bare names (no $), C operators, **, %, ternary.
  • Integer only. Decimals → bc -l, awk, python3.
  • Leading zero = octal. Force base 10 with $(( 10#$n )).
  • (( )) returns non-zero when result is 0 — guard under set -e.
  • $RANDOM (0–32767), $SECONDS, $(( RANDOM % 100 )) for a rough 0–99.
Q&A
Why prefer $(...) to backticks?
It nests without escaping ($(a $(b))), backslash handling inside is intuitive, and it's visually clearer. Backticks are only kept for very old sh compatibility.
Does command substitution capture stderr?
No, only stdout. Add 2>&1 inside: out=$(cmd 2>&1) to fold stderr in.
Difference between $(( )) and (( ))?
$(( )) is an expansion that produces the numeric result as text (use it where you need the value). (( )) is a command that evaluates the expression for its side effects and exit status (use it in if/while or for i++).
Why does x=$(( 08 + 1 )) error?
A leading zero makes bash parse 08 as octal, and 8 isn't a valid octal digit. Use $(( 10#08 + 1 )) to force base 10.
How do you do floating-point division in the shell?
Delegate: echo "scale=2; 7/3" | bc -l, or awk 'BEGIN{printf "%.2f\n", 7/3}'. Bash arithmetic is integer-only.

Exit Status, set -euo pipefail & trap

The "unofficial strict mode" — what it buys you, and where it bites.

Notes

The strict-mode header

#!/usr/bin/env bash
set -euo pipefail
IFS=$'\n\t'          # optional: safer word-splitting
OptionEffect
set -e (errexit)Exit immediately if a command returns non-zero (with many exceptions, below).
set -u (nounset)Referencing an unset variable is a fatal error. Use "${x:-}" for intentionally-optional vars.
set -o pipefailA pipeline fails if any stage fails, not just the last.
set -x (xtrace)Print each command (after expansion) before running — debugging.

Where set -e does not trigger

  • A command in an if/while/until condition, or on the left of && / ||, or negated with !.
  • Any command in a pipeline except the last (unless pipefail).
  • Inside a function called in such a context — set -e is suppressed for the whole function if the call is tested. This is the classic surprise.
  • local x=$(failing_cmd) — status is the local builtin's.

So set -e is a helpful safety net, not a guarantee. For critical steps, still check explicitly: cmd || die "cmd failed".

trap — run code on signals and on exit

tmpdir=$(mktemp -d)
cleanup() { rm -rf "$tmpdir"; }
trap cleanup EXIT              # runs on ANY exit: normal, error, or signal
trap 'echo "interrupted"; exit 130' INT TERM

EXITThe shell exits, for any reason. Best place for cleanup.
ERRA command fails (same rules/exceptions as set -e). Good for logging context.
INTCtrl-C (SIGINT).
TERMkill default.
DEBUGBefore every command (bash) — profiling/tracing.

trap - EXIT removes a trap. Traps are per-shell: a subshell doesn't inherit them unless it's a function context. Keep handlers short and idempotent (an EXIT trap can run after a partial failure).

Safe temp files

tmp=$(mktemp)                       # unique file, mode 600
tmpdir=$(mktemp -d)                 # unique dir
trap 'rm -f "$tmp"; rm -rf "$tmpdir"' EXIT

Never use /tmp/myscript.$$ hand-rolled names — predictable, racy, a symlink-attack vector. mktemp creates atomically.

Cheat Sheet
  • Header: set -euo pipefail. Add set -x temporarily to debug.
  • -e exit-on-error, -u unset-is-error, pipefail any-stage-fails.
  • -e is skipped in if/while conditions, after !, before &&/||, and non-final pipe stages — and inside a function whose call is being tested.
  • For must-succeed steps: cmd || die "msg" — don't rely on -e alone.
  • Allow one command to fail under -e: cmd || true.
  • trap 'cleanup' EXIT — runs on normal exit, error, and signal. Put temp-file removal here.
  • trap 'handler' INT TERM for graceful Ctrl-C / kill.
  • trap - SIG resets; trap '' SIG ignores.
  • Temp files: mktemp / mktemp -d, never /tmp/$$.
Q&A
What do the three parts of set -euo pipefail do?
-e: abort on any unchecked command failure. -u: abort on use of an unset variable. pipefail: make a pipeline's status reflect the first failing stage, not just the last command.
Why is set -e not a substitute for real error handling?
It has many exemptions (conditions, negation, &&/|| chains, pipelines, tested function calls) and can be toggled off by a sourced file. Critical operations still need explicit || { ...; exit 1; }.
How do you guarantee cleanup even if the script is killed?
trap 'rm -rf "$tmpdir"' EXIT. The EXIT trap runs on normal completion, on set -e abort, and after the default action of most signals.
How do you let a single command fail without set -e killing the script?
Append || true (or || :), or wrap it: if ! cmd; then handle; fi.
Why use mktemp instead of /tmp/out.$$?
$$ is predictable, so an attacker can pre-create /tmp/out.PID as a symlink and redirect your writes. mktemp creates a fresh, unguessable name atomically with safe permissions.

How do you see every command as it executes?
set -x (or run the script with bash -x script.sh). set +x turns it off.

Intermediate core

With set -e, this function doesn't abort on failure when called as if check; then. Why?
When a function (or any compound command) is used as the condition of if, &&, ||, or after !, errexit is disabled for the entire duration of that command — including inside the function. So an internal failing command won't stop it; only the function's final exit status is used. If you need internal failures to matter, don't test the call, or check explicitly inside.
Write a robust temp-dir + cleanup preamble.

trap 'echo "aborted" >&2; exit 130' INT TERM
The EXIT trap covers normal and error exit; the INT/TERM trap gives a clean message and a conventional code (and still triggers EXIT).
Why can grep pattern file under set -e abort your script unexpectedly?
grep exits 1 when it finds no match — a normal outcome, not an error, but set -e treats non-zero as failure. Guard it: grep pattern file || true, or handle both cases with an if.
How do you make an ERR trap print the failing line and command?
trap 'echo "ERR at line $LINENO: $BASH_COMMAND (rc=$?)" >&2' ERR
$LINENO and $BASH_COMMAND are set by bash at the point of failure; useful with set -o errtrace (-E) so the trap is inherited by functions and subshells.

Advanced deep

Your script spawns a long child; on Ctrl-C the script exits but the child keeps running. Fix it.
The child is in the same process group and also received SIGINT, but if it ignores it or is in its own session it survives; conversely a backgrounded child doesn't get the terminal's SIGINT at all. Track the PID and kill it from the trap: 
child_pid=
cleanup() { [[ $child_pid ]] && kill "$child_pid" 2>/dev/null; }
trap cleanup EXIT INT TERM
long-task & child_pid=$!
wait "$child_pid"
For a whole tree, kill -- -$$ (negative PID = process group) or start the child with setsid and kill its group.
Explain why set -e; a | b with b succeeding hides a's crash, and the two ways to catch it.
errexit only inspects the pipeline's exit status, which by default is b's. If b exits 0, the pipeline is "successful" regardless of a. Fix 1: set -o pipefail, making the pipeline status the last non-zero one. Fix 2: check ${PIPESTATUS[@]} right after the pipeline and act on any non-zero entry.
What's the difference between trap '' INT, trap - INT, and trap 'handler' INT in a script that also spawns children?
trap 'handler' INT installs your handler. trap '' INT makes the shell ignore SIGINT — and crucially, children started afterward inherit "ignored", so they can't be Ctrl-C'd either. trap - INT resets to the default disposition (terminate). A common bug: setting trap '' INT to protect a critical section and forgetting to restore it, leaving un-interruptible subprocesses.

Implement a graceful shutdown: on SIGTERM, stop accepting work, let in-flight jobs finish, then exit.
pids=()
term=0

    next_item || break
    work "$item" & pids+=($!)
done

exit 0
The trap just sets a flag; the loop checks it at a safe point rather than being interrupted mid-item, then waits out the workers. Real supervisors (systemd) send SIGTERM, wait TimeoutStopSec, then SIGKILL.
A backgrounded child becomes a zombie / an orphan. Explain both and how they're handled.
Zombie: the child exited but the parent hasn't waited, so the kernel keeps its exit status and a PID slot. In a script, wait (or the shell reaping jobs) clears it; a long-lived parent that never waits leaks zombies. Orphan: the parent exited first; the child is re-parented to init/PID 1 (or a subreaper), which waits for it when it dies. Orphans are harmless; zombies accumulate. nohup/disown deliberately create orphans that outlive the shell.
You need to kill a process and all its descendants. What are the options and trade-offs?
(1) Process group: start it with setsid or in its own job, then kill -TERM -- -$PGID (negative = whole group). Clean, but a child that calls setsid escapes. (2) pkill -P / walk /proc/*/stat for the PID tree recursively — racy if processes fork during the walk. (3) cgroups (systemd-run --scope, or a manual cgroup.kill): the kernel guarantees every task in the cgroup is included — the robust modern answer. (4) A PID-namespace (container): killing PID 1 in the namespace takes everything with it.

  • struct and class can have member functions, constructors/destructors, access control (class defaults private, struct public).
  • new/delete (call ctors/dtors) instead of malloc/free.
  • References, function/operator overloading, templates, namespaces, RAII, exceptions, the STL.
  • nullptr not NULL; bool is built in; // comments (also in C99).
Cheat Sheet
  • Reference = permanent alias: init required, no rebind, no null, no arithmetic.
  • Pointer = object holding an address: nullable, reseatable, supports arithmetic.
  • Read-only non-trivial param → const T&. Optional param → const T* or std::optional.
  • Small/trivially-copyable → pass by value. Strings you only read → std::string_view.
  • Never return a reference/pointer to a local.
  • const T& to a temporary extends the temporary's life to the ref's scope (immediate temp only).
  • T&& is an rvalue reference (see Move Semantics), not "reference to reference".
  • class members default private; struct default public. Otherwise identical.
Q&A
Can a reference be null or rebound?
No. It must be bound to a valid object at initialisation and refers to that same object for its whole life. If you need "maybe none" or "point somewhere else later", use a pointer.
Why prefer const std::string& over std::string for a read-only parameter?
It avoids copying the string on every call. const documents and enforces that the function won't modify the caller's object. (For strings specifically, std::string_view is often even better.)
Is a reference an object?
Not observably — it has no size of its own (sizeof(ref) gives the referent's size), you can't take "the address of the reference" (you get the referent's address), and you can't have an array of references. Implementations typically use a pointer under the hood.
What extends a temporary's lifetime?
Binding it directly to a named const& (or &&) reference. The temporary then lives as long as the reference. This does not apply to a reference returned from a function or to a temporary reached via a member access.
Default access in class vs struct?
class: members and base classes are private by default. struct: public. That's the only language difference.
Interview Questions

Basic warm-up

Give three differences between a reference and a pointer.
A reference must be initialised and can't be reseated or null; a pointer can be uninitialised, reassigned, and null. A pointer supports arithmetic and has its own address/storage; a reference doesn't. Syntax: . vs ->.
How do you pass a large object to a function without copying it, read-only?
By const reference: void f(const BigThing& b).
What's wrong with returning int& to a local variable?
The local is destroyed when the function returns, so the caller holds a reference to freed stack memory — undefined behaviour on use.

Intermediate core

When is a pointer parameter the right choice over a reference?
When "no argument" is meaningful (an optional out-param you can pass nullptr for), when the callee must store or reseat what it's given, when interoperating with a C API, or when passing an array with a separate length. Otherwise a reference is clearer and can't be null.
Explain what happens: const std::string& s = std::string("x") + "y";
The + produces a temporary std::string. Binding it to the named const& extends its lifetime to match s's scope, so using s afterwards is valid. Without the reference (or with auto&& plus a member access) it would be destroyed at the end of the full expression.
What does int& f(int& x) { return x; } enable, and what's the risk?
Returning a reference lets the call be an lvalue: f(a) = 5; assigns to a. It's how operator[] and operator* work. The risk is returning a reference to something that won't outlive the call (a local, or a container element after the container is resized).

Advanced deep

Why does std::vector<bool> break the "references alias real objects" model?
It's a space-optimised specialisation that packs bits, so v[i] can't return a real bool& — it returns a proxy object that behaves like a reference. Consequences: auto x = v[i]; deduces the proxy, not bool; bool* p = &v[i]; doesn't compile; and generic code written for "container of T" can misbehave. This is the standard example of "don't use vector<bool> when you want a container of bytes-sized bools".
Does binding a temporary to a const& member in a constructor extend its lifetime?
No. Lifetime extension does not apply to reference members: the temporary is destroyed at the end of the constructor, leaving the member dangling. A class that stores a const T& member must be documented as non-owning and the caller must guarantee the referent outlives the object. If you need ownership, store a value or a smart pointer.
What is reference collapsing and where does it matter?
When references-to-references arise through templates or typedefs, they collapse by the rule "& wins": T& &, T&& &, T& && → T&; only T&& && → T&&. This is the mechanism behind forwarding references (template<class T> void f(T&& x)): an lvalue argument deduces T as U& so T&& collapses to U&, an rvalue deduces U so it stays U&& — enabling std::forward.

Classes, Constructors, Destructors & RAII

RAII is the single idea that makes C++ resource management sane. Know it cold.

Notes

Object lifetime

Construction runs when an object comes into existence (declaration, new, element insertion); the destructor runs deterministically when it leaves scope, is deleted, or its container is destroyed. This determinism — unlike GC languages — is what RAII exploits.

Member initialisation

class Widget {
    int id_;
    std::string name_;
    const Config& cfg_;
public:
    Widget(int id, std::string name, const Config& c)
        : id_(id), name_(std::move(name)), cfg_(c) {}   // member init list
};
  • Members are initialised in declaration order, not the order in the init list — compilers warn if they differ.
  • Use the init list, not assignment in the body: const members, references, and members without a default ctor must be initialised there; others avoid a default-construct-then-assign.
  • Prefer default member initialisers (int id_ = 0;) for defaults.

Special member functions

FunctionPurpose
Default constructorT() — suppressed once you declare any other ctor.
Destructor~T() — release resources.
Copy ctor / copy assignValue-copy from another T.
Move ctor / move assignSteal resources from an rvalue T.

= default asks for the compiler's version; = delete forbids it (e.g. a non-copyable handle). Declaring a destructor or copy op suppresses the implicit move ops — see Rule of 5.

RAII

Resource Acquisition Is Initialisation: wrap every resource (heap memory, file handle, lock, socket, DB transaction) in an object that acquires it in its constructor and releases it in its destructor. Then correctness is automatic — early return, exception, or normal exit all run the destructor.

{
    std::lock_guard<std::mutex> lk(m);   // lock acquired
    std::ofstream out("log.txt");        // file opened
    if (bad) return;                     // dtors still run: file closed, mutex unlocked
    out << data;
}                                        // dtors run here on the normal path

Standard RAII types: std::unique_ptr/shared_ptr, lock_guard/unique_lock/scoped_lock, fstream, std::vector/string, std::jthread. Roll your own with a small wrapper class or std::unique_ptr with a custom deleter.

explicit

Mark single-argument constructors explicit to stop surprising implicit conversions (void f(Widget); f(42); silently building a Widget from 42). explicit on conversion operators too. Rule of thumb: single-arg ctors are explicit unless you deliberately want the conversion (like std::string from const char*).

Cheat Sheet
  • Dtor runs deterministically at scope exit / delete / container destruction — the basis of RAII.
  • Init members in the member initialiser list; they run in declaration order.
  • const members, references, and no-default-ctor members must use the init list.
  • Prefer default member initialisers (T x_ = 0;) for simple defaults.
  • Declaring any constructor removes the implicit default constructor.
  • RAII: acquire in ctor, release in dtor → exception-safe, leak-free, no manual cleanup.
  • Use standard RAII types; never raw new/delete, raw lock/unlock, raw fopen.
  • explicit on single-argument constructors and conversion operators by default.
  • = default / = delete to request or forbid a special member.
Q&A
What is RAII in one sentence?
Tie a resource's lifetime to an object's lifetime, so the destructor releases it automatically on every exit path.
In what order are class members constructed?
In the order they are declared in the class, regardless of the order in the constructor's initialiser list. Destructors run in reverse.
Why prefer the member initialiser list to assigning in the constructor body?
Body assignment first default-constructs the member then overwrites it (two steps, and impossible for const/reference/no-default-ctor members). The init list constructs it once with the right value.
What does explicit prevent?
Implicit conversions and copy-initialisation through that constructor/operator, so Widget w = 5; or passing 5 where a Widget is expected won't silently compile.
When does the compiler stop giving you a default constructor?
As soon as you declare any constructor of your own. Add T() = default; to get it back.
Interview Questions

Basic warm-up

When does a destructor run for a local object?
When control leaves the object's scope — by reaching the closing brace, return, break, or an exception propagating through. Always, on every path.
Name three standard RAII types.
std::unique_ptr / std::shared_ptr, std::lock_guard / std::scoped_lock, std::fstream, std::vector / std::string — any three.
What's the fix for a function that news an object and might throw before delete?
Don't use raw new. Hold it in a std::unique_ptr (or a value/container). Its destructor frees the memory whether the function returns normally or via an exception.

Intermediate core

Members declared a then b; init list says : b(1), a(b). What happens?
a is constructed first (declaration order) using b, which hasn't been initialised yet — so a gets garbage. Then b is set to 1. The init-list order is misleading; reorder the declarations or don't cross-depend.
Write a minimal RAII wrapper for a C FILE*.
class File {
    FILE* f_;
public:
    explicit File(const char* p) : f_(std::fopen(p, "r")) {
        if (!f_) throw std::runtime_error("open");
    }
    ~File() { if (f_) std::fclose(f_); }
    File(const File&) = delete;
    File& operator=(const File&) = delete;
    FILE* get() const { return f_; }
};
Or just std::unique_ptr<FILE, decltype(&std::fclose)> with fclose as the deleter.
Why should you generally not do real work in a constructor that can't signal failure?
A constructor has no return value, so the only way to report failure is to throw. If throwing isn't acceptable in your context, the object can end up half-constructed and invalid. Options: throw and let RAII clean up, use a factory function returning std::optional/expected, or a two-phase init() (least preferred — leaves a zombie state).

Advanced deep

What happens if a destructor throws, and what's the rule?
If a destructor throws while another exception is already propagating (stack unwinding), std::terminate is called — the program dies. Since C++11 destructors are implicitly noexcept, so a throw from one calls terminate anyway. Rule: destructors must not let exceptions escape. If cleanup can fail (e.g. close() on a buffered file), catch and log inside the destructor, and offer a separate close() method callers can use to handle errors explicitly.
Explain the order of operations when an exception is thrown from a constructor's body.
Any base-class subobjects and data members that were fully constructed before the throw are destroyed, in reverse order. The object's own destructor does not run (the object never finished construction). If the object was being created with new, the matching operator delete is called to free the raw storage. This is why a member that is itself RAII (like a unique_ptr) makes constructor bodies exception-safe for free.
You need "run this cleanup on scope exit" without writing a whole class. Options?
A scope-guard: a small template holding a callable and invoking it in its destructor (ScopeGuard g{[&]{ cleanup(); }};), with a dismiss() to cancel. This is std::experimental::scope_exit / gsl::finally / Boost.ScopeExit, and is standardised as std::scope_exit in C++23's library fundamentals. Useful for C-API resources and rollback logic where a dedicated RAII type would be overkill.

Copy Semantics & the Rule of 3/5/0

If you write one of the special members, you probably need to think about all of them.

Notes

Shallow vs deep copy

The compiler-generated copy constructor and copy assignment do a memberwise copy. For a class holding a raw owning pointer that means two objects pointing at the same buffer — a double-free and aliasing bug. You then need a deep copy that duplicates the buffer.

class Buf {
    int* p_; size_t n_;
public:
    Buf(const Buf& o) : p_(new int[o.n_]), n_(o.n_) { std::copy(o.p_, o.p_+n_, p_); }
    Buf& operator=(Buf o) { swap(*this, o); return *this; }  // copy-and-swap
    ~Buf() { delete[] p_; }
};

The rules

RuleStatement
Rule of 3If you define a destructor, copy ctor, or copy assignment, you almost certainly need all three.
Rule of 5C++11: add the move ctor and move assignment to that set.
Rule of 0Best: design classes that need none of them — hold resources in RAII members (vector, unique_ptr) so the compiler-generated versions are correct.

copy-and-swap

Take the parameter by value (invokes copy or move), then swap with *this. One implementation handles both copy and move assignment, is self-assignment safe, and gives the strong exception guarantee (the copy happens before any mutation).

Suppression rules

  • Declaring a destructor or any copy op ⇒ move ops are not generated (you silently get copies where you expected moves).
  • Declaring a move op ⇒ copy ops are deleted.
  • So: if you declare one special member, = default or = delete the rest explicitly.
Cheat Sheet
  • Compiler copy = memberwise (shallow). Raw owning pointer → you must deep-copy.
  • Rule of 3: dtor + copy ctor + copy assign travel together.
  • Rule of 5: + move ctor + move assign (C++11).
  • Rule of 0: hold resources in RAII members, declare none of the five, let the compiler do it right.
  • copy-and-swap: T& operator=(T rhs){ swap(*this,rhs); return *this; } — covers copy+move, self-assign safe, strong guarantee.
  • User-declared dtor/copy ⇒ no implicit moves (perf trap). User-declared move ⇒ copies deleted.
  • If you declare one, =default/=delete the others.
  • Non-copyable resource handle: T(const T&)=delete; T& operator=(const T&)=delete;.
Q&A
What's the Rule of 3?
If a class needs a user-defined destructor, copy constructor, or copy-assignment operator, it almost certainly needs all three, because they all manage the same resource.
What is the Rule of 0 and why is it preferred?
Write classes so they need none of the special members — put each resource in a type that already manages itself (std::vector, std::unique_ptr, std::string). The implicitly generated copy/move/destroy then do the right thing, with less code to get wrong.
Why does copy-and-swap handle self-assignment automatically?
The right-hand side is copied into a by-value parameter first; only then do you swap. Even if &rhs == this, you're swapping with an independent copy, so nothing is corrupted.
You add a destructor to log object destruction. What breaks?
The implicit move constructor and move assignment stop being generated, so operations you expected to move now silently copy — a performance regression. Add T(T&&) = default; T& operator=(T&&) = default;.
How do you make a class non-copyable but movable?
= delete the copy constructor and copy assignment; = default (or define) the move constructor and move assignment. This is exactly what std::unique_ptr does.
Interview Questions

Basic warm-up

What does the compiler-generated copy constructor do?
Copies each base and member subobject from the source — a memberwise (shallow) copy. Fine for value-like members; wrong for a raw owning pointer.
Which five functions does the Rule of 5 cover?
Destructor, copy constructor, copy assignment, move constructor, move assignment.
How do you forbid copying?
MyClass(const MyClass&) = delete; and MyClass& operator=(const MyClass&) = delete;.

Intermediate core

Implement copy-assignment for a class owning an int* data_; size_t n_; without copy-and-swap. What must you handle?
Guard self-assignment, allocate the new buffer before freeing the old (strong guarantee), copy, then release the old and update pointers/size: 
Buf& operator=(const Buf& o) {
    if (this == &o) return *this;
    int* q = new int[o.n_];
    std::copy(o.data_, o.data_ + o.n_, q);
    delete[] data_;
    data_ = q; n_ = o.n_;
    return *this;
}
copy-and-swap does all of this more safely with less code.
Why is Rule of 0 not always achievable?
When you're wrapping a resource with no ready-made RAII type — an OS handle, a C library object, a resource needing a non-trivial release protocol. Then write one small RAII wrapper (Rule of 5, or unique_ptr with a custom deleter) and let everything else compose it (Rule of 0).

Advanced deep

A class has a std::vector member and a user-declared destructor that does nothing. Performance profile shows copies where moves were expected. Explain and fix.
The empty user-declared ~T() {} suppresses the implicit move constructor/assignment, so T is copy-only; returning one by value or inserting into a container deep-copies the vector. Fix: delete the pointless destructor entirely (best — back to Rule of 0), or if it must stay, add T(T&&) = default; T& operator=(T&&) = default; (and the copies too, to be explicit).
Is a defaulted copy assignment operator always noexcept? Why does it matter?
No — if any member's copy assignment can throw (e.g. std::string reallocating), the defaulted one is potentially-throwing. It matters because std::vector and friends use std::move_if_noexcept: if a type's move constructor isn't noexcept, the vector copies instead of moves during reallocation to preserve the strong guarantee. So marking move operations noexcept (when they truly can't throw) is a real performance lever.

Move Semantics & rvalue References

Transferring ownership instead of copying it — and what std::move actually does (almost nothing).

Notes

Value categories

  • lvalue — has a name / identity, address-of works (x, *p, arr[i]).
  • prvalue — a pure "value" with no identity (42, a + b, f() returning by value).
  • xvalue — an "expiring" object, e.g. the result of std::move(x) — has identity but may be moved from.

T&& is an rvalue reference: it binds to rvalues (prvalues/xvalues) and lets an overload "claim" a temporary's guts.

std::move and std::forward

std::string a = "hello";
std::string b = std::move(a);   // move ctor: b steals a's buffer; a is valid-but-unspecified

std::move is just a static_cast<T&&> — it produces no code, it only changes the value category so a move overload is selected. Nothing is moved until a move ctor/assignment actually runs. std::forward<T>(x) conditionally casts, used with forwarding references to preserve the caller's lvalue/rvalue-ness ("perfect forwarding").

Writing move operations

Buf(Buf&& o) noexcept
    : p_(o.p_), n_(o.n_) { o.p_ = nullptr; o.n_ = 0; }   // leave source destructible
  • Mark them noexcept — containers only move (rather than copy) on reallocation if the move can't throw.
  • Leave the moved-from object in a valid but unspecified state: safe to destroy and to assign to, contents undefined. Don't read its value.

Copy elision / RVO

Returning a local by value doesn't copy or move — the object is constructed directly in the caller's slot (guaranteed for prvalues since C++17, and NRVO for named locals as an optimisation). So return std::move(local); is an anti-pattern: it disables NRVO and forces a move.

Cheat Sheet
  • lvalue = named/addressable; prvalue = pure value; xvalue = expiring (from std::move).
  • std::move(x) = static_cast<T&&>(x): no runtime cost, just enables a move overload.
  • Move ctor/assign: steal the pointers, null out the source, be noexcept.
  • Moved-from = valid but unspecified: OK to destroy/reassign, don't rely on the value.
  • noexcept moves let std::vector move instead of copy on growth (move_if_noexcept).
  • Don't return std::move(local) — it blocks NRVO. Just return local;.
  • T&& as a deduced template parameter is a forwarding reference; use std::forward<T>.
  • Pass-by-value + std::move into a member is a clean "sink" parameter idiom.
Q&A
What does std::move do at runtime?
Nothing. It's a compile-time cast to an rvalue reference. The actual work happens if and when a move constructor or move assignment operator is subsequently called.
What state is a moved-from object left in?
Valid but unspecified: its invariants hold, it can be destroyed and assigned a new value, but you must not assume anything about its contents. Standard-library types are typically left empty.
Why should move operations be noexcept?
Containers like std::vector use std::move_if_noexcept when reallocating: they move elements only if the move constructor is noexcept, otherwise they copy (to keep the strong exception guarantee). A throwing move op silently costs you copies.
Is return std::move(x); a good idea?
No. For a local returned by value, the compiler can elide the copy/move entirely (RVO/NRVO). Wrapping it in std::move turns the return expression into an xvalue that no longer qualifies for NRVO, forcing an actual move. Just return x;.
What's a forwarding (universal) reference?
T&& where T is a template parameter deduced from the argument. It binds to both lvalues and rvalues; combined with std::forward<T> it passes the argument on with its original value category intact.
Interview Questions

Basic warm-up

Difference between an lvalue and an rvalue, informally?
An lvalue has a name and a stable address you can take (x, obj.member). An rvalue is a temporary/literal with no lasting identity (x + 1, 42, a by-value function return).
What type of reference does std::move(x) yield?
An rvalue reference (T&&) — specifically an xvalue — so overload resolution picks the move constructor/assignment.
After auto b = std::move(a); for a std::string a, can you still use a?
Yes, but only operations with no precondition on its value: destroy it, or assign it a fresh value. Reading its contents is not meaningful (it's typically empty).

Intermediate core

Write a "sink" setter that works efficiently for both lvalue and rvalue strings.
void set_name(std::string n) { name_ = std::move(n); }
Called with an lvalue → one copy into n, then a move. Called with an rvalue → one move into n, then a move. Single overload, near-optimal both ways.
Why does adding a throwing move constructor sometimes make code slower?
std::vector reallocation calls move_if_noexcept. If your move ctor isn't noexcept, the vector copies every element instead of moving during each growth, to preserve the strong guarantee if an element operation throws. Marking the move noexcept (when true) restores move-on-grow.

Advanced deep

Explain why template<class T> void wrap(T&& x){ inner(std::forward<T>(x)); } forwards correctly but inner(x) or inner(std::move(x)) would not.
With a forwarding reference, an lvalue argument deduces T = U& (so T&& collapses to U&), an rvalue deduces T = U (T&& stays U&&). Inside, x itself is always an lvalue (it has a name). inner(x) would always pass an lvalue, losing move-ability. inner(std::move(x)) would always pass an rvalue, wrongly stealing from an lvalue the caller still owns. std::forward<T>(x) casts back to U& or U&& exactly matching what was passed.
When is guaranteed copy elision (C++17) actually guaranteed, versus just NRVO?
Guaranteed: initialising an object from a prvalue of the same type — T x = T(args);, return T(args);, passing T(args) by value. There is no temporary at all; the object is built in place. NRVO (returning a named local) is still only a permitted optimisation, not mandatory, and can be defeated by e.g. returning one of several different locals on different paths, or return std::move(local).

Inheritance & Virtual Dispatch

The vtable, the virtual destructor rule, and object slicing.

Notes

How dynamic dispatch works

A class with any virtual function gets a hidden vptr pointing at its class's vtable — an array of function pointers. A call base_ptr->draw() reads the vptr, indexes the vtable, and calls the most-derived override. Cost: one extra indirection and a non-inlinable call.

struct Shape {
    virtual double area() const = 0;   // pure virtual -> abstract class
    virtual ~Shape() = default;         // REQUIRED for polymorphic base
};
struct Circle : Shape {
    double r;
    double area() const override { return 3.14159 * r * r; }
};

The virtual destructor rule

If you ever delete a derived object through a base pointer, the base destructor must be virtual — otherwise only ~Base runs and the derived part leaks / is UB. Any class with virtual functions should have a virtual (or protected) destructor.

override and final

  • override — compiler error if it doesn't actually override (wrong signature, missing const). Always use it.
  • final — on a method: no further overriding; on a class: no further derivation. Can enable devirtualisation.

Object slicing

Circle c{{}, 2.0};
Shape s = c;        // SLICE: only the Shape subobject is copied; area() is Shape's
std::vector<Shape> v; v.push_back(c);   // slices too

Polymorphism needs a pointer or reference (Shape&, Shape*, unique_ptr<Shape>). Store std::unique_ptr<Shape> in containers, not Shape.

Non-virtual by default

Unlike Java, C++ methods are non-virtual unless marked. Calling a non-virtual method through a base pointer uses the static type. Also: never call virtuals from a constructor or destructor — dispatch resolves to the currently-constructed class, not the derived one.

Cheat Sheet
  • virtual → vptr + per-class vtable → call resolved by dynamic type. One indirection, no inlining.
  • Polymorphic base ⇒ virtual ~Base() (or protected ~Base()). Non-negotiable if deleting via base ptr.
  • Always write override; use final to seal and to help devirtualisation.
  • Pure virtual (= 0) → abstract class, can't instantiate.
  • Polymorphism only through pointer/reference. Value assignment → slicing.
  • Containers of polymorphic objects: vector<unique_ptr<Base>>.
  • Methods are non-virtual by default (unlike Java/C#).
  • Don't call virtual functions from ctors/dtors — you won't get the derived override.
  • dynamic_cast for safe downcasts (needs RTTI); returns nullptr / throws on failure.
Q&A
What is a vtable?
A per-class table of pointers to that class's virtual function implementations. Each polymorphic object holds a hidden pointer (vptr) to its class's vtable; a virtual call dereferences it to find the right override at runtime.
Why must a polymorphic base class have a virtual destructor?
So that delete base_ptr; invokes the derived destructor first (then the base's). Without virtual, only the base destructor runs — the derived members leak and it's undefined behaviour.
What is object slicing?
Copying a derived object into a base-type variable (by value) discards the derived part, leaving only the base subobject. Virtual calls then dispatch to the base version. Avoid by using references/pointers.
Are C++ member functions virtual by default?
No. You must write virtual. A call through a base pointer to a non-virtual method uses the pointer's static type.
Why not call a virtual function from a constructor?
During Base's constructor the object is a Base (the derived part isn't built yet), so the call resolves to Base's version, not the override you probably expected. Same in reverse during destruction.
Interview Questions

Basic warm-up

What makes a class abstract?
At least one pure virtual function (virtual void f() = 0;). You can't create instances of it, only of concrete derived classes that override every pure virtual.
What does override buy you?
A compile-time check that the function really overrides a base virtual. It catches signature typos (missing const, wrong parameter type) that would otherwise silently create a new, non-overriding function.
How should you store polymorphic objects in a std::vector?
As std::vector<std::unique_ptr<Base>> (or shared_ptr). Storing Base by value slices.

Intermediate core

Roughly what's the runtime cost of a virtual call vs a normal call?
One extra load (vptr) plus an indirect call through the vtable slot — a few cycles, usually well-predicted. The bigger cost is that the compiler can't inline it, blocking downstream optimisation. final or a known concrete type lets the compiler devirtualise and inline.
A base class has no virtual functions but is used polymorphically via Base*. Someone adds virtual void foo(). What just changed about sizeof(Base) and layout?
The class gains a vptr (typically 8 bytes on 64-bit), so sizeof grows and the member layout shifts. This breaks binary compatibility and any code that assumed a POD layout (e.g. memcpy, C interop, serialization by raw bytes).

Advanced deep

How does virtual dispatch interact with multiple inheritance and virtual bases?
Each base subobject that introduces virtuals gets its own vptr, so a multiply-derived object can hold several vptrs. Calling through a pointer to a secondary base requires a "this-pointer adjustment" (a fixed offset, often stored in the vtable as a thunk) so the override sees the correct this. Virtual inheritance adds a level of indirection (a vbase pointer/offset) to locate the shared base subobject. This is why MI with polymorphism has real layout and call-cost complexity, and why interfaces (pure-virtual, no data) are the usual disciplined use of MI.
What is the "deleting destructor" in a vtable and why is it there?
For a class with a virtual destructor, the compiler typically puts two destructor entries in the vtable: a "complete object destructor" (runs member/base dtors) and a "deleting destructor" (does that and then calls operator delete). delete base_ptr goes through the deleting-destructor slot so the correct operator delete (possibly a class-specific one, with the right size) is invoked for the dynamic type.

Operator Overloading

Make your type behave like a built-in — and know the canonical forms so it behaves correctly.

Notes

Member vs free function

  • Member: =, [], (), ->, and anything that must have a class lvalue on the left.
  • Free (often friend): symmetric binary operators (+, ==, <<) so that implicit conversions work on both sides (2 + mynum as well as mynum + 2).

Canonical arithmetic

struct Vec2 {
    double x, y;
    Vec2& operator+=(const Vec2& r) { x += r.x; y += r.y; return *this; }
};
inline Vec2 operator+(Vec2 a, const Vec2& b) { a += b; return a; }  // define + in terms of +=

Pattern: implement the compound-assignment version as a member, then the binary version as a free function taking the left operand by value and reusing +=.

Comparison — the C++20 spaceship

auto operator<=>(const Vec2&) const = default;   // generates < <= > >= and ==

Pre-C++20 you wrote == and < and derived the rest (or used std::rel_ops / Boost). <=> returns std::strong_ordering / weak_ordering / partial_ordering.

Stream insertion

friend std::ostream& operator<<(std::ostream& os, const Vec2& v) {
    return os << '(' << v.x << ", " << v.y << ')';
}

Rules & pitfalls

  • You cannot invent new operators or change arity/precedence. Can't overload ., ::, ?:, sizeof.
  • ++/--: prefix returns T&; postfix takes a dummy int and returns a T by value.
  • [] usually needs a const and non-const overload; C++23 allows multi-arg [].
  • Overload only when the meaning is obvious. Cute operators (+ for "run pipeline") hurt readers.
  • Conversion operators: make them explicit unless the implicit conversion is genuinely wanted (explicit operator bool() is the common case).
Cheat Sheet
  • Members: = [] () -> and left-operand-mutating ops. Free/friend: symmetric + - == <<.
  • Define op= as a member, then op as a free function: T operator+(T a, const T& b){ a += b; return a; }.
  • C++20: auto operator<=>(const T&) const = default; → all six relational + ==.
  • Pre-20: write == and <, build the rest from them.
  • operator<< for streams is a friend taking (ostream&, const T&), returns the stream.
  • Prefix ++: T& operator++(). Postfix: T operator++(int).
  • Can't create new operators or touch . :: ?: sizeof.
  • explicit operator bool() for "is valid" checks; keep other conversions explicit too.
  • Overload only when semantics are unambiguous.
Q&A
Why implement operator+ as a non-member?
So implicit conversions apply symmetrically. A member operator+ only converts the right operand, so 2 + obj wouldn't compile while obj + 2 would. A free function converts both.
How do prefix and postfix ++ differ in signature?
Prefix: T& operator++();. Postfix: T operator++(int); — the unused int parameter is just a tag; it returns a copy of the old value.
What does operator<=> generate?
From a single defaulted (or user) three-way comparison, the compiler synthesises <, <=, >, >=; a defaulted <=> also gives you == and !=.
Which operators cannot be overloaded?
. (member access), .*, ::, ?:, sizeof, alignof, typeid, and the preprocessor's #/##.
Why make a conversion operator explicit?
To prevent it firing in unexpected contexts (arithmetic, overload resolution, function arguments). explicit operator bool() still works in if/while conditions (contextual conversion) but not in int x = obj;.

Basic warm-up

Which operator must be a member function?
operator=, operator[], operator(), and operator-> must be non-static members.

T& (returning *this), so assignments can chain: a = b = c;.

Give the two overloads of operator[] a container needs and why.
T& operator[](size_t i); for mutable access and const T& operator[](size_t i) const; for read access on a const container. Without the const overload you can't index a const object at all.

Advanced deep

What ordering category should operator<=> return for a type holding a float, and what's the consequence?
std::partial_ordering, because floating-point has NaN: NaN is unordered with everything, so no total order exists. Consequence: you can't use such a type directly as a std::set/map key or with algorithms requiring a strict weak ordering without defining a custom total-order comparator (e.g. one that gives NaN a defined position). A defaulted <=> on a struct with a float member yields partial_ordering automatically.
Why can overloading operator&& / operator|| be a subtle bug source?
The built-in &&/|| short-circuit and impose a sequence point between operands. An overloaded version is an ordinary function call: both operands are fully evaluated, in unspecified order, before the "operator" runs. Code relying on short-circuit semantics (p && p->ok()) silently breaks. Same trap historically with overloading operator,. Best practice: don't overload these three.

Templates & Generic Programming

Compile-time code generation — how deduction, specialization and instantiation actually work.

Notes

Function and class templates

template<class T>
const T& max_of(const T& a, const T& b) { return a < b ? b : a; }

template<class T, size_t N>
struct Array { T data[N]; size_t size() const { return N; } };

A template is a pattern; the compiler instantiates a concrete version for each set of arguments actually used. Unused member functions of a class template aren't instantiated.

Argument deduction

  • Function templates deduce T from the call arguments; class templates need explicit args (or CTAD in C++17: std::vector v{1,2,3};).
  • Deduction strips top-level const and references (unless the parameter is T&/T&&).
  • auto uses the same rules; decltype(auto) preserves references/const.

Specialization

template<class T> struct Hash { size_t operator()(const T&) const; };
template<> struct Hash<std::string> { size_t operator()(const std::string&) const; };  // full
template<class T> struct Hash<T*> { size_t operator()(T*) const; };  // partial (classes only)

Function templates can only be fully specialized — for "partial" behaviour, overload instead.

Where the code must live

Template definitions normally go in the header: the compiler needs the full definition at each instantiation point. Putting them in a .cpp gives "undefined reference" link errors unless you use explicit instantiation.

Two-phase lookup

Names that don't depend on T are looked up when the template is defined; dependent names when it's instantiated. Hence this->member, typename T::iterator, and template disambiguators in dependent contexts.

Cheat Sheet
  • Template = pattern; compiler instantiates one concrete version per distinct argument set.
  • Function templates deduce args; class templates need explicit args or CTAD (C++17).
  • Definitions go in headers (or use explicit instantiation in a .cpp).
  • Full specialization: template<> struct X<int> {...};. Partial: classes only. Functions: overload instead.
  • Dependent type → prefix typename; dependent template → prefix template; dependent member → this->.
  • Non-type params: integers, enums, pointers, auto (C++17), and structural types (C++20).
  • Unused member functions of a class template are never instantiated (can hold ill-formed code for unused types — fragile).
  • Concepts (C++20) > SFINAE for constraining; error messages are far better.
Q&A
Why do template definitions usually go in headers?
The compiler generates code separately for each translation unit that instantiates the template, so it needs the full definition visible there. A definition hidden in one .cpp can't be instantiated elsewhere → link error.
Difference between full and partial specialization?
Full: you fix all template parameters (template<> class X<int, 4>). Partial: you fix some or constrain the shape (template<class T> class X<T*, 4>). Only class templates and variable templates support partial specialization.
Why typename T::value_type and not just T::value_type?
Inside a template, T::value_type is a dependent name and the compiler assumes it's a value, not a type, unless you write typename. (C++20 relaxes this in some contexts.)
What is CTAD?
Class Template Argument Deduction (C++17): std::pair p{1, 2.0}; deduces std::pair<int,double> without you spelling the arguments, using implicit or user-written deduction guides.
Does instantiating std::vector<MyType> instantiate all its members?
No — only the member functions you actually call. That's why a type missing, say, operator< can still be stored in a vector, as long as you never call sort on it.
Interview Questions

Basic warm-up

What does "template instantiation" mean?
The compiler generating a concrete function or class from the template pattern for a specific set of template arguments, the first time that combination is used.
Where do you put a class template's member function definitions?
In the header (inline in the class, or after it in the same header). Not in a separate .cpp, unless you explicitly instantiate for each needed type there.
Can a function template be partially specialized?
No. Only fully specialized. For partial-specialization-like behaviour you write additional overloads.

Intermediate core

Given template<class T> void f(T x), what is T for const int& r; f(r);?
T = int. By-value deduction strips the reference and the top-level const, so x is a plain int copy. If the parameter were T&, T would be const int; if T&& (forwarding ref), T would be const int&.
Why might a template compile for int but fail only when instantiated with std::string?
Non-dependent errors are caught at definition, but anything depending on T is only checked at instantiation. If the body does something valid for int but not std::string (e.g. x * 2, or calls a member string lacks), you only find out when that instantiation is required. Concepts / static_assert surface it earlier with a clear message.

Advanced deep

Explain how explicit instantiation lets you keep template definitions in a .cpp.
Put the template definition in a .cpp, then in that same file write template class Foo<int>; / template void bar<double>(double); for each type you support. The compiler emits those concrete instantiations into the object file, so other TUs (which see only a declaration in the header) link against them. Trade-off: the set of supported types is fixed and centralised; used for compile-time reduction and to hide implementation in libraries.
What is the ODR hazard with templates and how do implementations avoid link errors from duplicate instantiations?
The same template instantiation (e.g. std::vector<int>::push_back) is generated in many translation units, technically violating the one-definition rule for a normal function. Templates get a special ODR exemption provided every definition is token-for-token identical. The linker then deduplicates: instantiations are emitted into COMDAT sections / weak symbols, and the linker keeps one copy and discards the rest. Inconsistent definitions (different compile flags, macros, headers) produce silent ODR violations rather than errors.

Metaprogramming: SFINAE, Concepts, CRTP

Constraining templates and computing with types — the old way and the C++20 way.

Notes

Type traits & if constexpr

template<class T>
void dump(const T& v) {
    if constexpr (std::is_integral_v<T>)  std::cout << std::hex << v;
    else if constexpr (std::is_floating_point_v<T>)  std::cout << std::scientific << v;
    else  std::cout << v;
}

<type_traits> gives compile-time predicates (is_pointer_v, is_same_v, is_base_of_v…) and transformations (remove_cv_t, decay_t, conditional_t). if constexpr (C++17) discards the untaken branch at compile time, so each branch only needs to be valid for the types that reach it.

SFINAE (pre-C++20 constraint mechanism)

template<class T,
         class = std::enable_if_t<std::is_arithmetic_v<T>>>
T twice(T x) { return x + x; }

"Substitution Failure Is Not An Error": if forming the signature with a given T is ill-formed, that overload is silently removed from the set rather than causing a hard error. Powerful but produces infamous error messages.

Concepts (C++20 — use these instead)

template<class T>
concept Number = std::integral<T> || std::floating_point<T>;

template<Number T>
T twice(T x) { return x + x; }        // clear constraint, clear errors

auto f(std::ranges::range auto&& r);   // terse form

CRTP — static polymorphism

template<class Derived>
struct Printable {
    void print() const {
        std::cout << static_cast<const Derived&>(*this).to_string();
    }
};
struct Widget : Printable<Widget> { std::string to_string() const; };

The base is parameterised on the derived class, so it can call derived methods with no vtable — compile-time dispatch, zero runtime cost. Used for mixins, enable_shared_from_this, expression templates.

Variadic templates

template<class... Args>
void log(Args&&... args) {
    (std::cout << ... << args) << '\n';   // C++17 fold expression
}
Cheat Sheet
  • <type_traits>: is_*_v predicates, *_t transforms, conditional_t, decay_t.
  • if constexpr (cond) — compile-time branch; untaken branch not instantiated.
  • SFINAE = remove an overload when its signature is ill-formed for the given types (enable_if_t, trailing-return decltype).
  • C++20 concepts replace SFINAE for constraints: readable, better errors, subsumption-based overload ordering.
  • Terse constrained templates: void f(std::integral auto x).
  • CRTP: struct D : Base<D> — static polymorphism, no vtable; base uses static_cast<D&>(*this).
  • Variadic: template<class... Ts>, sizeof...(Ts), fold expressions (... op pack).
  • static_assert(cond, "msg") to fail loudly and early.
Q&A
What does SFINAE stand for and do?
Substitution Failure Is Not An Error. When the compiler substitutes template arguments and the resulting signature is invalid, that candidate is dropped from overload resolution instead of triggering a compile error — letting you select overloads by type properties.
Why prefer concepts over enable_if?
Concepts express the requirement directly, produce short "constraint not satisfied" errors instead of pages of substitution noise, participate in overload ordering (more-constrained wins), and can be reused and named.
What problem does CRTP solve?
Polymorphic-style code reuse (a base providing behaviour in terms of derived operations) without the runtime cost of virtual calls, because the derived type is known at compile time.
What is if constexpr good for?
Writing one template that does different things per type, where the non-selected branch would be ill-formed for that type. The discarded branch isn't instantiated, so it doesn't need to compile.
How do you get the number of arguments in a variadic pack?
sizeof...(Args) (or sizeof...(args)) — a compile-time size_t.
Interview Questions

Basic warm-up

<type_traits>.

    { t.size() } -> std::convertible_to<std::size_t>;

In CRTP, how does the base call a derived method?
static_cast<Derived&>(*this).method() — a safe downcast because Derived is the template argument and is guaranteed to be the actual most-derived type.

Intermediate core

Rewrite an enable_if-constrained function using a concept.
// old

// new

What's the runtime and binary-size trade-off of CRTP vs virtual functions?
CRTP: no vptr, calls inline, fastest — but each derived type instantiates its own copy of the base's code (code bloat), the type must be known at compile time, and you can't store heterogeneous objects in one container. Virtual: one shared implementation, runtime polymorphism, heterogeneous containers — at the cost of an indirection and no inlining. Use virtual for open sets / plugin-style designs; CRTP for closed sets in hot paths.

Advanced deep

Explain the "detection idiom" and what replaced it in C++20.
Pre-C++20, to ask "does T have member x?" you used std::void_t plus a primary/partial-specialization pair: the specialization is only viable if decltype(std::declval<T>().x) is well-formed, and you check which one was chosen. It's verbose and easy to get subtly wrong (value category, const). C++20 requires-expressions do this directly and readably: requires(T t){ t.x; }, usable inline or as a named concept.
How does concept subsumption affect overload resolution?
When two candidate function templates are both viable and constrained, the one whose constraints subsume the other's (are strictly more specific, decomposed into atomic constraints) is preferred — no ambiguity. E.g. an overload constrained on std::random_access_iterator beats one on std::forward_iterator for a pointer argument. This gives clean "pick the best-matching implementation" tag-dispatch without helper types, but only works if the concepts are defined so one genuinely implies the other.

Q&A
Default container, and why?
std::vector — contiguous storage means great cache locality and O(1) indexing; amortised O(1) append. Only move away from it when a measured need (front insertion, ordered keys, hashed lookup, stable node addresses) says so.
What invalidates vector iterators?
Any operation that reallocates (push_back/insert/resize past capacity) invalidates all iterators, pointers, and references. Insert/erase without reallocation invalidates those at or after the modification point.
Why can't you std::sort a std::list?
std::sort needs random-access iterators (it does index arithmetic); list only offers bidirectional. Use the member list::sort(), which is a merge sort over the nodes.
map vs unordered_map?
map: red-black tree, O(log n), keeps keys sorted, stable iteration order, needs operator<. unordered_map: hash table, O(1) average / O(n) worst, no order, needs a hash + operator==. Pick unordered for raw speed, map when you need ordering or range queries.
What's the gotcha with map::operator[]?
If the key isn't present it inserts a default-constructed value and returns a reference to it. Read-only lookups should use find or at to avoid accidental insertion (and it doesn't work on a const map).
Interview Questions

Basic warm-up

Which container gives O(1) random access and contiguous storage?
std::vector (and std::array for fixed size).
How do you remove all elements equal to x from a vector?
v.erase(std::remove(v.begin(), v.end(), x), v.end()); — or C++20 std::erase(v, x);.
Which containers keep their elements sorted?
std::map, std::set, std::multimap, std::multiset (ordered associative, tree-based).

Intermediate core

You append 10 million ints to a vector in a loop and it's slow. Fix?
Call v.reserve(10'000'000) first. Without it the vector reallocates and moves all elements ~log₂(n) times as it grows (geometric growth), which dominates. With reserve, every push_back is a true O(1) write.
You store objects in a vector and keep pointers to them elsewhere. What's the danger?
Any reallocation (further push_back, insert, resize) moves the storage, leaving your external pointers dangling. Options: reserve enough up front, use std::deque (stable element addresses except at the modified end), a node-based container, or store std::unique_ptr<T> in the vector so the pointees don't move.

Advanced deep

When can unordered_map degrade to O(n), and how do you defend against it?
When many keys hash to the same bucket — a weak hash function, or adversarial input (hash-flooding DoS). All operations on that bucket become linear. Defences: a good/seeded hash (randomised per process), monitoring load_factor() and bucket_size, switching to std::map (guaranteed O(log n)) for untrusted keys, or a container with better worst-case behaviour. Note unordered_map also has poor cache behaviour vs a flat hash map because of its node-per-element, chained design.
Compare std::map and a sorted std::vector of pairs for a lookup-heavy, insert-rarely workload.
Sorted vector + std::lower_bound: O(log n) lookup like map, but contiguous — far better cache locality, smaller memory (no per-node pointers/colour bit), and prefetch-friendly, so typically several times faster in practice. Downside: insertion/erase is O(n) (shift elements), and iterators/references are invalidated on insert. For "build once, query many" it's the better structure; map wins when inserts and deletes are frequent and interleaved with lookups.

Q&A
What is the erase-remove idiom?
std::remove(_if) shuffles the "kept" elements to the front and returns an iterator to the new logical end, but doesn't change the container's size. You then call container.erase(newEnd, container.end()) to actually drop the tail. C++20 wraps both in std::erase/std::erase_if.
Difference between [=] and [&] capture?
[=] copies every used variable into the closure (safe lifetime, but copies, and this is captured by pointer). [&] captures by reference (no copy, but the closure must not outlive those variables). Explicit lists are preferred over both.
Why can a non-capturing lambda be assigned to a function pointer but a capturing one can't?
A capturing lambda carries state, so it's a unique class type with data members — there's nothing for a plain function pointer to point at. A stateless lambda has an implicit conversion to R(*)(Args...).
What's the runtime cost of std::function?
Type erasure: it may allocate on the heap for larger callables, and invoking it is an indirect call through a vtable-like mechanism, so it doesn't inline. Fine for callbacks and event tables; avoid in tight inner loops.
How do you move a unique_ptr into a lambda?
Init-capture: [p = std::move(ptr)]() mutable { ... } (C++14+). Plain [ptr] would try to copy it.

A view pipeline stored in a variable produces garbage when iterated later. Why?

Smart Pointers & Ownership

Express who owns what in the type system, so leaks and double-frees become compile-time-ish problems.

Notes

std::unique_ptr — sole ownership

auto w = std::make_unique<Widget>(args);   // no raw new
use(*w); w->method();
return w;                                 // moves out; cheap
  • Zero overhead vs a raw pointer (same size, no refcount) — the default owning pointer.
  • Move-only: transfers ownership, can't be copied.
  • Custom deleter for C resources: std::unique_ptr<FILE, decltype(&fclose)> f(fopen(...), &fclose);.
  • Use it for pimpl, factory returns, and members that own a resource.

std::shared_ptr — shared ownership

  • Holds a control block with a strong count and a weak count; the object is destroyed when the strong count hits 0, the control block when the weak count also hits 0.
  • Refcount updates are atomic — thread-safe count, but not a thread-safe object.
  • make_shared does one allocation for object + control block (faster, better locality); a separate shared_ptr(new T) does two.
  • Twice the size of a raw pointer; copies touch atomics. Don't pass shared_ptr around when you only need to use the object — pass T& or T*.

std::weak_ptr — break cycles

std::weak_ptr<Node> parent;          // child->parent is weak; parent->child is shared
if (auto p = parent.lock()) use(*p);   // lock() returns shared_ptr or null

Two shared_ptrs pointing at each other never reach refcount 0 → leak. Make one direction weak_ptr. Also used for caches and observer lists.

Ownership signalling in APIs

ParameterMeans
unique_ptr<T> by value"I take ownership"
shared_ptr<T> by value"I share ownership (will keep it alive)"
T& / T*"I just use it; caller keeps ownership"
T* (nullable) or optional<T&>-ish"use it if provided"
Cheat Sheet
  • make_unique / make_shared — never bare new/delete.
  • unique_ptr: sole owner, move-only, zero overhead. The default.
  • shared_ptr: refcounted, atomic count, 2× pointer size, control block. Use only when ownership is genuinely shared.
  • make_shared: single allocation (object + control block); shared_ptr(new T): two.
  • weak_ptr: non-owning observer; .lock() to get a shared_ptr or null; breaks reference cycles.
  • Pass smart pointers only to transfer/share ownership; otherwise pass const T& / T*.
  • Custom deleter: part of the type for unique_ptr, type-erased for shared_ptr.
  • Atomic refcount = thread-safe count, not thread-safe object.
  • enable_shared_from_this to hand out shared_ptr to this safely.
Q&A
unique_ptr vs shared_ptr — default choice?
unique_ptr. It's the same size as a raw pointer, has no atomic operations, and expresses the common case (one owner). Reach for shared_ptr only when multiple parts of the program genuinely need to keep the object alive independently.
What's inside a shared_ptr's control block?
The strong reference count, the weak reference count, the deleter, and (for make_shared) the object storage itself. Strong hits 0 → object destroyed; weak also 0 → control block freed.
Why make_shared over shared_ptr<T>(new T)?
One heap allocation instead of two (object + control block combined), better cache locality, and it's exception-safe in argument lists. Downside: the object's memory isn't freed until the last weak_ptr also goes away.
How does weak_ptr prevent leaks?
It observes an object without contributing to the strong count, so a parent↔child or node↔node relationship where one side is weak_ptr can still reach refcount 0 and be destroyed.
Is shared_ptr thread-safe?
The reference count is atomic, so copying/destroying shared_ptrs to the same object from multiple threads is safe. Accessing the pointed-to object concurrently, or mutating the same shared_ptr instance from multiple threads, is not — you need your own synchronisation (or atomic<shared_ptr>).
Interview Questions

Basic warm-up

How do you create a unique_ptr to a new Foo(1, 2)?
auto p = std::make_unique<Foo>(1, 2);.
Can you copy a unique_ptr?
No — it's move-only. auto q = std::move(p); transfers ownership and leaves p null.
Which smart pointer breaks reference cycles?
std::weak_ptr — it references the object without keeping it alive.

Intermediate core

A tree where each node has shared_ptr children and a shared_ptr back to its parent leaks. Fix it.
Make the parent link a std::weak_ptr<Node>. Children keep the parent alive is the wrong direction; the parent owns the children (shared_ptr down), children merely observe the parent (weak_ptr up). Now destroying the root drops all strong counts to 0.
A function takes std::shared_ptr<Config> by value but only reads from it. What's wrong and what's better?
Every call bumps and later drops an atomic refcount, and copies 16 bytes, for no ownership reason. Take const Config& (or const Config* if it can be absent). Pass the shared_ptr itself only if the function stores it or spawns work that outlives the call.

Advanced deep

Why is returning shared_ptr(this) from a member function a bug, and what's the correct mechanism?
It creates a second, independent control block for an object that's presumably already owned by another shared_ptr — now two control blocks think they own it, and you get a double delete. Correct: derive from std::enable_shared_from_this<T> and call shared_from_this(), which returns a shared_ptr sharing the existing control block. Precondition: the object must already be managed by a shared_ptr (else shared_from_this throws / is UB pre-C++17).
What's the memory cost difference between make_shared<T>() and shared_ptr<T>(new T) beyond the allocation count, and when does it matter?
make_shared puts the object and control block in one block, so the object's storage can't be reclaimed until the last weak_ptr dies (the whole block is freed together). With separate allocation, the object is freed as soon as the strong count hits 0, and only the small control block lingers for the weak count. So for large objects with long-lived weak_ptrs (caches, observers), separate allocation frees the big buffer sooner. Otherwise make_shared wins on speed and locality.

Exception Handling & Safety Guarantees

Stack unwinding, noexcept, and the three levels of "this function is exception-safe".

Notes

Mechanics

try {
    risky();
} catch (const std::out_of_range& e) {
    log(e.what());
} catch (const std::exception& e) {   // base last
    log(e.what());
} catch (...) {                        // anything else
    cleanup(); throw;                    // rethrow current exception
}
  • throw expr; copies/moves expr into an implementation-managed area, then unwinds the stack: every fully-constructed local's destructor runs, up to a matching catch.
  • Catch by const& (no slicing, no copy). Order handlers most-derived first.
  • Throw by value, catch by reference. Throw types deriving from std::exception.
  • No matching handler anywhere → std::terminate.

noexcept

  • void f() noexcept; promises not to throw. If it does, std::terminate — no unwinding.
  • Destructors and (usually) move operations should be noexcept; the library optimises based on it (move_if_noexcept).
  • noexcept(expr) is also a compile-time query.

The three exception-safety guarantees

GuaranteeMeaning
No-throwNever throws (swap, destructors, most moves). The strongest.
StrongIf it throws, state is exactly as before — commit-or-rollback (e.g. copy-and-swap).
BasicIf it throws, no leaks and all invariants hold, but state may have changed. The minimum acceptable.

Writing exception-safe code

  • Lean on RAII — every resource in a guard object, so unwinding cleans up automatically.
  • Do all the "can throw" work (allocate, copy) into locals first, then commit with non-throwing operations (swap, moves, pointer assignment).
  • Never let an exception escape a destructor or a noexcept function.
  • Exceptions are for exceptional, rare failures. For expected failures (parse error, key not found) prefer std::optional / std::expected / error codes — exceptions have near-zero cost when not thrown but are expensive when thrown.
Cheat Sheet
  • Throw by value, catch by const&, order handlers derived→base, catch(...) last.
  • throw; (no operand) rethrows the in-flight exception.
  • Unwinding runs destructors of fully-constructed locals up to the handler.
  • Derive exception types from std::exception; override what().
  • noexcept: violate it → std::terminate. Put it on dtors and true-nothrow moves.
  • Guarantees: nothrow > strong (rollback) > basic (no leak, valid state). Aim for basic everywhere, strong where it matters.
  • Technique for strong: prepare in locals, commit via nothrow ops (copy-and-swap).
  • Destructors must not throw (they're implicitly noexcept).
  • Use optional/expected/error codes for expected failures; exceptions for rare ones.
Q&A
What is stack unwinding?
When an exception propagates, the runtime walks back up the call stack, running the destructor of every fully-constructed automatic object in each frame, until it finds a matching catch. This is what makes RAII cleanup automatic on the error path.
Why catch by const reference?
Catching by value slices a derived exception down to the handler's type and makes a copy (which could itself throw). By reference you get the real dynamic type and no copy; const because you shouldn't be mutating it.
What are the three exception-safety guarantees?
No-throw (never throws), strong (throw ⇒ state unchanged, like a transaction), basic (throw ⇒ no leaks and invariants intact, but state may differ). Basic is the minimum; strong is ideal for operations users treat as atomic.
What happens if a noexcept function throws?
std::terminate is called immediately — no stack unwinding, no catch gets a chance.
Why not use exceptions for a "key not found" lookup?
That's an expected outcome, not an exceptional one. Throwing/catching is comparatively slow and clutters control flow; return std::optional, an iterator compared to end(), or std::expected.
Interview Questions

Basic warm-up

Should you throw a pointer, a value, or a reference?
Throw by value (typically a temporary of a type derived from std::exception). Catch by const reference.
What does a bare throw; inside a catch block do?
Rethrows the exception currently being handled, preserving its dynamic type, so an outer handler can deal with it.
What's the ordering rule for multiple catch clauses?
Most-derived types first, base types after — the first matching handler wins, so a catch(std::exception&) placed first would shadow all more specific ones.

Intermediate core

Make this give the strong guarantee: void add(T x){ items_.push_back(x); ++count_; }
push_back can throw (allocation). If it does, count_ hasn't changed yet — good — but if you'd incremented first you'd be inconsistent. As written it's already close to strong provided count_ is only incremented after a successful push_back. Even better: drop count_ and use items_.size(), so there's nothing to keep in sync. If you must keep both, order matters: throwing operation first, bookkeeping after.
Why is a throwing move constructor a problem for std::vector?
On reallocation the vector must relocate elements. To preserve the strong guarantee it uses move_if_noexcept: if the move ctor isn't noexcept, it copies instead (so a mid-relocation throw leaves the original intact). So a throwing move silently forces copies on every growth.

Advanced deep

What is the runtime cost model of exceptions ("zero-cost" EH), and when is it a poor fit?
Modern table-based EH (Itanium ABI) adds essentially no cost on the non-throwing path — no per-try setup; instead the compiler emits static unwind tables consulted only when a throw happens. But a throw is expensive: table lookup, per-frame destructor dispatch, RTTI type matching — often microseconds. Poor fit: hot loops where "failure" is common (parsing, search misses), hard-real-time / latency-critical code where the unbounded throw cost is unacceptable, and constrained embedded targets where the unwind tables bloat the binary or EH is disabled entirely. There, use return-based error handling (expected, error codes).
Two exceptions in flight at once — when does that happen and what's the result?
It happens if a destructor (or other cleanup) throws while stack unwinding is already in progress for an earlier exception. The standard doesn't try to handle two simultaneously: std::terminate is called. This is the core reason destructors must be noexcept. If cleanup genuinely can fail, catch and swallow (or log) inside the destructor, and expose a separate throwing close()/commit() for callers who want to handle it. std::uncaught_exceptions() lets a type detect it's being destroyed during unwinding.

constexpr, consteval & Compile-time

Moving work from run time to compile time — and the keywords that force it.

Notes

The spectrum

KeywordMeaning
constRuntime-immutable. May or may not be a compile-time constant.
constexpr (var)Must be initialised by a constant expression; usable where the language needs one (array sizes, template args, case labels).
constexpr (function)Can run at compile time if all inputs are constant; otherwise runs normally at run time.
consteval (C++20)An immediate function — every call must be evaluated at compile time or it's an error.
constinit (C++20)Guarantees static/thread-storage init happens at compile time (no dynamic-init order fiasco), but the object stays mutable.

Example

constexpr int factorial(int n) {
    int r = 1;
    for (int i = 2; i <= n; ++i) r *= i;   // loops, locals, branches all fine since C++14
    return r;
}
constexpr int f5 = factorial(5);   // computed at compile time -> 120
int x = read_int();
int fx = factorial(x);            // same function, now runs at run time

if constexpr (sizeof(void*) == 8) { ... }   // compile-time branch (see Metaprogramming)

What's allowed in a constexpr function

Progressively relaxed: C++11 was one return; C++14 added loops, locals, mutation; C++20 added try/catch (no throw), constexpr new/delete, std::vector/std::string in constexpr context (if freed before the constant is finalised), virtual calls. Still no reinterpret_cast, no non-constexpr calls, no undefined behaviour (a constexpr eval that hits UB is a compile error — a nice bonus).

Why it matters

  • Lookup tables, hashes, parsers built at compile time → zero startup cost.
  • Values usable as template arguments / array bounds.
  • UB in a constant-evaluated path is diagnosed by the compiler.
  • Replaces most old template-metaprogramming "value computation" with ordinary code.
Cheat Sheet
  • const = won't change at runtime. constexpr = usable as a compile-time constant.
  • constexpr function: compile-time if it can be, else runtime. Same body serves both.
  • consteval: must be compile-time (immediate function).
  • constinit: compile-time initialisation, still mutable — kills static-init-order problems.
  • C++14+: loops, mutable locals, multiple statements allowed in constexpr.
  • C++20: constexpr std::vector/std::string, new/delete, virtual, try (no throw).
  • UB during constant evaluation = compile error (a feature).
  • Use for lookup tables, compile-time parsing/validation, and template/array-bound values.
  • if constexpr is a compile-time branch, unrelated to constexpr variables/functions but same family.
Q&A
const vs constexpr on a variable?
const just means "not modified after init" — the initialiser can be a runtime value. constexpr additionally requires the initialiser to be a constant expression, so the variable can be used where the language demands a compile-time constant.
Does a constexpr function always run at compile time?
No. It runs at compile time when called in a constant-expression context or with all-constant arguments; otherwise it's an ordinary function call at run time. consteval is the version that must be compile-time.
What does consteval add over constexpr?
It forbids runtime evaluation: every call site must produce a compile-time constant, or the program is ill-formed. Useful for things like compile-time-only factories or reflection helpers.
What problem does constinit solve?
The static initialisation order fiasco: it guarantees a namespace-scope or static variable is initialised at compile time (constant initialisation), so it can't depend on another TU's not-yet-run dynamic initialiser. Unlike constexpr, the object can still be modified later.
What happens if compile-time evaluation of a constexpr hits undefined behaviour?
It's a compilation error. The constant evaluator is not allowed to have UB, so things like signed overflow or out-of-bounds access in a constant-evaluated call are caught at build time.

Basic warm-up

Where can you use a constexpr int that you can't use a const int (initialised from input)?
As an array size, a non-type template argument, a case label, a static_assert operand — anywhere a compile-time constant is required.

Yes, since C++14 (along with local variables, mutation, multiple statements, branches).

Intermediate core

Build a 256-entry compile-time lookup table.
constexpr auto make_table() {
    std::array<uint8_t, 256> t{};
    for (int i = 0; i < 256; ++i) t[i] = popcount(i);
    return t;
}

No static initialiser runs at program startup; the array is baked into the binary.
Why might marking a function constexpr be a compile error even though the body looks fine?
It calls something not usable in constant evaluation (a non-constexpr function, I/O, reinterpret_cast, a throw in C++17), or it can never be evaluated as a constant for any arguments. The compiler diagnoses constexpr functions that have no possible constant-expression instantiation.

Advanced deep

How can C++20 allow std::vector in a constexpr function when heap allocation is runtime?
The constant evaluator has its own model of allocation ("transient allocation"): new/delete during constant evaluation operate on the evaluator's abstract memory, not the real heap. The rule is that any memory allocated during constant evaluation must be freed before that evaluation completes — you can build and manipulate a std::vector inside a constexpr function and return, say, its computed sum or a fixed-size std::array, but you can't have a constexpr variable that still owns heap memory at the end. C++23 relaxes some cases with constexpr-friendly allocators and std::string SSO.
What's the difference between if constexpr, a constexpr if condition, and a normal if with a constexpr condition?
A normal if (constexpr_cond) still compiles both branches and just picks one at runtime (the optimiser may drop the dead one). if constexpr (cond) requires cond to be a constant expression and discards the untaken branch at compile time — it isn't instantiated, so it may contain code that would be ill-formed for the current template type. That discarding behaviour is the whole point in templates; outside templates it's just a guaranteed dead-branch elimination.

What are structured bindings?

The Four Pillars

Everyone can name them. The interview is whether you can distinguish abstraction from encapsulation.

Notes

Abstraction

Exposing what something does, hiding how. You model a problem with the relevant essentials and ignore the rest. A List interface (add, get, size) is an abstraction; whether it's an array or linked nodes is an implementation detail. Achieved with interfaces, abstract classes, and well-named public methods.

Encapsulation

Bundling data with the methods that operate on it, and restricting direct access to the data so the object controls its own invariants. Private fields + public methods, validated setters, no leaking internal references. Abstraction is about the design view; encapsulation is the enforcement mechanism (access control) that protects it.

Inheritance

A new class reuses and extends an existing one (an is-a relationship): Manager is-a Employee. Gives code reuse and a subtype for polymorphism — but tight coupling to the base, so use it only for genuine subtype relationships; otherwise compose.

Polymorphism

"Many forms" — one interface, many implementations. Runtime (a base reference calls a method, the derived override runs) and compile-time (overloading, generics/templates). Lets you write code against the abstraction and drop in new types without changing callers.

The one-liner distinctions

PairDifference
Abstraction vs EncapsulationAbstraction = hide complexity in the design; Encapsulation = hide data behind access control to protect invariants.
Inheritance vs Compositionis-a vs has-a. Inheritance couples to a base; composition delegates to a member.
Overloading vs OverridingSame name different params, resolved at compile time; vs same signature in a subclass, resolved at runtime.
Cheat Sheet
  • Abstraction: model the essentials, hide the mechanism. Interfaces / abstract classes.
  • Encapsulation: data + behaviour together, private state, controlled access, protected invariants.
  • Abstraction = design intent; encapsulation = the access-control enforcement.
  • Inheritance: is-a, reuse + subtype, but tight coupling — use sparingly.
  • Polymorphism: one interface, many types. Runtime (virtual/override) + compile-time (overload/generics).
  • Encapsulation violated by public fields, leaking mutable internals, "getter/setter for everything".
  • Prefer composition + interfaces to deep inheritance trees.
Q&A
Abstraction vs encapsulation in one sentence each?
Abstraction: expose a simple model and hide the complicated implementation. Encapsulation: keep an object's data private and force all access through methods that maintain its invariants.
Is a class with all-public fields and no methods encapsulated?
No. Anyone can put it into an invalid state; there's no invariant protection. It's just a data bag (sometimes fine as a DTO, but not "encapsulated").
Name the two kinds of polymorphism.
Runtime/dynamic (method overriding via a base reference, dispatched by the object's actual type) and compile-time/static (method overloading, generics/templates).
Why is inheritance considered risky?
The subclass depends on the base's implementation details; a base change can silently break subclasses (fragile base class), and you inherit everything whether you want it or not. Composition exposes only what you delegate.
Which pillar does a Java interface most directly express?
Abstraction (a pure contract), and it enables polymorphism. It contributes to encapsulation only indirectly.
Interview Questions

Basic warm-up

List the four pillars.
Abstraction, encapsulation, inheritance, polymorphism.
How is encapsulation implemented in most OOP languages?
Access modifiers (private/protected/public) plus accessor methods, so external code can't touch internal state directly.
Give an everyday example of abstraction.
Driving a car: you use the steering wheel and pedals (interface) without knowing about the engine's combustion cycle (implementation).

Intermediate core

Can you have abstraction without encapsulation, or vice versa?
Yes both ways. A well-named interface backed by a class with public mutable fields is abstract-but-not-encapsulated. A class with private fields and getters/setters exposing every field 1:1 is encapsulated in mechanism but has no real abstraction (it just mirrors its data). Good design needs both.
Why do "getters and setters for every field" undermine encapsulation?
They reproduce direct field access with extra ceremony: callers still manipulate individual pieces of state, and the object no longer owns its invariants (e.g. setStart/setEnd lets a caller create an interval with start > end). Better: expose intent-level operations (moveBy, withEnd) that keep the object consistent.

Advanced deep

Some argue OOP's "four pillars" is a weak framing. What's the critique?
Inheritance is arguably not a fundamental building block but one (often overused) reuse mechanism; the genuinely load-bearing ideas are encapsulation (message-passing, protected invariants) and polymorphism (substitutability). Abstraction isn't OOP-specific at all. Alternative framings emphasise subtype polymorphism + encapsulation as the core, with inheritance demoted, which is why modern guidance is "prefer composition" and why languages like Go and Rust give you polymorphism (interfaces/traits) without implementation inheritance.
How does the Liskov Substitution Principle connect the pillars?
Inheritance creates subtypes; polymorphism relies on being able to use a subtype wherever the base is expected. LSP is the correctness condition for that: a subtype must honour the base's contract (no strengthened preconditions, no weakened postconditions, preserved invariants). If a subclass violates LSP, polymorphic code that was correct against the base breaks — so "inheritance" is only safe when it produces true behavioural subtypes, not just code reuse.

Class vs Object & Access Specifiers

Blueprint vs instance, and who is allowed to touch what.

Notes

Class vs object

A class is a type — a blueprint describing state (fields) and behaviour (methods). An object (instance) is a concrete value of that type occupying memory, with its own copy of the instance fields. Car is a class; myCar and yourCar are objects. this (or self) inside a method refers to the instance it was called on.

Instance vs static members

  • Instance members belong to each object; accessed via a reference.
  • Static (class) members belong to the class itself — one shared copy, accessed via the class name. Used for constants, counters, factory methods, utility functions. Static methods can't use this or instance members directly.

Access specifiers

Q&A
Difference between a class and an object?
A class is the definition/type; an object is a runtime instance of it with its own field values. One class, many objects.
What can a static method not do?
Use this or access instance (non-static) fields/methods directly, because it isn't called on any particular object.
protected vs private?
private: only the class that declares the member. protected: that class plus its subclasses (and same package in Java). protected members are part of the inheritance API and constrain future changes.
When is a static field appropriate?
For state genuinely shared by all instances or by no instance — constants, an instance counter, a cache, configuration. Beware: static mutable state is global state and hurts testability and thread-safety.
What does C++ friend do?
Lets a named external function or class access the private/protected members of the class granting friendship. It's not transitive or inherited.
Interview Questions

Basic warm-up

How many copies of an instance field exist for 100 objects?
100 — one per object. A static field would have just one, shared.
Which access level should fields default to?
private. Expose behaviour through methods, not raw fields.
Can you call a static method without creating an object?
Yes — ClassName.method(). That's the point of static.

Intermediate core

Why is a public static mutable field a design smell?
It's global mutable state: any code anywhere can change it, creating hidden dependencies and order-of-execution bugs; it's not thread-safe without extra work; and tests can't isolate from it. If shared state is truly needed, hide it behind an object with a controlled API, or inject it.
A subclass in another package can't see a protected field of its base in Java in some cases. Explain.
A subclass can access an inherited protected member only through references of its own type (or subtypes), not through a reference of the base type from another package. This prevents one package's subclass from poking at protected state of unrelated instances of the base.

Advanced deep

Is encapsulation about objects or about classes? Consider that in C++/Java one object can access another same-class object's privates.
It's class-level, not instance-level: access control is checked against the type of the code doing the access, not the identity of the object. So Foo::bar(Foo other) { other.privateField; } compiles — useful for copy constructors, equals, comparisons. Languages differ: Ruby and Smalltalk enforce per-object privacy (a private method can only be called on self). The class-level model trades a little theoretical purity for practical implementability of binary operations.
What are the trade-offs of the "nested class can see the outer class's privates" rule?
Nested/inner classes (Java, C++, C#) can access the enclosing class's private members, which is how iterators, builders, and event handlers stay cohesive with their owner without widening visibility for everyone. The cost: the nested type is tightly coupled to the outer's internals, so it must evolve together; and in Java a non-static inner class holds an implicit reference to the outer instance, a classic memory-leak source (e.g. an inner Runnable outliving its Activity). Prefer static nested classes unless you need the outer instance.

Constructors, Destructors & Object Lifecycle

Creation, initialisation, and clean-up — and when each actually happens.

Notes

Kinds of constructor

  • Default — no arguments. Often compiler-generated; suppressed once you declare any other constructor.
  • Parameterised — takes arguments to set initial state.
  • Copy — build a new object from an existing one of the same type (T(const T&)).
  • Move (C++11) — build from an rvalue by stealing its resources.
  • Delegating — one constructor calls another to avoid duplication (this(...) / : T(...)).

Initialisation order

Base class → members (in declaration order) → the constructor body. Destruction is the exact reverse. Assigning members in the body instead of an initialiser list means default-construct-then- overwrite, and can't initialise const/reference members at all.

Destructors / finalisers

  • C++: ~T() runs deterministically at scope exit / delete. Make it virtual in a polymorphic base.
  • Java/C#: no deterministic destructor. finalize() (deprecated) / GC is non-deterministic; use try-with-resources / using + AutoCloseable/IDisposable for cleanup.
  • Python: __del__ runs when the refcount hits zero (usually prompt) but not guaranteed on interpreter exit or in cycles; prefer context managers (with).

The lifecycle

allocate memory  ->  run base + member init  ->  run constructor body
      ...object is alive, methods callable...
run destructor body  ->  destroy members (reverse)  ->  destroy base  ->  free memory
Cheat Sheet
  • Constructors: default, parameterised, copy, move (C++), delegating.
  • Declaring any constructor removes the implicit default one.
  • Init order: base → members (declaration order) → body. Destruction reverses it.
  • Use initialiser lists, not body assignment (needed for const/reference/no-default members).
  • C++ dtor is deterministic; make it virtual for polymorphic bases.
  • Java/C#: no deterministic dtor — use AutoCloseable/IDisposable + try-with-resources/using.
  • Python: __del__ is unreliable for cycles/exit — use with / context managers.
  • Don't call overridable methods from a constructor — the subclass part isn't built yet.
Q&A
Why does declaring a parameterised constructor remove the default one?
The compiler only synthesises a default constructor if you declare no constructors, on the assumption that if you're specifying how to build the object you'll specify the no-arg case too if you want it. Add T() = default; (C++) or an explicit no-arg constructor.
What's a copy constructor for?
Creating a new object as a duplicate of an existing one — invoked on pass-by-value, return-by-value, and explicit copies. For classes owning resources you must define it to deep-copy (or delete it).
Java has no destructors — how do you release a file handle deterministically?
Implement AutoCloseable and use try-with-resources: try (var f = new Resource()) { ... } calls close() automatically at block exit, even on exception.
In what order are members destroyed?
Reverse of construction: constructor body's effects unwind, then members in reverse declaration order, then base classes.
Why avoid calling virtual methods from a constructor?
During the base constructor the object is only a base (the derived part and its overrides aren't set up), so the call resolves to the base version — in Java/C# it dispatches to the override but sees uninitialised subclass fields. Either way it's a bug magnet.
Interview Questions

Basic warm-up

When does a destructor run for a stack object in C++?
When the enclosing scope ends — closing brace, return, or an exception unwinding through it.
What is a delegating constructor?
A constructor that forwards to another constructor of the same class to reuse initialisation logic, e.g. Foo() : Foo(defaultValue) {}.
Does Java guarantee finalize() runs?
No. It may run late, or never (e.g. on JVM exit). It's deprecated. Use explicit close() via AutoCloseable.

Intermediate core

Members declared a, b; constructor initialiser list is : b(compute()), a(b). Bug?
Yes — members initialise in declaration order, so a is built from b before b is initialised. a gets garbage. Reorder declarations or remove the dependency.
Why is deterministic destruction (C++/RAII) often easier to reason about than GC finalisation?
You know exactly when cleanup happens (scope exit), so ordering of releases is predictable and resource lifetimes compose. GC finalisers run at an unknown time on an unknown thread, can resurrect objects, and don't run in a defined order — so non-memory resources (files, sockets, locks) need a separate explicit disposal protocol anyway.

Advanced deep

An exception is thrown from a constructor after some members are initialised. What is destroyed?
Only the sub-objects that were fully constructed — base classes and members initialised before the throw — are destroyed, in reverse order. The object's own destructor does not run because the object never finished construction. If it was heap-allocated with new, the matching operator delete frees the raw storage. This is why RAII members make constructors exception-safe automatically.
How does object construction differ under a language with two-phase init (e.g. some frameworks / Objective-C alloc/init)?
Allocation and initialisation are separate calls, so between them there's a valid-but-uninitialised object. Risks: methods called on a half-initialised instance, init returning a different object than alloc produced (must always use the return value), and forgetting to call init. The single-phase constructor model (C++/Java/C#) avoids the zombie window but forces you to throw for failure. Frameworks that need two-phase (e.g. deserialization, DI) usually add an explicit "is-fully-constructed" contract or a post-construct callback.

Inheritance Types & the Diamond Problem

is-a done right, and why multiple inheritance of state is a minefield.

Notes

Forms of inheritance

FormShape
SingleB : A
MultilevelC : B : A
HierarchicalB : A, C : A
MultipleC : A, B (C++, Python; not Java/C# for classes)
Hybrid / diamondD : B, C where B : A and C : A

The diamond problem

    A
   / \
  B   C
   \ /
    D

If B and C each inherit A, then D has two A subobjects — which A::x does d.x mean? Ambiguous.

  • C++ solution: virtual inheritance — class B : virtual A, class C : virtual A. Now D has a single shared A. Costs an extra indirection and complicates construction (the most-derived class initialises the virtual base).
  • Java/C#: no multiple inheritance of classes. Multiple interfaces are allowed (no state), and default methods can still collide — the compiler forces you to override and disambiguate with Interface.super.method().
  • Python: allows it; resolves via MRO (C3 linearisation), a deterministic order you can inspect with Cls.__mro__.

Guidance

Prefer single inheritance + interfaces + composition. Use multiple inheritance only for mixins that add behaviour without state, or well-understood interface combinations.

Cheat Sheet
  • Inheritance models is-a; if it's really has-a, compose instead.
  • Forms: single, multilevel, hierarchical, multiple, diamond/hybrid.
  • Diamond = two paths to a common base → duplicated base subobject → ambiguity.
  • C++ fix: virtual inheritance → one shared base; most-derived class constructs it.
  • Java/C#: single class inheritance; multiple interfaces OK; default-method clashes must be overridden explicitly.
  • Python: allowed; MRO (C3 linearisation), check __mro__; call up with super().
  • Favour interfaces + composition; reserve MI for stateless mixins.
Q&A
What is the diamond problem?
With multiple inheritance, a class D derived from two classes that share a common base A ends up with two copies of A's members, making references to those members ambiguous.
How does C++ solve it?
Virtual inheritance: B and C inherit A virtually, so D gets a single shared A subobject. The most-derived class is responsible for constructing that virtual base.
Why doesn't Java have the diamond problem for classes?
It forbids multiple class inheritance. Interfaces carry no fields, so there's no duplicated state; if two interfaces provide the same default method, the implementing class must override it and can pick with A.super.m().
What is Python's MRO?
Method Resolution Order — the linear sequence Python searches for attributes/methods, computed by the C3 linearisation algorithm, guaranteeing a consistent, monotonic order for cooperative super() calls.
When is multiple inheritance reasonable?
For orthogonal, stateless mixins (e.g. Comparable + Serializable behaviour), or combining pure interfaces. Avoid it for combining two stateful implementations.
Interview Questions

Basic warm-up

What relationship does inheritance model?
"is-a" — a Dog is an Animal. If the honest phrasing is "has-a", use composition.
Does Java allow a class to extend two classes?
No. One extends, but any number of implements (interfaces).
What keyword gives C++ a single shared base in a diamond?
virtual — class B : virtual public A.

Intermediate core

Two interfaces both declare default void log(). A class implements both. What must it do?
The class won't compile until it overrides log(). Inside, it can delegate to a specific one with InterfaceA.super.log(); or provide its own implementation.
Why does C++ virtual inheritance move base construction to the most-derived class?
So the single shared virtual base is constructed exactly once. If B and C each tried to construct A, it'd be built twice. The most-derived object (D) names the virtual base in its initialiser list; B's and C's attempts to initialise A are ignored when they're not the most-derived.

Advanced deep

Explain how C3 linearisation resolves a non-trivial diamond, and what "monotonicity" guarantees.
C3 produces an ordering of all ancestors such that: a class always precedes its parents; the relative order of parents from a bases list is preserved; and the result is monotonic — the MRO of a subclass is consistent with the MRO of each of its bases (no base's ancestor order is reversed). For D(B, C), B(A), C(A) it yields D, B, C, A: A comes after both B and C, so a cooperative super().__init__() chain visits each class exactly once. If no consistent order exists, Python raises TypeError at class-creation time.
What's the memory/vtable cost of virtual inheritance in C++?
Each object with a virtual base stores a hidden pointer (or offset in the vtable) to locate the shared base subobject, because its position relative to the derived object isn't fixed across the hierarchy. Accessing a virtual base member costs an extra indirection to find it. Casts to/from the virtual base can't be simple pointer adjustments. Construction/destruction is more complex (the most-derived class drives virtual-base init). This is why interfaces (pure virtual, no data) are the recommended way to get multiple supertypes without paying for virtual inheritance of state.

Compile-time vs Runtime Polymorphism

Static binding, dynamic binding, and where the decision is made.

Notes

Compile-time (static) polymorphism

  • Function/operator overloading — the compiler picks an overload from the argument types.
  • Generics / templates — one source, many concrete types generated at compile time.
  • Resolved before the program runs → no runtime cost, fully inlinable.

Runtime (dynamic) polymorphism

  • A call through a base reference/pointer to a virtual/overridable method dispatches to the object's actual type at runtime.
  • Implemented via a per-class table of method pointers (vtable) + a per-object pointer to it.
  • Cost: one indirection, not inlinable across the boundary. Benefit: open extension — new subtypes work with existing code.

Static vs dynamic binding

Animal a = new Dog();
a.speak();     // dynamic: Dog.speak() runs (overridden)
a.legs;        // static: fields/hidden methods use the declared type (Animal)

Overridden methods bind late (by object type); fields, static methods, private methods, and non-virtual methods bind early (by reference type). This is the source of many "why did the base version run?" bugs.

Ad hoc vs parametric vs subtype

KindMechanism
Ad hocOverloading — different code per type combination.
ParametricGenerics/templates — same code, any type.
SubtypeOverriding — a subtype substituted for its supertype.
Cheat Sheet
  • Compile-time: overloading + generics/templates. No runtime cost, inlinable.
  • Runtime: virtual/override dispatch via vtable; one indirection; enables open extension.
  • Overridden methods → late binding (object's dynamic type). Fields, static/private/non-virtual → early binding (reference's static type).
  • Java methods are virtual by default; C++/C# need virtual.
  • Three flavours: ad hoc (overload), parametric (generics), subtype (override).
  • Downcast safely with dynamic_cast/instanceof/is; overuse signals a missing virtual method.
Q&A
Overloading vs overriding — which is which kind of polymorphism?
Overloading is compile-time (ad hoc) polymorphism — the compiler chooses by static argument types. Overriding is runtime (subtype) polymorphism — the running object's type chooses.
Given Base b = new Derived();, does b.field use Base's or Derived's field?
Base's. Field access is not polymorphic — it's resolved by the static type of the reference. Only overridden method calls dispatch dynamically.
How is runtime polymorphism implemented?
Each polymorphic class has a vtable (array of function pointers to its versions of the virtual methods); each object stores a pointer to its class's vtable; a virtual call reads that pointer and jumps through the right slot.
Is template/generic code polymorphic?
Yes — parametric polymorphism. The same written code works for many types, with the concrete versions produced at compile time (C++ instantiation) or via type erasure (Java generics).
Why can excessive instanceof/dynamic_cast be a smell?
It often means behaviour that should be a polymorphic method has leaked into callers as a type switch. Move the behaviour into the classes and call it virtually.
Interview Questions

Basic warm-up

Which is resolved at compile time: overloading or overriding?
Overloading. Overriding is resolved at runtime by the object's actual type.
What data structure backs runtime method dispatch?
A virtual method table (vtable) per class, plus a vtable pointer per object.
Are C++ member functions polymorphic by default?
No — you must mark them virtual. Java methods are virtual unless final/static/private.

Intermediate core

Explain the output: a base-class method calls this.helper(); a subclass overrides helper(). Which runs when you call the base method on a subclass instance?
The subclass's helper(). The call dispatches on the dynamic type of this, which is the subclass. This "template method" behaviour is intentional — but it also means a base method can call into not-yet-initialised subclass state if invoked from a constructor.
Why is field access not polymorphic, and what bug does that cause?
Fields are bound by the reference's declared type for performance and predictability (no vtable for data). Bug: shadowing a base field with a same-named subclass field means ((Base)obj).x and ((Sub)obj).x see different values on the same object. Don't shadow fields; use accessor methods if you need overridable data.

Advanced deep

Compare the trade-offs of subtype polymorphism (virtual) vs parametric polymorphism (templates/generics) for a container library.
Virtual: one compiled implementation, heterogeneous storage (List<Shape> holding any Shape), runtime extensibility — but an indirection per operation, no inlining, and elements must be reference types (boxing in Java). Templates/C++ generics: monomorphised per type, fully inlined, value semantics, no boxing — but code bloat (one instantiation each), slower compiles, worse error messages pre-concepts, and no single binary that works for types unknown at build time. Java erased generics sit in between: no bloat, but type info lost at runtime and everything is a reference. The STL chose templates for zero-overhead value semantics; GUI frameworks choose virtual for open extension.
How does double dispatch / the visitor pattern get around single dispatch?
Most OO languages dispatch on one receiver only. When behaviour depends on two runtime types (e.g. collide(Asteroid, Ship) vs collide(Ship, Ship)), you chain two virtual calls: a.accept(v) dispatches on a's type and calls v.visit(this), which dispatches on v's type — the pair of dynamic dispatches selects the right combination. Cost: every element type needs an accept, and adding a new element type forces changes to every visitor (the visitor pattern trades "easy to add operations" for "hard to add types").

Overloading vs Overriding vs Hiding

Three similar-looking things with completely different resolution rules.

Notes

Overloading

Same method name, different parameter list (count or types), in the same scope. Chosen at compile time by the static types of the arguments. Return type alone can't distinguish overloads.

Overriding

A subclass provides a new body for an inherited virtual method with the same signature. Chosen at runtime by the object's actual type. Rules: same name and parameters; return type must be the same or covariant (a subtype); access can't be narrower; can't throw broader checked exceptions (Java); mark with override / @Override.

Hiding (shadowing)

A subclass declares a member with the same name as a non-virtual base member (or a static method, or a field). It doesn't override — it hides. Which one you get depends on the reference's static type. Almost always a mistake.

struct A { void f() { puts("A"); } };          // not virtual
struct B : A { void f() { puts("B"); } };      // hides A::f
B b; A& a = b;
a.f();   // "A"  -- static type wins, no dynamic dispatch
b.f();   // "B"

Cheat Sheet
  • Overload = same name, different params, same class, compile-time pick.
  • Override = same signature, subclass, base method virtual/overridable, runtime pick.
  • Hide = same name over a non-virtual/static/field base member → resolved by reference type. Avoid.
  • Return type alone can't overload; covariant returns are allowed on override.

Q&A
Can two methods differing only in return type be overloads?
No. The parameter list must differ. (Covariant return types are only relevant when overriding.)
What is a covariant return type?
An override may return a subtype of what the base method returns — e.g. base Animal clone(), override Dog clone(). Callers using the base type still see Animal; callers with the derived type get the narrower type.
What's the difference between overriding and hiding in C++?
Overriding requires the base method to be virtual; the call dispatches on the object's dynamic type. If it's not virtual, a same-signature method in the derived class merely hides the base one, and calls resolve by the pointer/reference's static type.
Why annotate every override?
If your signature doesn't actually match (wrong parameter type, missing const), @Override/override turns a silent "you created a new unrelated method" into a compile error.
Are static methods overridden?
No — they're hidden. A static method call is bound at compile time to the class named (or the reference's type), not dispatched on an instance.
Interview Questions

Basic warm-up

Two methods area(int) and area(double) in one class — what is that?
Overloading — same name, different parameter types, resolved at compile time by the argument type.
What must match for an override?
Method name and parameter list; return type same or covariant; access not narrower; the base method must be overridable (virtual / non-final).
Does overriding happen at compile time or runtime?
Runtime — the JVM/CLR/vtable picks the implementation based on the object's actual class.

Intermediate core

In C++, base void f() (non-virtual), derived void f(). Base* p = new Derived; p->f(); — which runs, and how do you fix it?
Base::f runs — it's hiding, not overriding, and the call binds to the static type. Fix: declare virtual void f(); in Base and void f() override; in Derived.
Java: overriding a method, you widen a thrown checked exception from IOException to Exception. Result?
Compile error. An override may throw the same or narrower checked exceptions, or none — never broader — because callers coded against the base signature only handle what the base declared.

Advanced deep

Overload resolution with implicit conversions can pick a "surprising" overload. Give an example and the principle.
f(long) and f(const std::string&); call f(0) or f("x") — f(0) matches long via integral conversion, but f(NULL) (defined as 0) also picks f(long), not the pointer overload people expect. Principle: the compiler ranks candidates by conversion sequence quality (exact > promotion > standard conversion > user-defined), and picks the best; ambiguity is an error. Adding a seemingly-unrelated overload can change which one an existing call binds to. nullptr, explicit, and named functions instead of overloads reduce these traps.
Why does adding an override in a subclass sometimes "hide" the base class's overloads of the same name?
In C++ (and similarly Java for a different reason), declaring any member function named f in the derived class hides all base f overloads for unqualified lookup — name lookup stops at the first scope that has the name. So Base with f(int) and f(double), and Derived overriding only f(int), makes d.f(3.14) fail or narrow to int. Fix: bring them in with using Base::f; in the derived class, then override the ones you need.

Abstract Classes & Interfaces

Two ways to say "implement this" — and when each is the right tool.

Notes

Abstract class

  • Can't be instantiated; may hold state, constructors, concrete methods, and abstract (unimplemented) methods.
  • Expresses an is-a with shared implementation. A subclass gets one abstract base.
  • Use for a partial implementation / template-method skeleton where subclasses fill in specifics.

Interface

  • A pure contract: method signatures, constants; historically no state or bodies.
  • A class can implement many interfaces — the way to get multiple supertypes without MI of state.
  • Modern languages blur the line: Java 8+ default methods, C# 8+ default interface members, so interfaces can carry behaviour — but still no instance fields.

Choosing

Want to…Use
share code + fields among related typesabstract class
define a capability many unrelated types can haveinterface
allow a type to have several of these rolesinterfaces (multiple)
evolve the contract later without breaking implementersinterface + default methods (carefully)

Rule of thumb: program to interfaces for the public API; use an abstract base internally if there's real shared implementation.

C++ note

C++ has no interface keyword — an interface is just an abstract class with only pure virtual functions and no data members (= 0 on every method, virtual destructor).

Cheat Sheet
  • Abstract class: no instances, can have state + constructors + concrete + abstract methods; single inheritance.
  • Interface: contract only (+ constants, + default methods in modern langs); no instance state; implement many.
  • Abstract class = "is-a + shared code". Interface = "can-do capability".
  • Need multiple supertypes → interfaces.
  • Program to interfaces in public APIs; abstract base for internal code reuse.
  • C++ "interface" = abstract class, all methods pure virtual, virtual dtor, no data.
  • Adding a method to an interface breaks implementers unless it has a default.
Q&A
Key difference between an abstract class and an interface?
An abstract class can hold state and concrete implementation and you can only extend one; an interface is (primarily) a contract with no instance state and a class can implement many.
When would you pick an abstract class?
When several closely-related subtypes share fields and method implementations, and you want to provide a skeleton with a few "fill in the blank" abstract methods (template method pattern).
Can an interface have method bodies now?
Yes — Java default methods (8+) and C# default interface members (8+). Still no instance fields, so no per-object state.
How do you model an interface in C++?
An abstract class with only pure virtual functions (= 0), no data members, and a virtual (or protected) destructor.
What's the cost of adding a method to a published interface?
Every existing implementer breaks (must implement it) unless the language lets you provide a default body. This is why interfaces should be small and stable.
Interview Questions

Basic warm-up

Can you instantiate an abstract class?
No. You instantiate a concrete subclass that implements all its abstract methods.
How many interfaces can a class implement?
Any number.
What makes a C++ class abstract?
Having at least one pure virtual function (virtual void f() = 0;).

Intermediate core

You have Bird and Airplane. Both can fly() but share no ancestry. Model it.
An interface Flyable { void fly(); } that both implement. An abstract class would force an artificial common base. Interfaces express orthogonal capabilities across unrelated hierarchies.
When do default interface methods cause trouble?
Diamond-style conflicts (two interfaces provide the same default → implementer must override and disambiguate), and API evolution surprises (a new default silently changes behaviour of existing implementers that had their own method resolved differently). They also tempt you to put logic in interfaces that really wants state, which they can't hold.

Advanced deep

Java added default methods primarily for one reason. What was it, and what did it cost?
To let java.util.Collection etc. gain methods like stream(), forEach(), removeIf() in Java 8 without breaking the millions of existing classes implementing those interfaces. The cost: interfaces are no longer pure contracts, resolution rules got more complex (class wins over interface; more-specific interface wins; otherwise you must override), and "interface vs abstract class" is now a fuzzier decision. It was a pragmatic backward-compatibility trade, not a design ideal.
Discuss "interface segregation" as it applies to designing an abstract base with many methods.
A fat abstract class (or interface) forces every subclass to deal with methods it doesn't need — often by throwing UnsupportedOperationException (an LSP violation) or writing empty overrides. Splitting into small role interfaces (Readable, Writable, Seekable) lets each type implement exactly what it supports, callers depend only on what they use, and you avoid the "read-only view still has write()" problem. The cost is more types and sometimes an adapter to combine them.

Composition over inheritance

  • Inheritance is compile-time, fixed, exposes the whole base API, and couples you to base internals (fragile base class).
  • Composition delegates to a member; you expose only what you choose, can swap the member (even at runtime via an interface), and stay decoupled.
  • Use inheritance only for genuine, stable is-a subtype relationships you'll use polymorphically. Otherwise hold the other object and delegate.

Delegation

class Stack {
    std::vector<int> data_;                 // composition, not "class Stack : vector"
public:
    void push(int x) { data_.push_back(x); } // expose only stack operations
    void pop()        { data_.pop_back(); }
};

Deriving Stack from vector would leak insert, operator[], iterators — letting callers violate stack semantics.

Cheat Sheet
  • Association: "uses". Aggregation: "has, shared, independent lifetime" (hollow diamond). Composition: "owns, exclusive, shared lifetime" (filled diamond).
  • Composition ⇒ the whole constructs and destroys the part; no external references to it.
  • Aggregation ⇒ part is passed in, may be shared, outlives/precedes the whole.
  • Favour composition + delegation over inheritance for code reuse.
  • Inheritance couples to base internals, is fixed at compile time, exposes the full base API.
  • Composition + an interface member = swappable behaviour at runtime (Strategy).
  • Only inherit for real, stable is-a used polymorphically.
Q&A
Aggregation vs composition?
Both are "has-a". Composition is exclusive ownership with a shared lifetime — destroy the whole, the part goes too (a house and its rooms). Aggregation is a looser "has", where the part can be shared and outlives or precedes the whole (a playlist and its songs).
Why "favour composition over inheritance"?
Composition gives looser coupling (you depend on a small interface, not a base class's internals), runtime flexibility (swap the component), and a controlled surface (expose only what you delegate). Inheritance is rigid and drags in the whole base contract.
Give a classic misuse of inheritance.
Deriving Stack from ArrayList/vector (Java's java.util.Stack did this) — now callers can add(index, e) or index arbitrarily, breaking LIFO semantics. Should be composition + delegation.
How does composition enable the Strategy pattern?
The class holds a reference to an interface (Comparator, CompressionAlgorithm) and delegates to it; you inject different implementations, even swapping them at runtime, without subclassing.
Is "association" a code construct?
It's the weakest UML relationship — usually just one object holding a reference to, or receiving as a parameter, another. No ownership implied.
Interview Questions

Basic warm-up

Car and Engine — composition or aggregation?
Composition — the engine is created with and destroyed with the car (in a typical model). University–Department is composition; Department–Professor is aggregation.
What does "has-a" indicate?
An association/aggregation/composition relationship — one object contains or refers to another — as opposed to "is-a" (inheritance).
Name one advantage of composition over inheritance.
You can change the composed object (or swap its implementation via an interface) without touching the containing class, and you only expose the operations you choose to delegate.

Intermediate core

Refactor class LoggingList extends ArrayList (which overrides add to log) to composition. Why is the inheritance version buggy?
addAll() in ArrayList calls add() internally on some JDKs, so overriding both double-logs (self-use dependency). Composition: class LoggingList { private final List<T> inner; void add(T x){ log(x); inner.add(x); } ... } — you control exactly which calls log, with no reliance on the base's internal call graph.
When is inheritance genuinely the right call over composition?
When there's a true subtype relationship you exploit polymorphically (client code holds Shape and calls area() on any subtype), the base is designed and documented for extension, and the "is-a" holds for the whole base contract (LSP). Framework hook classes, sealed hierarchies of variants, and ADT-like designs fit.

Advanced deep

Composition has a cost too. What are the downsides versus inheritance?
Boilerplate: forwarding methods for everything you want to expose (mitigated by language features — Kotlin by delegation, C++ private inheritance, Lombok @Delegate). An extra indirection and object. You lose automatic polymorphic substitutability — the wrapper isn't a subtype of what it wraps unless it also implements a shared interface. And "flat" delegation can obscure a genuine type hierarchy that would communicate intent better. The guidance is "favour", not "always".
How do mixins / traits sit between inheritance and composition?
A mixin/trait bundles behaviour (and sometimes requires certain abstract members) that gets mixed into a class — giving reuse like inheritance but composably, without a single rigid base chain. Scala traits, Rust trait default methods, Ruby modules, and Python cooperative multiple inheritance all do this. They avoid the "one base class" limit and the fragile deep hierarchy, but reintroduce resolution-order questions (which trait's method wins) and can still create implicit coupling if a trait assumes state it doesn't own.

SOLID, Coupling & Cohesion

Five principles for classes that stay changeable, plus the two metrics they optimise.

Notes

SOLID

Coupling & cohesion

  • Coupling — how much one module depends on another's internals. Low is good: change one thing without a ripple. Reduce it with interfaces, DI, events, small APIs.
  • Cohesion — how focused a module is on one job. High is good: everything in the class relates to its single purpose. Low cohesion = "utils grab-bag".
  • Goal: high cohesion, low coupling.

Law of Demeter

"Only talk to your immediate friends." Avoid a.getB().getC().doThing() (train wrecks) — it couples you to a's whole object graph. Ask a to do the thing, or pass C in.

DRY / KISS / YAGNI

Don't Repeat Yourself (one source of truth per piece of knowledge — but don't over-abstract coincidental duplication); Keep It Simple; You Aren't Gonna Need It (don't build for speculative requirements).

Cheat Sheet
  • SRP: one reason to change. OCP: extend, don't modify. LSP: subtypes honour the base contract. ISP: small focused interfaces. DIP: depend on abstractions, inject concretions.
  • Aim for high cohesion (class does one thing) + low coupling (few, abstract dependencies).
  • Coupling reducers: interfaces, dependency injection, events/pub-sub, facades, small APIs.
  • Law of Demeter: don't chain through objects you were handed; tell, don't ask.
  • DRY = single source of truth (not "delete all similar-looking code").
  • KISS, YAGNI — simplest thing that works; don't pre-build for maybe-futures.
  • Symptoms of violation: shotgun surgery (SRP), if type == ladders (OCP), throw NotSupported in overrides (LSP/ISP), new ConcreteThing() deep in business logic (DIP).
Q&A
State the Single Responsibility Principle precisely.
A module should have exactly one reason to change — it should be responsible to a single actor/stakeholder. If billing rules and report layout both live in one class, two different teams' changes collide there.
What does the Open/Closed Principle ask you to do when a new payment type appears?
Add a new class implementing the payment interface, not edit a switch in existing, tested code. The system is "closed" to modification of what works, "open" to extension by new types.
Give a Liskov violation.
The classic: Square extends Rectangle, but setWidth on a Square also changes height, breaking code that assumes setWidth(5); setHeight(4); assert area()==20 for any Rectangle. Or a ReadOnlyList subtype whose add() throws.
Coupling vs cohesion — which do you want high?
High cohesion (a class's parts all serve one purpose), low coupling (minimal, abstract dependencies between classes).
What's a "train wreck" and which principle addresses it?
order.getCustomer().getAddress().getCity() — a chain that couples you to the internal structure of several objects. The Law of Demeter says depend only on direct collaborators; add order.shippingCity() instead.
Interview Questions

Basic warm-up

What does the D in SOLID stand for and mean?
Dependency Inversion: high-level modules and low-level modules should both depend on abstractions (interfaces), not on each other's concrete classes; concrete implementations are injected.
You want high ___ and low ___.
High cohesion, low coupling.
What does YAGNI advise?
Don't implement functionality until it's actually needed — speculative generality adds cost and rarely fits the real future requirement.

Intermediate core

A Report class reads from the DB, computes totals, and renders HTML. Which principle is violated and how do you fix it?
SRP — three reasons to change (schema, business rules, presentation). Split into ReportRepository (data), ReportCalculator (rules), ReportRenderer (HTML), coordinated by a thin service. Now a layout change doesn't risk the query logic.
How does Dependency Injection support the Open/Closed Principle?
The class receives its collaborators through an interface (constructor/parameter), so you extend behaviour by passing a different implementation — no edit to the class. Combined with a DI container or factory, new strategies/adapters plug in via configuration rather than code changes to consumers.

Advanced deep

SOLID is sometimes criticised as leading to over-engineering. What's the balanced view?
Each principle is a response to a real pain (ripple changes, edit-to-extend, broken substitutability), but applied dogmatically they explode class counts, add indirection that obscures flow, and create interfaces with one implementation "for testing". The pragmatic reading: apply them where change is actually happening or expected. A stable, simple class doesn't need five collaborator interfaces. Refactor toward SOLID when a second reason to change appears (rule of three), not pre-emptively. "Make it work, make it right, make it fast" — SOLID is mostly about the "right" step, driven by evidence.
Explain the LSP conditions (preconditions, postconditions, invariants, history) with an example each.
Preconditions can't be strengthened: base withdraw(amount) accepts any positive amount; a subtype that rejects amounts over 100 breaks callers. Postconditions can't be weakened: base guarantees the list is sorted after insert; a subtype that sometimes doesn't sort breaks readers. Invariants preserved: base keeps balance >= 0; subtype must too. History constraint: base is immutable after construction; a "mutable subtype" lets state change in ways base clients never expect (this is why MutablePoint extends Point is a trap). Violating any means polymorphic code correct against the base can fail on the subtype.

Q&A
Strategy vs Template Method?
Both vary an algorithm. Strategy uses composition — the varying part is a separate object you plug in (and can swap at runtime). Template Method uses inheritance — the base defines the skeleton, subclasses override the hook steps (fixed at compile time).
Adapter vs Decorator?
Adapter changes an object's interface to match what a client needs. Decorator keeps the same interface but adds behaviour by wrapping. Adapter is about compatibility; Decorator is about layered features.
Why is Singleton often called an anti-pattern?
It's global mutable state with hidden coupling: any code can reach it, tests can't isolate from it, lifecycle is unclear, and thread-safety needs care. Usually better to create one instance at the composition root and inject it.
What problem does Observer solve and what's its main hazard?
Decoupled one-to-many change notification. Hazards: memory leaks if observers don't unsubscribe (listener lapsing), unclear/ cyclic update ordering, and cascades of updates. Modern reactive libraries address these.
When is a Builder worth it?
When an object has many optional parameters, needs step-wise construction with validation at the end, or you want an immutable result without a huge constructor. For a couple of fields, don't bother.

Basic warm-up

Which pattern gives swappable algorithms behind a common interface?
Strategy.
Which pattern wraps an object to add behaviour while keeping its interface?
Decorator (e.g. BufferedInputStream wrapping a FileInputStream).

A single, simplified interface to a larger, more complex subsystem.

Intermediate core

Or just an enum singleton. (Still consider whether you want a singleton at all.)

Advanced deep

"Patterns are a sign of missing language features." Discuss with examples.
Peter Norvig's observation: in languages with first-class functions, Strategy/Command/Observer/Template-Method largely vanish — you pass a function, store a closure, keep a list of callbacks. Iterator is built into for-each/generators. Singleton is a module in Python/JS. The GoF patterns were partly workarounds for C++/Java circa 1994 lacking closures, mixins, and reflection. What remains genuinely useful is the shared vocabulary ("this is a Decorator") and the patterns that address structural problems functions don't (Composite, Visitor for double dispatch, Facade). So: know them for communication and for the cases they still solve, but don't scaffold a class hierarchy where a lambda suffices.
Compare the State pattern with a plain enum + switch state machine.
Enum + switch: all transitions visible in one place, trivial to serialize the state (it's just a value), low ceremony — but the switch grows with every event×state combination and each state's behaviour is scattered across many switches. State pattern: one class per state, each encapsulating that state's behaviour and its outgoing transitions; adding a state is a new class (Open/Closed), and behaviour is cohesive — but more classes, the "current state" is now an object (serialization needs mapping), and shared data must be passed to each state. Rule: few states / simple logic → enum+switch; many states with rich per-state behaviour → State pattern (or a table-driven FSM).

Complexity Analysis & Big-O

The language for "how does this scale" — and the traps (amortised, average, hidden constants).

Notes

The notations

  • O(f) — upper bound (grows no faster than f).
  • Ω(f) — lower bound. Θ(f) — tight bound (both).
  • We drop constants and lower-order terms: 3n² + 5n + 9 is O(n²).
  • Big-O describes asymptotic behaviour — for small n, constants can dominate (which is why std::sort switches to insertion sort for tiny ranges).

The common growth rates

ClassNameExample
O(1)constantarray index, hash lookup (avg), stack push
O(log n)logarithmicbinary search, balanced-tree op
O(n)linearscan, single loop
O(n log n)linearithmicmerge/quick/heap sort, building a heap of sorted output
O(n²)quadraticnested loop, bubble/insertion sort
O(2ⁿ), O(n!)exponential / factorialsubsets, permutations, naive TSP

Best / average / worst

Quicksort: O(n log n) average, O(n²) worst (bad pivots). Hash lookup: O(1) average, O(n) worst (all collisions). Always know which case an interviewer means — and whether the worst case is adversarially triggerable.

Amortised analysis

vector::push_back is O(n) on the occasional reallocation, but O(1) amortised: over n pushes the total work is O(n) because capacity doubles, so the expensive copies happen rarely and geometrically. Amortised O(1) ≠ worst-case O(1) — matters for real-time systems.

Space complexity

Count extra memory beyond the input: recursion stack depth (O(log n) for balanced recursion, O(n) for a bad quicksort), auxiliary arrays (merge sort O(n)), or O(1) "in-place".

Cheat Sheet
  • O = upper, Ω = lower, Θ = tight. Drop constants and lower terms.
  • Growth order: 1 < log n < n < n log n < n² < n³ < 2ⁿ < n!.
  • Nested loop over n → O(n²); halving each step → O(log n); loop with a doubling index → O(log n).
  • Recursion cost = (number of calls) × (work per call); use the recursion tree or Master Theorem.
  • Amortised = average over a sequence of ops (dynamic array push = O(1) amortised, O(n) worst single).
  • Average case often assumes random input; worst case may be attacker-controlled (hash flooding, quicksort pivots).
  • Space: input excluded; count aux arrays + recursion depth. "In-place" = O(1) extra.
  • Log base is irrelevant in O() (differ by a constant), but matters for exact counts.
Q&A
Difference between O and Θ?
O(f) is an upper bound — the algorithm is no worse than f asymptotically. Θ(f) is a tight bound — it grows exactly like f (both O and Ω). Saying merge sort is O(n²) is technically true but weak; Θ(n log n) is precise.
Why is dynamic-array append O(1) amortised but not worst-case O(1)?
Most appends just write to a free slot (O(1)), but when capacity is exhausted it allocates a bigger buffer and copies everything (O(n)). Because capacity grows geometrically (usually ×2), those copies happen rarely enough that the total over n appends is O(n), i.e. O(1) each on average.
What's the time complexity of a loop that does i *= 2 until i > n?
O(log n) — i takes values 1, 2, 4, …, n, which is about log₂(n) iterations.
Does O(1) mean "fast"?
No — it means "independent of input size". An O(1) operation with a huge constant (e.g. a fixed 10,000-iteration setup) can be slower than an O(n) one for realistic n. Big-O is about scaling, not absolute speed.
What's the space complexity of recursive merge sort?
O(n) — the merge step needs an auxiliary array of size n. The recursion stack adds O(log n), which is dominated by the O(n) buffer.
Interview Questions

Basic warm-up

What is the time complexity of binary search?
O(log n) — each comparison halves the remaining search space.
Simplify O(2n² + 100n + 7).
O(n²). Constants and lower-order terms drop.
Two nested loops each from 0 to n — complexity?
O(n²).

Intermediate core

What's the complexity of for i in 0..n: for j in i..n:?
Still O(n²). The inner loop runs n, n-1, …, 1 times; the sum is n(n+1)/2 ≈ n²/2, which is Θ(n²).
Give the recurrence and solution for merge sort.
T(n) = 2·T(n/2) + Θ(n). By the Master Theorem (a=2, b=2, f(n)=n, n^(log_b a)=n) it's case 2 → Θ(n log n).
An algorithm is O(n) time but O(n) space; another is O(n log n) time, O(1) space. Which to prefer?
It depends on constraints. If memory is tight or n is huge (won't fit), the O(1)-space one wins despite the log factor. If speed dominates and memory is ample, the linear-time one wins. Interviewers usually want you to state the trade-off, not pick blindly.

Advanced deep

Explain amortised analysis via the accounting (banker's) method for dynamic array push.
Charge each push 3 units: 1 to insert the element, and 2 saved as "credit" on that element. When the array is full (say k elements) and doubles, you must copy k elements — but the k/2 elements added since the last resize each carry 2 credits = k units saved, exactly paying for the k copies. So every operation costs O(1) amortised even though individual resizes are O(n). The potential method formalises this with Φ = 2·(size) − capacity.
Why can average-case complexity be misleading for security-sensitive code?
Average case assumes a benign input distribution. An attacker who controls inputs can force the worst case every time: crafted keys that all collide turn a hash map's O(1) into O(n) (hash-flooding DoS); adversarial arrays make naive quicksort O(n²); pathological regexes cause exponential backtracking (ReDoS). Mitigations: randomised/seeded hashing, introsort (quicksort that falls back to heapsort), non-backtracking regex engines — i.e. pick structures with acceptable worst-case bounds for untrusted input.

Static & dynamic arrays

  • Contiguous memory; O(1) index by address arithmetic; excellent cache locality and prefetching.
  • Insert/delete in the middle is O(n) (shift elements). Append is O(1) amortised for a dynamic array (geometric growth); prepend is O(n).
  • Dynamic array (vector, ArrayList, Python list): keeps size and capacity; grows by ~1.5–2× when full.

Cheat Sheet

Q&A
Why is array indexing O(1)?
Elements are contiguous and equal-sized, so address = base + i × elementSize — one multiply-add, no traversal.
When does a linked list actually beat a dynamic array?
When you do many insertions/deletions in the middle and already hold iterators/nodes to those positions (so no O(n) search), or you need element addresses to stay stable across edits, or you splice whole sublists between lists in O(1).
What's the cost of push_front on a std::vector?
O(n) — every existing element shifts up one slot. Use std::deque for O(1) front insertion.
How do you find the middle of a singly linked list in one pass?
Two pointers: advance slow by 1 and fast by 2 each step; when fast reaches the end, slow is at the middle.
Why are linked lists slow in practice despite good asymptotic insert?
Each node is a separate allocation scattered in memory, so traversal is a chain of cache misses; and you usually pay O(n) to find the insertion point anyway. Arrays' contiguous layout and hardware prefetching win for typical sizes.
Interview Questions

Basic warm-up

Time to access the k-th element of a singly linked list?
O(k) — you must walk from the head. O(n) in the worst case.
What two fields does a dynamic array track?
size (elements in use) and capacity (slots allocated).
Which list type lets you delete a node in O(1) given a pointer to it?
Doubly linked list (you have both neighbours to relink). In a singly linked list you'd need the previous node.

Intermediate core

Detect whether a linked list has a cycle, O(1) space.
Floyd's tortoise and hare: move slow one step and fast two steps per iteration. If fast (or fast.next) becomes null, no cycle. If slow == fast at some point, there is a cycle. To find the start, reset one pointer to the head and advance both by 1 until they meet again.
Reverse a singly linked list in place.
prev = null; curr = head
while curr:
    nxt = curr.next
    curr.next = prev
    prev = curr
    curr = nxt
head = prev
O(n) time, O(1) space.
You need frequent random access and frequent middle insertion. What structure?
Neither array nor list is great. Options: a balanced BST / order-statistics tree (O(log n) both), a skip list, a gap buffer or rope (for text), or a "tiered" / unrolled linked list. If insertions cluster, a std::deque or segmented array can be enough.

Advanced deep

Why might std::list be slower than std::vector even for a workload with many middle insertions?
Finding the insertion point in a list is O(n) pointer-chasing through cache-cold nodes; the vector's O(n) shift is a single memmove over contiguous, prefetched memory that the CPU does at near-bandwidth speed. Unless you already hold the iterator (from a prior traversal) and the elements are large, the vector's constant factor is small enough that it wins up to surprisingly large n. Benchmarks (Stroustrup's) show vector beating list for insert-sorted workloads into the thousands of elements.
What is an unrolled linked list and what does it optimise?
Each node holds a small array of elements (say 16–64) plus the next pointer. This amortises the per-element pointer/allocation overhead, restores some cache locality (a whole block is contiguous), and keeps O(1)-ish splicing at block granularity. Trade-offs: partially-full blocks waste space, and insert/delete within a block still shifts up to blockSize elements. Used in some database and editor buffer implementations; the CPU-cache-aware middle ground between array and list.

Stacks & Queues

LIFO and FIFO — simple structures that power parsing, scheduling, and traversal.

Notes

Stack (LIFO)

  • push, pop, peek/top, isEmpty — all O(1).
  • Implement on a dynamic array (push/pop at the back) or a singly linked list (push/pop at the head).
  • Uses: function call stack, expression evaluation & balanced-parens, DFS, undo, backtracking, "next greater element" (monotonic stack).

Queue (FIFO)

  • enqueue (back), dequeue (front), front, isEmpty — O(1).
  • Array implementation: use a circular buffer (head/tail indices mod capacity) so dequeue isn't O(n). Linked list: keep head + tail pointers.
  • Uses: BFS, task/job scheduling, producer–consumer buffers, rate limiting, streaming.

Cheat Sheet
  • Stack = LIFO: push/pop/peek O(1). Array back, or linked-list head.
  • Queue = FIFO: enqueue back / dequeue front O(1). Use a circular buffer for the array version.
  • Deque = both ends O(1); is a superset of stack + queue.
  • Ring buffer: fixed capacity, no alloc, head/tail mod N, overwrite-or-block when full.
  • Priority queue: pop by priority, heap-backed, O(log n).
  • Stack uses: DFS, parsing, balanced brackets, undo, call frames, monotonic-stack range problems.
  • Queue uses: BFS, scheduling, buffering, level-order traversal.
  • Queue from two stacks: amortised O(1); stack from two queues: O(n) on one side.
Q&A
Why use a circular buffer for an array-backed queue?
So dequeue is O(1). A naive array queue that removes from index 0 must shift every element down (O(n)); a circular buffer just advances a head index modulo capacity.
Which traversal uses a stack and which uses a queue?
DFS uses a stack (explicit, or the call stack via recursion); BFS uses a queue (process level by level).
What is a monotonic stack good for?
Problems asking "next/previous greater (or smaller) element", largest rectangle in a histogram, sliding-window maximum — it maintains a stack whose values are monotonic, popping dominated elements, giving overall O(n).
How do you implement a queue with two stacks?
An inStack for pushes and an outStack for pops. On dequeue, if outStack is empty, pop everything from inStack into outStack (which reverses it), then pop from outStack. Each element is moved at most once → amortised O(1).
What does a priority queue change about "queue" semantics?
It dequeues the highest-priority element rather than the earliest-inserted one. It's not FIFO; it's backed by a heap and costs O(log n) per push/pop.
Interview Questions

Basic warm-up

What does LIFO stand for and which structure is it?
Last-In-First-Out — a stack.
Which structure would you use to check balanced parentheses?
A stack: push opening brackets, pop and match on closing brackets; balanced iff the stack is empty at the end and never mismatches.
Enqueue and dequeue happen at the same end or different ends?
Different ends — enqueue at the back, dequeue from the front.

Intermediate core

Design a fixed-size ring buffer. How do you tell "full" from "empty" when head == tail?
Two common fixes: (a) keep an explicit count; full when count == capacity, empty when count == 0. (b) Leave one slot unused: full when (tail + 1) % cap == head, so head == tail always means empty. (a) uses the whole buffer; (b) avoids a separate counter.
Sliding-window maximum over an array, O(n). Sketch it.
Use a deque of indices whose values are decreasing. For each i: pop from the back while the back's value ≤ a[i]; push i; pop from the front if it's outside the window (≤ i - k); the front index's value is the window max. Each index is pushed and popped once → O(n).

Advanced deep

How would you build a lock-free single-producer/single-consumer queue?
A ring buffer with an atomic head (consumer) and atomic tail (producer). The producer writes the element then does a release store to tail; the consumer does an acquire load of tail before reading. Because there's exactly one writer per index, no CAS is needed — just the acquire/release fence pair to publish the data before the index. Pad head and tail onto separate cache lines to avoid false sharing. Multi-producer or multi-consumer needs CAS loops and is much harder to get right.
Prove the two-stack queue is amortised O(1) using the potential method.
Let Φ = size of inStack. push: real cost 1, ΔΦ = +1 → amortised 2. dequeue when outStack non-empty: real cost 1, ΔΦ = 0 → amortised 1. dequeue that transfers k elements: real cost k (moves) + 1 (pop), ΔΦ = −k → amortised (k + 1) − k = 1. Every operation is amortised ≤ 2 = O(1), even though a single transfer is O(k).

Hash Tables & Collision Handling

O(1) average lookup — and everything that has to go right for that to hold.

Notes

The idea

Map a key to a bucket index with hash(key) % capacity. Good average-case O(1) for insert/find/delete, at the cost of no ordering and a worst case of O(n).

A good hash function

  • Deterministic, fast, and spreads keys uniformly across buckets (avalanche: one input bit flips ~half the output bits).
  • For hash tables you want speed + distribution (FNV, MurmurHash, xxHash, SipHash for DoS-resistance) — not a cryptographic hash.
  • % capacity with a power-of-two capacity is a fast bitmask, but only mixes the low bits — hash functions must pre-mix.

Load factor & resizing

load factor α = n / capacity. As α rises, collisions and probe lengths grow. When it crosses a threshold (~0.75), rehash: allocate a larger table (usually 2×) and reinsert every element — O(n), but amortised O(1) per insert. This is why iterators are invalidated on insert.

Worst case & defence

All keys colliding → O(n) per operation (a linked list). Causes: bad hash, or an attacker choosing colliding keys (hash-flooding DoS). Defences: randomised per-process seed, SipHash, switching a bucket to a balanced tree above a threshold (Java 8 HashMap), or a tree map for untrusted keys.

Cheat Sheet
  • Average O(1) insert/find/delete; worst O(n); no ordering.
  • Hash must be deterministic, fast, well-distributed (avalanche). Not cryptographic for tables.
  • Chaining: bucket = list/tree; tolerates α > 1; simple delete; pointer-chasing.
  • Open addressing: probe sequence; α < 1; cache-friendly; delete needs tombstones.
  • Probing: linear (clustering), quadratic (less clustering), double hashing (best spread).
  • Resize (rehash) at α ≈ 0.7–0.75, grow ×2, reinsert all — O(n), amortised O(1); invalidates iterators.
  • DoS defence: seeded hash / SipHash / treeify overpopulated buckets.
  • A set is a hash table storing only keys; a map stores key→value.
Q&A
Chaining vs open addressing?
Chaining stores colliding entries in a per-bucket list, tolerates load factor > 1, and deletes easily, but chases pointers. Open addressing keeps everything in the array and probes for a free slot — better cache behaviour and less memory, but the load factor must stay below 1 and deletion needs tombstones or shifting.
What is the load factor and why does it matter?
α = entries / buckets. Higher α means more collisions and longer probe/chain lengths, degrading the O(1) average toward O(n). Tables rehash to a bigger array when α passes a threshold.
Why is resizing O(n) but insertion still amortised O(1)?
Resizing reinserts all n elements, but capacity doubles each time, so resizes happen geometrically rarely; summed over n inserts the total rehash work is O(n).
What makes a hash function good for a hash table?
Speed, determinism, and uniform distribution so different keys land in different buckets (small input changes should scatter the output). Cryptographic strength isn't needed unless you're defending against adversarial keys.
How does Java 8's HashMap mitigate collision attacks?
When a single bucket's chain exceeds 8 entries (and the table is large enough), it converts that bucket from a linked list to a red-black tree, bounding that bucket's operations at O(log n) instead of O(n).
Interview Questions

Basic warm-up

Average and worst-case lookup time for a hash table?
O(1) average, O(n) worst case (all keys collide).
What is a collision?
When two distinct keys hash to the same bucket index.
Name two collision-resolution strategies.
Separate chaining and open addressing (linear/quadratic probing, double hashing).

Intermediate core

In open addressing, why can't you just set a deleted slot to "empty"?
A later search for a key whose probe sequence passed through that slot would stop early at the "empty" and wrongly report "not found". You mark it as a tombstone (deleted-but-was-occupied) so searches keep probing, or you do a backward-shift deletion that repairs the probe sequence. Tombstones accumulate and eventually require a rehash.
Why is a power-of-two capacity with hash & (cap-1) risky, and how is it fixed?
It only uses the low bits of the hash, so a hash function that varies mostly in its high bits produces heavy clustering. Fixes: a hash function with good avalanche across all bits, an extra mixing step on the stored hash (Java's h ^ (h >>> 16)), or a prime-number capacity with true modulo (better distribution, slower operation).

Advanced deep

Compare linear probing, quadratic probing, and double hashing for clustering behaviour.
Linear (+1, +2, …): suffers primary clustering — runs of occupied slots grow and merge, so probe lengths blow up near high load; but it's the most cache-friendly (sequential access). Quadratic (+1, +4, +9, …): avoids primary clustering but has secondary clustering (keys with the same initial bucket follow the same probe path) and may not visit every slot unless capacity and constants are chosen carefully. Double hashing (step = hash2(key)): each key gets its own probe stride, eliminating both clustering types — best distribution, but two hash computations and random-access probing (cache-unfriendly). Modern implementations (Google's SwissTable, Rust's hashbrown) use SIMD-scanned linear probing to get linear's locality without its clustering pain.
How does a concurrent hash map allow safe multi-threaded access without a global lock?
Techniques: lock striping (Java 7 ConcurrentHashMap — N segment locks, so writers to different segments don't contend); per-bucket / CAS-based updates (Java 8 — CAS to install the first node, synchronise only on the bucket head for chains, help with resize); fully lock-free designs using atomic pointers and a "resize in progress" forwarding marker; or RCU / epoch schemes where readers never block and writers publish new versions. Reads are usually wait-free. Trade-offs: memory overhead, weaker iteration guarantees (weakly consistent iterators), and size() becoming approximate or expensive.

Trees & Binary Search Trees

Traversals, the BST invariant, and why an unbalanced BST is just a slow linked list.

Notes

Terminology

Root, parent/child, leaf, internal node, edge, depth (root to node), height (node to deepest leaf), subtree. A binary tree: each node has ≤ 2 children. Complete, full, perfect, balanced are distinct shapes.

DFS traversals are naturally recursive (call stack) or iterative with an explicit stack; level-order needs a queue.

Binary Search Tree

  • Invariant: for every node, all keys in the left subtree are < the node's key, all keys in the right subtree are >.
  • search, insert, delete: O(h) where h is the height. Balanced → O(log n); degenerate (sorted insertions) → O(n).
  • Delete cases: leaf (remove), one child (splice), two children (replace with in-order successor/predecessor, then delete that).
  • In-order traversal yields keys in ascending order — a free sorted iteration.

When BSTs degenerate

Inserting already-sorted (or reverse-sorted) data builds a path, not a bush → O(n) operations. Fixes: self-balancing trees (AVL, red-black — next topic), randomised insertion order, treaps, or just use a hash table if you don't need ordered iteration / range queries.

Cheat Sheet
  • Height = longest root→leaf path; depth = node's distance from root.
  • In-order = sorted (for a BST). Pre-order = serialize. Post-order = free / bottom-up aggregates. Level-order = BFS with a queue.
  • BST invariant: left subtree < node < right subtree, recursively.
  • search/insert/delete = O(h): O(log n) balanced, O(n) degenerate.
  • Delete-with-two-children: swap with in-order successor (leftmost of right subtree), then delete that.
  • Sorted input into a plain BST → linked-list shape → use a self-balancing tree.
  • Use a BST/ordered map for range queries, floor/ceil, ordered iteration; use a hash map otherwise.
  • DFS recursion depth = tree height → risk of stack overflow on skewed trees; go iterative if needed.
Q&A
Which traversal prints a BST's keys in sorted order?
In-order (left, node, right).
Difference between height and depth of a node?
Depth is the number of edges from the root down to the node; height is the number of edges from the node down to its deepest descendant leaf. The tree's height is the root's height.
What's the time complexity of BST search, and what does it depend on?
O(h), the height. For a balanced tree h ≈ log₂n; for a degenerate (linear) tree h = n.
How do you delete a node with two children from a BST?
Replace its key with its in-order successor (the smallest key in the right subtree) or predecessor, then recursively delete that successor node, which has at most one child.
Why can inserting sorted data into a BST be a problem?
Each new key is larger than all previous, so it always goes to the far right — the tree becomes a straight chain of height n, and every operation is O(n). Self-balancing trees restructure to keep height O(log n).
Interview Questions

Basic warm-up

What data structure does level-order traversal use?
A queue.
State the BST property.
For every node, all keys in its left subtree are smaller and all keys in its right subtree are larger than the node's key.

Intermediate core

Validate that a binary tree is a BST.
Recurse with an allowed (min, max) range: each node's key must be strictly within its bounds; recurse left with max = node.key, right with min = node.key. Checking only node.left.key < node.key < node.right.key locally is wrong — it misses violations deeper down. Equivalent: an in-order traversal must be strictly increasing.
Find the k-th smallest element in a BST.
In-order traversal, counting nodes; return the k-th visited. O(k) with early stop, O(h + k) to reach it. If the tree stores subtree sizes (an order-statistics tree), it's O(h): at each node compare k with left-subtree size to go left, return, or go right with adjusted k.

Advanced deep

How do you do an iterative in-order traversal with O(1) extra space?
Morris traversal: for each node with a left child, find its in-order predecessor (rightmost node of the left subtree) and temporarily set that node's right pointer to the current node (a "thread"). Walk left; when you return via a thread, output the node, remove the thread, and go right. It mutates pointers during traversal but restores them, using no stack — O(n) time, O(1) space. Trade-off: not thread-safe / not usable on a shared immutable tree, and more complex to get right.
Serialize and deserialize a binary tree. What's the key design choice?
Choose a traversal and explicitly mark null children (e.g. pre-order with # for null). Pre-order + null markers lets deserialize rebuild recursively by consuming tokens in the same order. Level-order + null markers also works (LeetCode's format). Without null markers a single traversal is ambiguous — you'd need two (e.g. in-order + pre-order), which fails if keys aren't unique. Cost: null markers roughly double the token count for sparse trees.

All give O(log n) search/insert/delete and, unlike a hash table, keep keys ordered (range queries, floor/ceil, sorted iteration). Balance is restored by rotations (local O(1) pointer rewires) after an insert/delete.

Binary heap

  • A complete binary tree stored in an array: node i's children are 2i+1, 2i+2; parent is (i-1)/2. No pointers.
  • Heap property: min-heap — every parent ≤ its children (root is the minimum). Max-heap is the mirror.
  • push: append, then sift up — O(log n). pop (min): swap root with last, shrink, sift down — O(log n). peek: O(1).
  • Build-heap from an unsorted array: sift down from the last internal node upward — O(n), not O(n log n).

Uses

Priority queue (Dijkstra, A*, task scheduling), heapsort (build max-heap, repeatedly pop), "top-k" (a size-k heap in O(n log k)), median maintenance (two heaps), merging k sorted lists.

Heap vs BST

A heap only gives you the min (or max) fast — no ordered iteration, no arbitrary search (that's O(n)). A balanced BST gives ordered operations but a larger constant and pointer overhead. Use a heap when you only ever want the extreme element.

Cheat Sheet
  • AVL: tightly balanced, more rotations, fastest reads. Red-black: looser, fewer rotations, default for library maps.
  • B/B+ trees: wide fan-out, one node per disk page → database and filesystem indexes.
  • Balanced BST ops all O(log n); rebalancing = O(1) rotations per level.
  • Binary heap = complete tree in an array; children of i at 2i+1/2i+2.
  • push/pop O(log n) (sift up/down), peek O(1), build-heap O(n).
  • Heap = priority queue; no search, no ordered traversal.
  • Heapsort: build max-heap O(n), pop n times O(n log n), in-place, not stable.
  • Top-k with a min-heap of size k: O(n log k). Streaming median: max-heap (low half) + min-heap (high half).
Q&A
How is a binary heap stored without pointers?
As an array representing a complete binary tree level by level. For index i: left child 2i+1, right child 2i+2, parent (i-1)/2. The completeness guarantee is what makes this indexing valid.
Why is building a heap O(n), not O(n log n)?
You sift down from the bottom up. Most nodes are near the leaves and sift down only a level or two; the work is ∑ (nodes at height h) × h, which converges to O(n). Inserting one-by-one with sift-up would be O(n log n).
AVL vs red-black tree — when does each win?
AVL keeps stricter balance, so lookups are slightly faster — better for read-heavy workloads. Red-black does fewer rotations per update, so it's better for write-heavy workloads and is the common choice for standard-library ordered maps.
Can you search a heap for an arbitrary value efficiently?
No — O(n). The heap property only orders parents vs children, not siblings or cousins. If you need search, use a balanced BST or keep a side hash map of value→index.
Why do databases use B-trees instead of binary balanced trees?
Disk/SSD reads happen in pages (4–16 KB). A B-tree node fills a page and has hundreds of children, so the tree is very shallow (3–4 levels for millions of keys) — each level is one I/O. A binary tree would need ~log₂n ≈ 20+ I/Os for the same data.
Interview Questions

Basic warm-up

What's at the root of a min-heap?
The smallest element. peek is O(1).
Insert and extract-min complexity for a binary heap?
Both O(log n) — sift up on insert, sift down after removing the root.
Does a self-balancing BST keep keys in sorted order?
Yes — in-order traversal is still sorted, which is why it supports range queries that a hash map can't.

Intermediate core

Find the k largest elements of an n-element array efficiently.
Maintain a min-heap of size k: push the first k, then for each remaining element, if it's larger than the heap's min, pop and push it. End with the k largest. O(n log k) time, O(k) space — better than sorting (O(n log n)) when k « n. (Quickselect gives O(n) average if you only need them unordered.)
Maintain the running median of a stream.
Two heaps: a max-heap for the lower half, a min-heap for the upper half, kept balanced in size (differ by ≤ 1). Insert into the appropriate heap, then rebalance by moving one element across if sizes diverge. Median is the top of the larger heap, or the average of both tops when equal. O(log n) per insert, O(1) query.

Advanced deep

Dijkstra with a binary heap is O((V+E) log V). What does a Fibonacci heap change, and why isn't it used much?
A Fibonacci heap gives amortised O(1) decrease-key and O(1) insert, with O(log n) extract-min, lowering Dijkstra to O(E + V log V) — asymptotically better for dense graphs. In practice it's rarely used: large hidden constants, poor cache locality (lots of pointer manipulation and node cutting), and complex implementation. Pairing heaps or just a binary heap with "lazy deletion" (push duplicates, skip stale pops) are simpler and faster on real inputs. It's a "great in theory" structure.
Why is heapsort O(n log n) worst-case and in-place, yet usually slower than quicksort in practice?
Heapsort's sift-down repeatedly jumps between array positions i and 2i+1/2i+2 — a scattered, cache-unfriendly access pattern — and it does more comparisons/swaps with worse branch prediction than quicksort's mostly-sequential partition scan. Quicksort's O(n²) worst case is avoidable (introsort: switch to heapsort when recursion goes too deep), so the standard library gets quicksort's speed with heapsort's guarantee. Heapsort shines when you need a hard worst-case bound and O(1) space, e.g. embedded or adversarial contexts.

BFS

  • Queue-based, explores by distance from the source.
  • Gives the shortest path in an unweighted graph (fewest edges).
  • O(V + E). Track visited to avoid revisiting; store parent to reconstruct paths.
  • Also: bipartite check (2-colour), level/"minimum steps" problems, multi-source BFS.

DFS

  • Stack/recursion, goes deep before wide.
  • O(V + E). Uses: cycle detection, topological sort (DAG), connected components, bridges/articulation points, strongly connected components (Tarjan/Kosaraju), maze/backtracking.
  • Edge classification (tree / back / forward / cross edges) — a back edge means a cycle.

Cycle detection

  • Undirected: DFS — a visited neighbour that isn't the parent means a cycle. Or union-find while adding edges.
  • Directed: DFS with three colours (white/grey/black) — an edge to a grey (in-progress) node is a back edge = cycle. Or Kahn's algorithm: if topological sort can't place all nodes, there's a cycle.

Topological sort

Linear ordering of a DAG so every edge points forward. Kahn's: repeatedly remove a node with in-degree 0. DFS: push nodes onto a stack on exit; reverse it. O(V + E). Used for build systems, task scheduling, dependency resolution.

Cheat Sheet
  • Adjacency list: O(V+E) space, sparse graphs (default). Matrix: O(V²), O(1) edge test, dense graphs.
  • BFS: queue, shortest path in unweighted graphs, level order, bipartite check. O(V+E).
  • DFS: stack/recursion, cycle detection, topological sort, components, bridges/SCC. O(V+E).
  • Always track visited; store parent to rebuild paths.
  • Directed cycle = back edge to a grey node (3-colour DFS) or Kahn's leftover nodes.
  • Undirected cycle = DFS hits a visited non-parent, or union-find sees both endpoints already joined.
  • Topological sort: Kahn (in-degree 0 queue) or DFS finish-time reverse; DAG only.
  • Weighted shortest path is a different tool (Dijkstra / Bellman-Ford — see Algorithms).
Q&A
When do you prefer an adjacency matrix?
Dense graphs (E ≈ V²), or when you frequently ask "is there an edge u→v?" and rarely iterate all neighbours. Otherwise the adjacency list's O(V+E) space wins for the sparse graphs that dominate practice.
Which traversal finds the shortest path in an unweighted graph, and why?
BFS. It expands nodes in non-decreasing order of distance from the source, so the first time it reaches a node is via a minimum-edge path.
How do you detect a cycle in a directed graph with DFS?
Mark nodes white (unvisited), grey (on the current DFS path), black (fully explored). If DFS finds an edge to a grey node, that's a back edge → there's a cycle.
What does topological sort require of the graph?
It must be a DAG (directed, acyclic). If a cycle exists, no valid linear ordering can exist.
Time and space complexity of BFS/DFS on an adjacency list?
O(V + E) time (each vertex and edge processed once). Space O(V) for the visited set plus the queue/stack (which can hold up to O(V)).
Interview Questions

Basic warm-up

Which structure backs BFS and which backs DFS?
BFS uses a queue; DFS uses a stack (explicit or the recursion call stack).
Space of an adjacency matrix for V vertices?
O(V²), regardless of how many edges exist.

Intermediate core

Count connected components in an undirected graph.
Iterate all vertices; each time you find an unvisited one, run BFS/DFS from it to mark its whole component and increment a counter. O(V + E). (Union-find also works: components = number of distinct roots after unioning every edge.)
Detect whether an undirected graph is bipartite.
BFS/DFS 2-colouring: colour the start, colour each neighbour the opposite. If you ever try to give a node a colour it already has that conflicts (a same-colour edge), it's not bipartite. Do this per component. O(V + E).
Implement Kahn's topological sort.
Compute in-degrees. Push all in-degree-0 nodes to a queue. Repeatedly pop a node, append to the order, and decrement each successor's in-degree, pushing any that hit 0. If the final order has fewer than V nodes, the graph has a cycle. O(V + E).

Advanced deep

Explain 0-1 BFS and when it beats Dijkstra.
When every edge weight is 0 or 1, use a deque: relax an edge of weight 0 by push_front, weight 1 by push_back. The deque stays sorted by distance in two "layers", so each node is finalised in O(1) amortised — total O(V + E), beating Dijkstra's O(E log V) and avoiding the heap entirely. Generalises to "0-k BFS" with k buckets (dial's algorithm) for small integer weights. Common in grid problems where moving costs 0 or 1.
How does Tarjan's algorithm find strongly connected components in one DFS pass?
During DFS it assigns each node a discovery index and tracks low[v] = the smallest index reachable from v's subtree via at most one back/cross edge to a node still on the stack. It keeps DFS-visited nodes on an explicit stack. When it finishes a node v with low[v] == index[v], v is the "root" of an SCC: pop the stack down to v — those nodes form one SCC. O(V + E), single pass, versus Kosaraju's two passes (DFS, transpose, DFS in finish order).

Union-Find & Tries

Two specialised structures: near-O(1) connectivity, and prefix-indexed strings.

Notes

Disjoint Set Union (Union-Find)

Maintains a partition of elements into disjoint sets, supporting:

  • find(x) — representative ("root") of x's set.
  • union(x, y) — merge the two sets.
  • connected(x, y) — find(x) == find(y).

Backed by a parent[] forest. Two optimisations make it nearly constant time:

  • Union by rank/size — attach the smaller tree under the larger, keeping trees shallow.
  • Path compression — during find, point every node on the path directly at the root.

Together: O(α(n)) amortised per operation, where α (inverse Ackermann) is ≤ 4 for any practical n — effectively O(1).

int find(int x) { return parent[x] == x ? x : (parent[x] = find(parent[x])); }
void unite(int a, int b) {
    a = find(a); b = find(b);
    if (a == b) return;
    if (size[a] < size[b]) swap(a, b);
    parent[b] = a; size[a] += size[b];
}

Uses: Kruskal's MST, connected components in a stream of edges, cycle detection while adding edges, "number of islands II", equivalence classes, percolation.

Trie (prefix tree)

  • A tree where each edge is a character; a path from the root spells a prefix; nodes flagged as "end of word".
  • insert, search, startsWith: O(L) where L = key length — independent of the number of stored keys.
  • Space can be large (a child pointer per possible character); compress with a radix/Patricia trie (merge single-child chains) or use a hash map per node.
  • Uses: autocomplete, spell-check, IP routing (longest-prefix match), dictionary word games, replacing a hash set when you need prefix queries or lexicographic order.
Cheat Sheet
  • Union-Find ops: find, union, connected, over a parent[] forest.
  • Union by size/rank + path compression → O(α(n)) ≈ O(1) amortised.
  • Union-Find uses: Kruskal MST, dynamic connectivity, cycle detection on edge insertions, equivalence classes.
  • Can't efficiently split sets or enumerate a set's members (unless you keep extra structures).
  • Trie: edges = characters, mark word-ends. insert/search/prefix = O(key length).
  • Trie lookup time is independent of dictionary size; space is the cost.
  • Compress with radix/Patricia trie; or store children in a hash map for sparse alphabets.
  • Trie uses: autocomplete, longest-prefix match (routing), lexicographic iteration, prefix counting.
Q&A
What two optimisations make union-find near-constant-time?
Union by rank/size (attach the shorter/smaller tree under the taller/larger one) and path compression (flatten the find path toward the root). Together they give O(α(n)) amortised.
What is α(n) practically?
The inverse Ackermann function — it grows so slowly it's ≤ 4 for any n that fits in the universe. So union-find operations are effectively O(1).
Name a classic use of union-find.
Kruskal's minimum spanning tree: sort edges by weight, add an edge only if its endpoints are in different sets (no cycle), then union them.
What's the time complexity of trie search, and why is that notable?
O(L), the length of the search key — it doesn't depend on how many keys are stored, unlike a BST (O(L log n)) or even a hash set in the worst case.
When is a trie better than a hash set?
When you need prefix operations (autocomplete, "does any stored word start with X"), longest-prefix matching, sorted/lexicographic iteration, or counting words with a given prefix — things a hash set can't do without scanning everything.
Interview Questions

Basic warm-up

What does find(x) return in a disjoint-set structure?
The representative (root) element of the set containing x. Two elements are in the same set iff their find results are equal.
What does each edge in a trie represent?
A single character; the path from the root to a node spells out a string prefix.
Trie operation to check if any word starts with "pre"?
startsWith("pre") — walk the trie following p→r→e; success if all edges exist. O(3).

Intermediate core

Use union-find to detect a cycle while building an undirected graph from a list of edges.
For each edge (u, v): if find(u) == find(v), adding this edge creates a cycle — report it. Otherwise union(u, v). Processing all m edges is O(m · α(n)).
Why does path compression alone (without union by rank) still give good amortised bounds?
Path compression alone gives O(log n) amortised per operation, and with union by rank/size added it drops to O(α(n)). Either optimisation alone is decent; both together are what reach inverse-Ackermann. Union by rank alone (no compression) is O(log n) worst case per op.
Estimate a trie's memory for 100k English words vs a hash set.
A naive array-of-26-children trie allocates 26 pointers per node; with millions of nodes that's tens of MB — often several times the hash set, which stores each string once plus a small overhead. Mitigations: hash-map children (only allocate used slots), radix/Patricia compression (collapse non-branching chains, big win for real dictionaries), or a DAWG (merge identical suffix subtrees). The trie "pays" memory to buy O(L) prefix queries.

Advanced deep

How would you support union and find plus rollback (undo the last k unions)?
Use union by rank/size without path compression (compression makes changes hard to undo), and keep a stack recording each union's effect (which root got a new parent, and the old rank/size). To roll back, pop the stack and restore parent and rank/size. Ops become O(log n) instead of O(α), but you get persistence — used in "offline dynamic connectivity" and segment-tree-on-time / DSU-on-tree techniques. A weighted / partially-persistent variant supports full history queries.
What is a suffix trie / suffix automaton used for, and why not just a plain trie of all suffixes?
A trie of all n suffixes of a length-n string has O(n²) nodes — too big. A suffix tree (Ukkonen's algorithm, O(n)) path-compresses it to O(n) nodes and answers substring queries, longest repeated substring, longest common substring of two strings, etc. in O(pattern length). A suffix automaton is an even more compact O(n) DAG recognising all substrings, great for counting distinct substrings. Both trade implementation complexity for powerful linear-time string analytics that a plain trie or hashing can't match.

Know the four that matter, their trade-offs, and when comparison sorts stop being optimal.

Stability

A stable sort preserves the relative order of equal keys. Matters when you sort by one field after another (sort by name, then stably by department). Merge/insertion/Tim are stable; quick/heap are not (without extra work).

The Ω(n log n) lower bound

Any sort that only compares elements needs Ω(n log n) comparisons in the worst case (there are n! orderings; each comparison gives 1 bit; log₂(n!) ≈ n log n).

Non-comparison sorts (beat the bound with structure)

  • Counting sort — O(n + k) for integer keys in a small range k. Stable.
  • Radix sort — O(d · (n + b)) for d digits in base b; sorts fixed-width integers/strings by repeated stable counting sort per digit.
  • Bucket sort — O(n) expected for uniformly distributed reals in [0, 1).
Cheat Sheet
  • Quicksort: avg O(n log n), worst O(n²), in-place, not stable, fastest real-world. Randomise the pivot.
  • Merge sort: always O(n log n), stable, O(n) space, ideal for linked lists / external sort.
  • Heapsort: always O(n log n), O(1) space, not stable, cache-unfriendly.
  • Insertion sort: O(n²), but O(n) on nearly-sorted; small-array base case.
  • std::sort = introsort; Python/Java-objects = Timsort (adaptive, stable).
  • Comparison sorts can't beat Ω(n log n) worst case.
  • Small integer range → counting sort O(n+k); fixed-width keys → radix sort; uniform reals → bucket sort.
  • Need stability → merge / Tim / counting; not quick / heap.
Q&A
Why is quicksort usually faster than merge sort despite the same average complexity?
It sorts in place with a tight, cache-friendly partition loop and low constant factors; merge sort does extra data movement into and out of an O(n) buffer. Quicksort's downside is the O(n²) worst case, mitigated by randomised pivots / introsort.
What does "stable" mean and when do you need it?
Equal elements keep their original relative order. You need it for multi-key sorting done in passes (sort by secondary key, then stably by primary), or when equal keys carry associated data whose order is meaningful.
Why can't a comparison sort be faster than O(n log n)?
There are n! possible input orderings; a comparison yields one bit, so a decision tree distinguishing all of them has depth ≥ log₂(n!) ≈ n log n. Any algorithm restricted to comparisons hits this bound in the worst case.
When is counting/radix sort applicable and what's the catch?
When keys are integers (or fixed-width) in a bounded range. Counting sort is O(n + k); if k is huge (e.g. 64-bit values), that's worse than n log n. Radix sort handles large ranges by processing digit-by-digit but needs a stable per-digit sort and extra space.
Which sort would you use for a nearly-sorted array?
Insertion sort (O(n) when few elements are out of place) or Timsort, which detects and merges existing sorted runs.
Interview Questions

Basic warm-up

Worst-case complexity of quicksort?
O(n²) — when the pivot is consistently the smallest or largest element (e.g. already-sorted input with a naive first-element pivot).
Which of merge sort and heapsort is stable?
Merge sort. Heapsort is not stable.
Which common sort is O(1) auxiliary space and always O(n log n)?
Heapsort.

Intermediate core

How does introsort avoid quicksort's O(n²) worst case?
It tracks recursion depth; if it exceeds ~2·log₂n (a sign of pathological pivots), it switches the current partition to heapsort, which is O(n log n) guaranteed. Small partitions are finished with insertion sort. So the common case runs at quicksort speed and the worst case is bounded.
You must sort 100 million 32-bit integers, memory permitting. What's fast?
LSD radix sort on the 4 bytes (four stable counting-sort passes, base 256) — O(4n) with a 256-entry histogram, typically beating comparison sorts for this size and key type. If memory is the constraint, an in-place MSD radix or introsort. If it doesn't fit in RAM, external merge sort.
Sort a large singly linked list. Which algorithm and why?
Merge sort. It needs only sequential access and O(1) extra pointers to split and merge (no random indexing, no shifting), it's stable, and it's O(n log n) worst case. Quicksort on a list is awkward (partitioning needs care) and heapsort needs random access.

Advanced deep

Explain how external merge sort handles data that doesn't fit in memory.
Phase 1 (run formation): read chunks that fit in RAM, sort each in memory (e.g. with quicksort/heapsort), write each as a sorted "run" to disk — producing ceil(N/M) runs for N records and memory M. Phase 2 (merge): do a k-way merge of the runs using a min-heap over the current front element of each run, streaming output to disk; k is bounded by how many input buffers fit in memory. If there are more runs than one merge pass can handle, merge in multiple passes (each pass reduces run count by factor k), giving O(N log_k(N/M)) I/O. Large sequential I/O and double-buffering are what make it practical.
Why does Timsort exist, and what real bug did its "galloping"/merge invariant have?
Real-world data has pre-sorted runs (appended logs, partially updated lists); Timsort finds ascending/descending runs, extends short ones with binary insertion sort to a minimum length, and merges runs while maintaining size invariants on a stack, using "galloping mode" (exponential search) when one run is consistently winning the merge. A 2015 formal-verification effort found the run-merging stack invariant was too weak, allowing the merge stack to exceed its preallocated size — a latent ArrayIndexOutOfBoundsException for adversarial inputs. It was fixed by strengthening the invariant / enlarging the stack. Lesson: even widely-deployed, "obviously correct" library sorts had a subtle bound bug found only by proof.

Recursion, Backtracking & DP

From "solve it in terms of smaller subproblems" to "and remember the answers".

Notes

Recursion

  • A function that calls itself on smaller input. Needs a base case and progress toward it.
  • Each call uses a stack frame → recursion depth is bounded by the stack (~10k–100k frames). Deep or unbounded recursion → stack overflow — convert to iteration + explicit stack, or use tail recursion where the language optimises it.
  • Cost = (number of calls) × (work per call). Draw the recursion tree.

Backtracking

Systematically build candidates and abandon ("prune") a partial candidate as soon as it can't lead to a solution. Template:

def backtrack(state, choices):
    if is_solution(state): record(state); return
    for choice in choices:
        if valid(state, choice):
            apply(state, choice)          # choose
            backtrack(state, next_choices) # explore
            undo(state, choice)            # un-choose

Uses: permutations/combinations/subsets, N-Queens, Sudoku, word search, generating valid parentheses, graph colouring. Worst case is exponential; pruning is what makes it tractable.

Dynamic programming

Applies when a problem has optimal substructure (optimal answer built from optimal sub-answers) and overlapping subproblems (the same sub-answers recur). Two styles:

Memoisation (top-down)Tabulation (bottom-up)
Formrecursion + a cachefill a table in dependency order
Computesonly needed statesall states
Overheadrecursion + hashingtight loops, often O(1) space with rolling arrays

Steps: define the state, write the recurrence (transition), identify base cases, decide iteration order, optionally reduce space. Classics: Fibonacci, coin change, knapsack, longest common subsequence, edit distance, longest increasing subsequence, matrix-chain, grid paths.

DP vs greedy vs divide-and-conquer

Divide-and-conquer: subproblems are independent (merge sort). DP: subproblems overlap. Greedy: a locally optimal choice is provably globally optimal (needs a proof; fails for 0/1 knapsack, works for fractional knapsack / Huffman / MST).

Cheat Sheet
  • Recursion needs a base case + strict progress toward it. Depth ≤ stack size.
  • Convert deep recursion to an explicit stack loop to avoid overflow.
  • Backtracking = choose / explore / un-choose, with pruning; exponential worst case.
  • DP requires optimal substructure + overlapping subproblems.
  • Memoisation = recursion + cache (lazy). Tabulation = iterative table fill (eager, often O(1) space with rolling rows).
  • DP recipe: state → recurrence → base cases → evaluation order → space optimisation.
  • Overlapping subproblems → DP; independent subproblems → divide & conquer; provable local-optimal → greedy.
  • Time ≈ (number of states) × (transitions per state).
Q&A
What two properties must a problem have for DP to apply?
Optimal substructure (the optimal solution is composed of optimal solutions to subproblems) and overlapping subproblems (the same subproblems are solved repeatedly in a naive recursion).
Memoisation vs tabulation?
Memoisation is top-down: normal recursion with a cache, computing only the states you actually reach. Tabulation is bottom-up: fill a table in an order where each entry's dependencies are already done, often allowing O(1)-space rolling arrays. Same complexity; different constant factors and stack usage.
How is backtracking different from brute force?
Brute force enumerates all candidates fully. Backtracking builds candidates incrementally and abandons a partial path the moment it violates a constraint (pruning), cutting the search space dramatically.
When does greedy fail where DP succeeds?
0/1 knapsack: taking the highest value-per-weight item first can be suboptimal because you can't take fractions. DP considers all combinations. Coin change with arbitrary denominations is another (greedy fails for {1, 3, 4} making 6).
What limits recursion depth in practice?
The call stack size (often ~1–8 MB → tens of thousands of frames). Beyond that you get a stack overflow; rewrite iteratively with an explicit stack or use an explicit work queue.
Interview Questions

Basic warm-up

What must every recursive function have?
A base case (a condition that returns without recursing) and recursive calls that move strictly toward it.
What does memoisation add to plain recursion?
A cache of already-computed results, so each distinct subproblem is solved once. Turns exponential recomputation into polynomial.
Three steps of the backtracking pattern?
Choose (apply a candidate), explore (recurse), un-choose (undo it before trying the next).

Intermediate core

Coin change (min coins for amount N, unlimited coins). Give the DP.
dp[0] = 0; for a from 1 to N: dp[a] = 1 + min(dp[a - c]) over all coins c ≤ a (infinity if none). Answer dp[N]. O(N × #coins) time, O(N) space. This is bottom-up tabulation; the state is "min coins to make amount a".
Why is naive recursive Fibonacci O(φⁿ) and how does DP fix it?
fib(n) calls fib(n-1) and fib(n-2), recomputing the same values exponentially — the call tree has ~φⁿ nodes. Memoise (cache fib(k)) or tabulate (loop keeping the last two values) to make it O(n) time, and O(1) space with the rolling-variable version.
Generate all subsets of a set. Recursion structure?
For each element, branch on "include it" or "exclude it", recursing on the rest; at the end of the list, emit the current subset. 2ⁿ leaves. Equivalent iterative form: for each of the 2ⁿ bitmasks, pick the elements whose bit is set.

Advanced deep

How do you reduce a 2-D DP (like edit distance) from O(nm) space to O(min(n, m))?
Each cell dp[i][j] depends only on dp[i-1][j], dp[i][j-1], dp[i-1][j-1] — i.e. the current and previous row. Keep two 1-D arrays (prev row, current row), or even one array plus a saved "diagonal" scalar, iterating so you overwrite each entry only after its old value has been used. Space drops to O(m) (choose the shorter dimension as the row). The catch: you lose the ability to backtrack the actual alignment/path afterward — if you need the path, either keep the full table, or use Hirschberg's divide-and-conquer to recover it in O(nm) time and O(min(n,m)) space.
What is "DP on subsets" (bitmask DP) and its complexity, with an example?
State = a subset of up to ~20 items encoded as an integer bitmask, plus maybe a position. Transitions add/remove one element. Example: Travelling Salesman — dp[mask][i] = shortest path visiting exactly the set mask, ending at city i; transition dp[mask | (1<<j)][j] = min(dp[mask][i] + dist[i][j]). Complexity O(2ⁿ · n²), feasible for n ≤ ~20. Also used for assignment problems, "minimum number of groups", and Steiner-tree-style problems. The exponential factor is inherent (these are NP-hard); bitmask DP just makes small n practical and is far better than brute-forcing n! orders.
